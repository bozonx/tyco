# Платформенное тестирование и виртуальные машины

Как проверяется платформенный слой (`src-tauri/src/services/platform/`) в
настоящих сессиях Linux и Windows. Устройство самого слоя —
[cross-platform.md](cross-platform.md), общие команды тестов —
[testing.md](testing.md). Подробности runner — [scripts/vm/README.md](../scripts/vm/README.md),
точные проверки по платформам — [scripts/vm/coverage.md](../scripts/vm/coverage.md).

## Уровни проверки

| Уровень                | Команда                        | Что проверяет                                                                                |
| ---------------------- | ------------------------------ | -------------------------------------------------------------------------------------------- |
| Unit                   | `pnpm test:unit:rust`          | Чистая логика: определение сессии, состояние трекера, классификация окон X11, утилиты буфера |
| Адаптеры в контейнерах | `pnpm test:platform:linux <x>` | X11/KWin/Sway без экрана, без сети                                                           |
| Native desktop smoke   | `pnpm test:desktop`            | Настоящий Tauri + WebDriver на Linux/X11 и Windows                                           |
| VM                     | `pnpm test:vm`                 | Полная пользовательская сессия: порталы, хоткеи, фокус, трей, keyring, звук, сон             |

Playwright проверяет только интерфейс с подменой desktop IPC.

### Адаптеры в контейнерах

`pnpm test:platform:linux x11|kwin|sway`. Образ на Debian Trixie с KWin 6;
сборка скачивает Rust-зависимости, контейнер запускается с `--network=none`.
Workflow `.github/workflows/linux-platform.yml` гоняет матрицу на Ubuntu 24.04.
Обычный `cargo test` эти тесты пропускает (`#[ignore]`).

| Сессия                   | Проверки                                                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Xvfb + Openbox           | x11rb-трекер, своё/чужое окно, активация, вставка XSendEvent, xclip и PRIMARY, восстановление буфера, новая копия, закрытие цели |
| KWin virtual + XWayland  | Production KWin-скрипты и D-Bus-отчёты, выбор и активация цели, вставка в XWayland-клиент, wl-clipboard/PRIMARY, закрытие цели   |
| Sway headless + libinput | wlr-foreign-toplevel-трекер, wl-clipboard/PRIMARY, настоящий ydotool, закрытие цели, отказ снимка буфера вне KDE                 |

Получатель — отдельный GTK-процесс, записывающий содержимое поля в файл. Окно
Tyco имитируется вторым процессом. Виртуальный KWin не читает libinput, поэтому
не проверяет ydotool и полную Wayland-вставку. Строка Sway требует `/dev/uinput`,
`/dev/input`, seatd и привилегированный контейнер — запускать только на
выделенном тестовом хосте (`modprobe uinput`). GNOME/Mutter и Weston сюда не входят.

### Native desktop smoke

`pnpm test:desktop`: production CSP, IPC, сохранение данных, CLI, перезапуск.
На Linux/X11 (Xvfb) ещё и полный путь вставки: GTK-редактор → `tyco-ctl` →
ввод в webview Tyco → вставка → проверка текста в чужом процессе. Xvfb не
читает устройства ввода, поэтому `scripts/linux-platform/ydotool-xtest.py`
заменяет ydotool и воспроизводит клавиши через XTest. На Windows выполняются
только проверки перезапуска. Wayland-вставку smoke не доказывает.

## Зачем VM

VM нужны для того, чего нет в контейнерах: системные хоткеи и диалоги порталов,
вставка в чужие приложения, фокус, трей, системное хранилище секретов,
аудиоустройства, установка пакета, lock/logout/reboot/suspend. Tyco управляется
через WebDriver, но результат проверяется независимо от его DOM и IPC: по тексту
в чужом процессе, байтам TTY, дереву accessibility, хешам keyring, событиям QMP,
клиентам PipeWire. Скриншот — дополнительное свидетельство.

## Стенды

| Профиль            | Сессия                 | Порт | Состояние                     |
| ------------------ | ---------------------- | ---- | ----------------------------- |
| `fedora44-kde`     | Fedora 44 KDE, Wayland | 2253 | native, package (AppImage)    |
| `ubuntu2604-gnome` | Ubuntu 26.04 GNOME     | 2254 | native; package не реализован |
| Windows 11         | —                      | —    | не реализован                 |
| Debian 13 KDE      | —                      | —    | не реализован (база LHC есть) |
| Debian 13 Xfce/X11 | —                      | —    | не реализован (базы нет)      |
| Kubuntu 26.04 KDE  | —                      | —    | не реализован (база LHC есть) |

Профили — `scripts/vm/profiles/*.json`. Все стенды x86_64. macOS и ARM64 не
проверяются; Windows 10 в VM не подтверждена.

### Базовые образы

Используются базы Left Hand Control в `/mnt/disk2/vm/` (`lhc-fedora-kde`,
`lhc-ubuntu2604-gnome`, `lhc-debian13-kde`, `lhc-kubuntu2604`,
`left-hand-control-windows`). Правила:

- база LHC только для чтения, её `vm.json` не меняется, активные overlay и
  cache-диски LHC не подключаются;
- Tyco создаёт свой подготовленный overlay (`prepared.qcow2`, read-only) и
  одноразовые диски на каждый прогон; GNOME использует собственную read-only
  копию базы (`source.qcow2`);
- при подготовке в overlay отключаются автозапуск LHC, remapper и его GNOME
  extension;
- код `scripts/vm/vmlib.py` свой, по образцу LHC; скрипты LHC на Tyco не запускаются.

Всё сгенерированное — в игнорируемом `dev_files/vm/`.

## Запуск

```sh
python3 scripts/vm/prepare-tools.py        # tauri-driver/WebKitWebDriver из образа desktop-smoke
pnpm test:vm --suite prepare               # один раз: подготовленная база (нужна сеть)
python3 scripts/vm/build-appimage.py       # сборка в Ubuntu 24.04 (glibc совместима с гостем)
pnpm test:vm --suite native \
  --artifact "src-tauri/target/container/debug/bundle/appimage/<name>.AppImage" \
  --ctl src-tauri/target/container/debug/tyco-ctl
pnpm test:vm:unit                          # тесты самого runner
```

Для GNOME всегда передавать `--profile scripts/vm/profiles/ubuntu2604-gnome.json
--vm dev_files/vm/ubuntu2604-gnome-v2`; по умолчанию используется Fedora.
`--artifact` принимает AppImage или embedded-бинарник
(`build-appimage.py --no-bundle`; использует WebKitGTK гостя). Release-пакет:
`build-appimage.py --release` и `--suite package`.

| Набор / флаг        | Что делает                                                     |
| ------------------- | -------------------------------------------------------------- |
| `--suite smoke`     | запуск и основной путь ввода, 3 цикла вставки                  |
| `--suite native`    | все применимые VM-01–17, 5 циклов                              |
| `--stress`          | то же, минимум 20 циклов hotkey/focus                          |
| `--only ID,...`     | адресная диагностика; не приёмка платформы                     |
| `--suite package`   | установка/запуск offline/переустановка/удаление release-пакета |
| `--keep`, `--show`  | сохранить успешный overlay, показать окно QEMU                 |
| `--hold-on-failure` | не выключать упавший гость до Enter                            |

Переходы сессии выполняются по три раза независимо от числа циклов. Отмена
портала, топология мониторов и каждый переход сессии идут в отдельных
одноразовых VM.

### Что гарантирует runner

- Блокировки стенда и порта, проверка идентичности базы до загрузки; teardown и
  освобождение блокировок при любом исходе. Неудачный прогон сохраняет диск.
- Файлы runner замораживаются на время прогона, их хеши пишутся в отчёт.
- Сеть: QEMU restricted + firewall в госте; разрешены только loopback-fixtures и
  SSH, недоступность внешнего адреса проверяется.
- Настоящая сессия: без Xvfb, без `dbus-run-session`, с реальными композитором и
  порталами. Программный рендеринг WebKit/Qt на виртуальной VGA явно записывается.
- Хоткеи нажимаются через QMP (вызов CLI не проверяет регистрацию); нажатия
  подтверждаются в ядре гостя. Диалоги порталов отвечаются через QMP.
- Тестовый config: английский интерфейс, Ctrl+Alt+I, Ctrl+Enter, история включена.
- Автоматических повторов действий нет, таймауты — это FAIL.

Получатели: KDE — Kate, Konsole, GTK-окна Wayland/XWayland, Firefox; GNOME —
GTK-получатели, GNOME Terminal, отдельный WebKitGTK-браузер. Что именно
проверяется на каждой платформе — в coverage.md.

Особенности GNOME: нет трекинга и активации чужих окон (возможность
`focusReturn`), поэтому гарантии VM-06 не заявляются; нет снимка буфера,
вставленный текст остаётся в буфере; терминал требует явно настроенного
сочетания вставки.

## Вердикты

- PASS — только по наблюдаемому результату. SKIP и BLOCKED имеют причину и не
  считаются пройденными; любой FAIL/BLOCKED даёт ненулевой код выхода.
- Неподдерживаемая возможность проверяется отдельным сценарием отказа.
- `--only` не подтверждает весь набор; функциональная, package- и
  hardware-приёмка имеют отдельные статусы.
- Дефект ОС/зависимости/гипервизора, воспроизведённый без Tyco, — внешнее
  ограничение, а не блокер продукта; исходный FAIL сохраняется, обработка
  ошибки Tyco проверяется. Неизвестную причину внешней не объявлять.

Известные внешние ограничения:

- KWallet 6.31.0 теряет только что записанный секрет при немедленной
  перезагрузке; проверки жизненного цикла используют заранее сохранённый секрет.
- QEMU/Q35 ломает повторный S3; suspend проверяется на i440fx (`pc`).
- Обновление пакета BLOCKED, пока нет реального предыдущего релиза
  (`--previous-artifact`); переустановка не заменяет миграцию.

VM не подтверждает физические GPU, микрофон/Bluetooth, мониторы и аппаратный сон.

## Когда запускать

- native smoke — после изменений platform, activation, hotkeys, clipboard,
  selection, жизненного цикла окон; адресные сценарии — по изменённой подсистеме;
- полный native на всех реализованных стендах и package — перед выпуском.

Обычный CI VM не запускает. Непроверенная затронутая платформа блокирует её приёмку.

## Отчёты

Каждый прогон пишет `report.json`, скриншоты, события QMP и диагностику гостя в
`dev_files/vm/<стенд>/runs/`. Итоги значимых прогонов — в
[`testing-results/`](testing-results/): commit и dirty diff, SHA256 артефакта,
команда, профиль и база, ОС/сессия/WebKit/портал, ID сценариев со статусами.
Исторические отчёты не переписываются. Секреты и пользовательские документы в
артефакты не попадают.
