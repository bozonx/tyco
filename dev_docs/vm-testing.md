# План нативного тестирования в виртуальных машинах

Дата актуализации: 2026-10-26. Это план внедрения, а не отчёт о пройденных
проверках всей матрицы Tyco. Fedora KDE подготовлена и проверяется автоматическим
runner; для Ubuntu GNOME реализованы отдельные нативные сценарии с учётом ограничений. Остальные профили пока не реализованы. Исходные диски соседнего проекта
используются read-only, изменения выполняются только в отдельных Tyco-overlay.

## Границы проверки

Playwright проверяет интерфейс с подменой desktop IPC. Существующий
`pnpm test:desktop` уже запускает настоящий Tauri/WebDriver на Linux и Windows:
production CSP, IPC, сохранение данных, CLI, перезапуск; на Linux/X11 — также
вставку в отдельный GTK-процесс. `pnpm test:platform:linux` проверяет адаптеры
X11/KWin/Sway в контейнерах. Повторять всю эту матрицу в VM не требуется.

VM нужны для полной пользовательской сессии: системные хоткеи и диалоги порталов,
вставка в чужие приложения, фокус и окна, трей, системное хранилище секретов,
аудиоустройства, установка пакета, выход/вход в сессию и сон. WebDriver можно
использовать внутри VM для управления Tyco, но действие ОС и результат в чужом
процессе должны проверяться независимо от DOM Tyco и его IPC-ответов.

Базовые команды и границы существующей автоматизации: [testing.md](testing.md).
Реализованные платформенные механизмы: [cross-platform.md](cross-platform.md).

## Выбранные ОС

Все первые стенды — x86_64. Версии ниже взяты из локальных документов LHC и имён
конфигураций; при первом запуске записать фактические версии ОС, desktop, ядра,
WebKitGTK/WebView2 и порталов. Не обновлять базу автоматически между прогонами.

| Стенд                           | Роль и объём                                                        | Почему нужен                                                                              |
| ------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Windows 11                      | Обязательный полный нативный прогон                                 | UI Automation, HWND, SendInput, Credential Manager, WebView2, UIPI                        |
| Debian 13 KDE Plasma 6, Wayland | Обязательный полный прогон; DEB и AppImage                          | Консервативные библиотеки, KWin, Secret Service, основной путь Wayland-вставки            |
| Fedora 44 KDE Plasma 6, Wayland | Обязательный полный прогон AppImage                                 | Более новый стек KDE/WebKitGTK, SELinux и другие системные зависимости                    |
| Ubuntu 26.04 GNOME, Wayland     | Обязательный прогон с учётом ограничений                            | Другой portal backend, отсутствие KWin/layer-shell, корректная деградация                 |
| Debian 13 Xfce, X11             | Обязательный полный прогон; новый отдельный стенд                   | Настоящая X11-сессия, EWMH, xdotool/xclip, терминальные сочетания; Xvfb этого не заменяет |
| Kubuntu 26.04 KDE, Wayland      | Дополнительный прогон перед выпуском и при изменениях упаковки/KWin | Уже готовая база Ubuntu с KDE; проверка DEB на другой версии библиотек                    |

Итого: Windows 11 и четыре обязательные Linux-среды; Kubuntu — расширение перед
выпуском. Debian KDE и Xfce можно получить из одной основы, но запускать как
раздельные профили с явно выбранной сессией и независимыми настройками.

Windows 10 остаётся заявленной в cross-platform.md, но пока без подтверждения VM.
Если её поддержку сохраняем к выпуску, нужен отдельный Windows 10 22H2 прогон;
Windows 11 его не заменяет. macOS и ARM64 вне этого этапа и не получают статус
проверенных. Для Sway/Hyprland пока оставляем адаптерные тесты; полноценную VM
добавляем при расширении поддержки, с проверкой внешнего назначения хоткеев.
Arch/openSUSE пока не добавляем: сначала закрываем разные backend и пакеты.

## Что можно взять из Left Hand Control

Источник: `../left-hand-control/docs/development/guide.md`, раздел L4,
`docs/testing/` и `apps/slint-shell/scripts/vm/`.

| Существующий каталог                      | Имя в vm.json      | SSH-порт хоста |
| ----------------------------------------- | ------------------ | -------------- |
| `/mnt/disk2/vm/left-hand-control-windows` | `windows11`        | 2241           |
| `/mnt/disk2/vm/lhc-debian13-kde`          | `debian13-kde`     | 2232           |
| `/mnt/disk2/vm/lhc-fedora-kde`            | `fedora44-kde`     | 2231           |
| `/mnt/disk2/vm/lhc-ubuntu2604-gnome`      | `ubuntu2604-gnome` | 2233           |
| `/mnt/disk2/vm/lhc-kubuntu2604`           | `kubuntu2604`      | 2234           |

Во всех пяти каталогах присутствуют `vm.json` и указанный базовый диск.
Также найдены специальные профили Windows clean-package/S3 и Debian automation.
Они не являются независимыми чистыми базами: часть ссылается на сохранённые
run-overlay или общие диски. Debian automation использует порт 2233, совпадающий
с GNOME: существующие профили нельзя безусловно запускать параллельно.

В LHC `vmlib.py` создаёт одноразовый qcow2 overlay, запускает QEMU/KVM, управляет
вводом и снимками через QMP, копирует файлы по SCP, собирает логи и удаляет
временный диск после остановки. `--keep` сохраняет диск, `--show` показывает окно.
Windows использует отдельные копии UEFI variables/TPM и постоянный build cache.
Гостевые задания Windows запускаются в интерактивной сессии, а не в SSH desktop.

**Решение:** использовать те же замороженные базовые образы через отдельные
Tyco-профили и одноразовые overlays. Не запускать базовый диск на запись,
не использовать активный overlay LHC и не подключать его cache-диск на запись.
Для Windows отдельно копировать UEFI variables и TPM, а кэш Tyco создать свой.
Выделить Tyco-порты 2251–2256 после проверки, что они свободны. Не менять оригинальные
`vm.json`. Внутри Tyco-overlay остановить LHC/autostart/remapper и отключить его
GNOME extension, чтобы они не перехватывали ввод и не расширяли возможности Tyco.
Проверку совместной работы с LHC вынести в отдельный необязательный сценарий.

Код `vmlib.py` пригоден как образец, но сейчас привязан к корню и отчётам LHC.
В Tyco нужен свой небольшой инфраструктурный модуль с указанием происхождения,
независимыми каталогами и блокировками ресурсов. Не импортировать его по относительному
пути из соседнего checkout. `run-linux.py`, `run-gnome.py`, `run-windows.py` и
prepare-скрипты LHC содержат продуктовые сценарии, группы input и разрешения
RemoteDesktop: их нельзя запускать на Tyco как готовый тест.
Tyco использует GlobalShortcuts и ydotool с RemoteDesktop fallback; GNOME bridge LHC не используется.

получателя, активное окно и число выполнений. Скриншот — дополнительное свидетельство.
Для текста использовать ASCII, кириллицу, emoji/ZWJ, многострочный и длинный текст.

VM-04–08: получатели KDE — Kate и Konsole плюс XWayland GTK editor; Xfce —
Mousepad и терминал; Windows — Notepad и браузерное поле; GNOME — Text Editor
и терминал для доступных операций. Версии получателей записать в отчёт.
Выделение в браузере и простом редакторе важно проверять отдельно: API доступности
и clipboard ведут себя по-разному. Неподдерживаемый путь — отдельная проверка
деградации, а не пропущенный положительный тест.

Уведомления VM проверяем на Linux на ошибке фонового действия. Windows backend
уведомлений сейчас пустой: успешный возврат функции не доказывает уведомление ОС.
Автозапуск проверять только если появляется реализованная настройка/системная запись;
наличие автологина тестового пользователя не доказывает автозапуск Tyco.

## Как запускать

### Сейчас: доступные команды

Из корня Tyco, после установки зависимостей и инструментов согласно testing.md:

```sh
pnpm test:integration:rust
pnpm test:browser:container
pnpm test:desktop:container
pnpm test:platform:linux x11
pnpm test:platform:linux kwin
```

Sway с доступом к input-устройствам запускать только на выделенном тестовом хосте,
как описано в cross-platform.md. Эти команды не запускают полноценных VM.

В госте с toolchain для проверки настоящего приложения:

```sh
pnpm install --frozen-lockfile
pnpm tauri:build --debug --no-bundle
cargo build --manifest-path src-tauri/Cargo.toml --locked -p tyco-ctl
pnpm test:desktop
cargo test --manifest-path src-tauri/Cargo.toml keychain -- --ignored
```

Нужны tauri-driver и платформенный WebDriver: WebKitWebDriver на Linux,
msedgedriver той же версии, что Edge, на Windows. Запускать в существующей
интерактивной сессии пользователя с её session bus/display, без Xvfb и без нового
`dbus-run-session`. На Windows SSH-задача должна передать запуск интерактивному
пользователю через scheduled task. `pnpm test:desktop` — существующий smoke;
он не реализует всю VM-матрицу и не доказывает Wayland-вставку.

### Автоматический runner Fedora KDE

Реализован `scripts/vm/`: независимый lifecycle QEMU/KVM, подготовленный Tyco-overlay,
одноразовые диски, блокировки ресурсов, QMP-ввод, управление Tyco через WebDriver,
отдельные GTK-получатели Wayland/XWayland и независимый наблюдатель окон KWin.
Исходная база LHC остаётся read-only. По умолчанию профиль Fedora использует порт
2253, а диски и подробные артефакты находятся в игнорируемом `dev_files/vm/`.

```sh
# Extract tools from the existing local desktop-test Docker image.
python3 scripts/vm/prepare-tools.py
# Prepare a separate Tyco base with dependencies once.
pnpm test:vm --suite prepare
# Build the embedded application and CLI.
pnpm tauri:build --debug --no-bundle
cargo build --manifest-path src-tauri/Cargo.toml --locked -p tyco-ctl
# Fully automated offline smoke without manual input.
pnpm test:vm --suite smoke --artifact src-tauri/target/debug/tyco --ctl src-tauri/target/debug/tyco-ctl
pnpm test:vm:unit
```

Для AppImage использовать `python3 scripts/vm/build-appimage.py`: сборка идёт
в Ubuntu 24.04 с отдельным persistent build cache. Пакет, собранный на более
новом хосте, может требовать отсутствующую в Fedora glibc. Передать полученный
`src-tauri/target/container/debug/bundle/appimage/*.AppImage` в `--artifact`,
а `src-tauri/target/container/debug/tyco-ctl` — в `--ctl`.

В `--artifact` также можно передать собранный debug AppImage. Внутри VM не нужны
Node/Rust. Разрешение GlobalShortcuts выдаётся настоящему диалогу KDE через QMP;
для Qt-диалогов и WebKit в виртуальной VGA-среде явно настроен программный
рендеринг. Его переменные записываются в отчёт. Desktop-запись тестовой установки
создаётся перед запуском для идентификации приложения порталом. Тестовый config
включает историю разработки, английский интерфейс, Ctrl+Alt+I и Ctrl+Enter.

Подробные инструкции: [scripts/vm/README.md](../scripts/vm/README.md).
Точное покрытие и ограничения: [scripts/vm/coverage.md](../scripts/vm/coverage.md).
Наличие runner не означает успешную приёмку: FAIL/BLOCKED сохраняются в отчётах,
а не заменяются ручной проверкой. Реализованы реальные системные диалоги,
конфликты хоткеев, выбор и перетаскивание файлов, секреты, аудио, DPI и смены
сессии. Исторический запуск обнаружил FAIL при повторном сне, удалении микрофона
и перезагрузке после записи секрета. Продолжение без AppImage добавляет HTML-only
clipboard, несколько мониторов и исправление захвата звука; сон проверяется на
i440fx из-за независимого сбоя Q35. Дефект немедленной записи KWallet сохраняется;
проверки жизненного цикла явно используют заранее сохранённый секрет.
См. [продолжение проверки](testing-results/2026-10-25-fedora44-kde-followup.md).
Установка release AppImage проверяется отдельно;
обновление BLOCKED без реального предыдущего релиза. Для Ubuntu GNOME добавлены отдельный профиль и начальные нативные проверки;
см. [результаты Ubuntu GNOME](testing-results/2026-10-26-ubuntu2604-gnome.md).
Остальные ОС ещё не имеют реализованных профилей. См. [результаты Fedora](testing-results/2026-10-25-fedora44-kde-current-head.md).

### Требования runner и расширение матрицы

Ниже — требования к полному runner и полной матрице; выполненные подслучаи smoke
не заменяют их.

1. Проверить QEMU, qemu-img, KVM, SSH/SCP, свободные порты, место и память;
   Windows дополнительно OVMF/swtpm. Брать 4 vCPU/6 GiB для запуска Linux,
   Windows — по существующему профилю; сборку выполнять отдельно либо выделять
   больше памяти. Не подключать общие host clipboard и input-устройства.
2. Захватить блокировки VM/порта/постоянных дисков, создать overlay, независимые
   UEFI/TPM и run-каталог. Сохранить SHA исходников и артефакта, состояние dirty tree.
3. Дождаться SSH и именно нужной разблокированной desktop-сессии. Проверить
   `XDG_SESSION_TYPE`, desktop, portal backend, tray host, keychain и зависимости
   в контексте пользователя. Неправильная сессия — ошибка подготовки, не PASS.
4. Скопировать артефакт и offline fixtures, установить зависимости в Tyco-overlay,
   запустить получателя и Tyco в пользовательской сессии. Ввести системный хоткей
   через QMP: вызов CLI вместо нажатия не проверяет регистрацию хоткея.
5. Выполнить сценарии с ожиданием наблюдаемого состояния и ограниченным timeout,
   без фиксированных sleep как критерия успеха. При отказе сохранить диагностику;
   teardown выполняется независимо от результата. Автоматических повторов нет.
6. Собрать отчёт, выключить VM и удалить успешный overlay, если нет `--keep`.
   При неудаче сохранять диск по явной политике runner, не терять логи.

Наборы: `smoke` — VM-01/02/04 либо VM-10 для GNOME;
`native` — все применимые VM-01–17; `package` — VM-18 и smoke установленного
артефакта в чистом госте без Node/Rust. Sleep/audio/DPI и системные диалоги также подлежат автоматизации. Пока сценарий
не реализован или среда не даёт надёжного наблюдения, его статус — BLOCKED с
причиной. Ручными остаются только свойства, которые нельзя воспроизвести и
проверить автоматически; отсутствие автоматизации само по себе не основание
переносить проверку в ручную и не даёт PASS.

В production config сейчас только DEB/AppImage. Fedora сначала проверяет AppImage;
RPM не объявляем готовым. Windows debug binary можно проверять уже сейчас,
а для VM-18 сначала добавить сборку NSIS/MSI и чистую Windows-базу с WebView2.
Проверять release-пакет отдельно от debug: `TYCO_DEV_HOME` работает только в debug,
для release изоляцию обеспечивает одноразовый guest user/disk.
Обновление требует двух реальных версий артефакта; повторная установка одной
версии не считается проверкой миграции.

Offline означает запрет внешнего выхода гостя при сохранении SSH-канала и локальных
fixtures. QEMU user networking сам по себе интернет не отключает: runner должен
применить явную фильтрацию. Для облачных AI-провайдеров отдельный opt-in онлайн
smoke с тестовыми ключами; он не заменяет offline-приёмку и не блокирует её.

## Порядок внедрения и частота

1. Подготовить Tyco-профили поверх обнаруженных баз, проверить чистоту, сессии и
   зависимости. Создать Xfce/X11-базу. Ничего не менять в базах LHC.
2. Реализовать lifecycle runner, отчёт и независимый GTK/Windows-получатель,
   который сохраняет фактический текст и фокус. Сначала smoke на Debian KDE и Windows.
3. Закрыть VM-04–09/17: это наиболее опасные ошибки доставки текста. Затем хоткеи,
   порталы, keychain, tray, dialogs и остальные native-сценарии на обязательных ОС.
4. Добавить чистую package-приёмку, Windows installer, upgrade и Kubuntu.
   Автоматизировать lock/resume и audio fixture с независимыми наблюдениями.
5. Запускать native smoke после изменений platform/activation/hotkeys/clipboard/
   selection/window lifecycle; targeted сценарии — по изменённой подсистеме.
   Полный native прогон обязательных ОС и package-набор с Kubuntu — перед выпуском.
   Сначала локально по запросу, затем на выделенном KVM runner; обычный CI остаётся
   быстрым. Непроверенная затронутая платформа явно блокирует её приёмку.

## Отчёты и условия приёмки

Хранить большие логи/скриншоты/видео/overlay вне Git. В `dev_docs/testing-results/`
сохранять небольшие итоговые отчёты значимой приёмки, когда появится первый прогон.
Каждый отчёт содержит commit и dirty diff/hash, SHA256 пакета, точную команду,
профиль и идентификатор базового образа, ОС/сессию/desktop/WebView/portal,
метод ввода, получателей, ID сценариев с PASS/FAIL/SKIP/BLOCKED и ссылки на артефакты.
Секреты и реальные пользовательские документы в артефакты не включать.

PASS требует наблюдаемого результата. SKIP и BLOCKED имеют причину и не считаются
пройденными. Известная неподдерживаемая возможность имеет явный сценарий отказа;
неожиданная невозможность проверить поддерживаемую функцию блокирует приёмку.
Для сна сохранять boot ID и события suspend/resume; перезагрузка не равна пробуждению.
Обычный smoke выполняет три цикла вставки; полный native — пять. Стресс-прогон
`--stress` выполняет минимум 20 циклов hotkey/focus без потери/дублирования текста
и залипших клавиш. Для lifecycle сохраняются три восстановления каждого типа.

VM проверяет виртуальную аудиокарту и виртуальный GPU. Реальный микрофон, Bluetooth,
NVIDIA/AMD/Intel, аппаратный сон и несколько физических мониторов требуют отдельной
проверки на железе. Успешный VM-прогон не снимает эти ограничения и не подтверждает
платформу целиком без указания набора сценариев.

## Правила закрытия этапа

Подготовленный стенд, реализованный тест, успешный адресный прогон и полная
приёмка — разные статусы. Отметки готовности ОС не заменяют перечень реально
выполненных сценариев и идентификатор бинарника. Текущие результаты и оставшиеся
пробелы описаны в [coverage.md](../scripts/vm/coverage.md); исторические отчёты
в `testing-results/` не переписываются после исправления контроллера или продукта.

Проблемы ОС, desktop, зависимостей и гипервизора, независимо воспроизведённые
без Tyco, не считаются блокерами продукта. Проверить корректную ошибку/деградацию
Tyco, сохранить исходный FAIL и отдельное воспроизведение причины. В частности,
потеря новой записи KWallet 6.31.0 при немедленной перезагрузке и повторный S3
QEMU/Q35 остаются внешними ограничениями; они не требуют обходов в Tyco.
Восстановление ранее сохранённых секретов и проверенный i440fx S3-путь остаются
продуктовыми проверками. Неизвестную причину сбоя нельзя автоматически объявлять
внешней.

Проверки package/upgrade и физического оборудования имеют отдельный статус.
Отсутствие старого опубликованного артефакта блокирует проверку upgrade, но не
разработку Windows/X11-стендов и не закрытие функционального этапа с явно
указанной областью проверки.

Матрица реализованных утверждений и границы GNOME:
