# Быстрый ввод по хоткею: план переноса в приложение

Основан на `dev_docs/quick-input-report.md`. Лаборатория доказала, что ввод
без потерь достижим; здесь — что именно поменять в TyCo, чтобы это получить.

Порядок важен: шаги 1 и 2 независимы и дают основной эффект, шаг 3 добавляет
позиционирование, шаг 4 проверяет, что эффект сохранился на настоящем UI.

## Шаг 1. Прогрев окна при старте

**Проблема.** Первые один-два вызова после старта процесса идут по медленному
пути: без прогрева первый вызов терял весь ввод, фокус не приходил вовсе.

**Что делать.** В `src-tauri/src/services/runtime.rs`, в `setup()`, отложенным
потоком прогнать 3 цикла `show_main_window` / `hide_main_window` с паузой
250 мс, через 400 мс после старта. Образец — `LAB_WARMUP`
в `prototypes/tauri-quick/src/main.rs`.

Прогрев не должен трогать состояние: `show_main_window` сейчас пишет
`params.mode` и `is_window_shown` и шлёт `emit_params`. Нужен отдельный путь,
который делает только `window.show()` / `window.hide()` без изменения
`AppState` и без событий во фронтенд.

**Критерий.** Первый вызов по хоткею после запуска приложения не теряет
символов.

**Риск.** Окно мелькает при запуске три раза. Открытый вопрос: достаточно ли  
для прогрева одного маппинга без реального фокуса. Если да — мигание убирается.  
Проверяется в лаборатории до переноса. 

## Шаг 2. Поле быстрого ввода вне роутера

**Проблема.** Сейчас смена режима идёт через `MODE_ROUTE_MAP` и `RouterView`
(`ui/src/App.vue`), то есть `EditorView` → `EditorInput` монтируются заново
на каждый показ. Фокус в поле встаёт через `onMounted` + `nextTick`
(`ui/src/components/EditorInput.vue:30-36`) и не синхронизирован с фокусом
от ОС. В замерах первый вызов в этом режиме терял 8 символов из 8,
фокус в DOM вставал через 818 мс.

**Что делать.** Вынести вью быстрого ввода из `RouterView` в `App.vue`
и держать его смонтированным всегда, переключая видимость через CSS.
Фокус оставлять в поле постоянно, в том числе пока окно скрыто: при скрытии
возвращать его в поле, а не снимать. Тогда к моменту прихода клавиатуры
сфокусированный элемент в DOM уже существует.

`<KeepAlive>` поверх `RouterView` не подходит: он сохраняет экземпляр
компонента, но убирает его из DOM, и фокус не переживает переключение.

Остальные режимы (история, настройки, чат) остаются на роутере — у них нет
требования мгновенного ввода.

**Критерий.** Между фокусом окна от ОС и наличием сфокусированного поля
в DOM нет зазора: `document.activeElement` — поле ввода ещё до показа окна.

## Шаг 3. layer-shell на главное окно

**Проблема.** На Wayland обычное окно не может себя позиционировать:
`set_position` там не работает, панель выходит по центру.

**Что делать.**

- В `src-tauri/tauri.conf.json` для окна `main`: `transparent: true`,
  `decorations: false`, `skipTaskbar: true`.
- Новый модуль по образцу `prototypes/tauri-quick/src/layer.rs`: шесть функций
  системной `libgtk-layer-shell` через `extern "C"`, без отдельного крейта.
  Линковка — строкой в `build.rs`.
- Вызов из `setup()` **до первого показа окна**: `window.gtk_window()`,
  затем init, overlay, anchor bottom, отступ, exclusive zone 0.
  Клавиатуру переключать между `None` и `Exclusive` в `show_main_window`
  и `hide_main_window`.
- Сборочная зависимость: пакет `gtk-layer-shell`. Добавить в требования
  к сборке в README.

**Откат.** `gtk_layer_is_supported()` возвращает false на GNOME — там остаётся
обычное окно по центру. Молчаливая деградация, не ошибка запуска.

**Критерий.** Панель появляется внизу экрана, полупрозрачная, без рамки
и без кнопки в панели задач; потерь символов по-прежнему нет.

**Дополнительно.** `exclusive` забирает клавиатуру при маппинге, не запрашивая
активацию у композитора. После этого шага activation token становится
не нужен — но только на композиторах с layer-shell.

## Шаг 4. Повторный замер на настоящем UI

Лаборатория гоняла голый HTML. Boot Vue, pinia-сторы и i18n добавят своё время,
и без замера переносить выводы нельзя.

**Что делать.** Прокинуть в приложение те же метки t0-t5 и команды `show`
/ `result`, что в `prototypes/tauri-quick/src/metrics.rs` и `src/ipc.rs`,
под флагом сборки или переменной окружения. Бенч
(`prototypes/tauri-quick/examples/bench.rs`) переиспользуется как есть.

**Критерий.** 20 попыток подряд, задержка первой клавиши 100 мс, пауза между
вызовами 10 с: ноль потерянных символов. То же, что взято в лаборатории.

Замер повторить на release-сборке: все цифры отчёта получены в debug.

## Шаг 5. Вставка обратно в исходное окно

В задачу лаборатории не входило, но без этого главный сценарий не закрывается.

`src-tauri/src/commands/window.rs:39` по умолчанию использует `xdotool`,
а он работает только на X11 — на нативных Wayland-окнах вставка не проходит.
Нужен `ydotool` (с правами на uinput) либо `zwp_virtual_keyboard`.
Там же два `thread::sleep(300)` (строки 52 и 68) — гонка того же класса,
что чинилась в шагах 1-2, только в обратную сторону: правильнее ждать события
фокуса, а не спать.

Приятное следствие шага 3: layer-поверхность не становится «активным окном»
в понимании композитора, поэтому исходный toplevel остаётся активным
и переактивировать его по `window_id` не нужно.

## Вне плана

- Windows и macOS: другой механизм панели (`tauri-nspanel`, стили no-activate).
  Отдельная ветка кода, отдельная проверка.
- Собственный спелчек со своими словарями и контекстным меню — отдельная тема,
  на быстрый ввод не влияет.
