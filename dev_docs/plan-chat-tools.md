Статус: фазы 1 и 2 реализованы, осталась ручная проверка (1.10, 2.4).  
Дата: 2026-10-16  
Стек: Vue 3, Pinia, TypeScript, Rust (Tauri 2), Vercel AI SDK 7 через `@bozonx/ai-kit`.

## 1. Концепция и границы

Профили ИИ — это консультанты по темам и помощники для рутинных действий. Им
можно передать файлы проекта, они ищут в интернете, читают и правят файлы,
вызывают пользовательские команды и MCP-серверы, генерируют изображения и
выполняют код для сложных вычислений.

**Что не делаем:**

- Автономные агенты и фоновые задачи без участия пользователя. Каждый цикл
  инструментов начинается с сообщения пользователя и ограничен числом шагов.
- Запуски по расписанию внутри приложения. Если чат профиля запускается через
  существующий внешний API (D-Bus / external API), планировщик остаётся на
  стороне пользователя.
- Агент для разработки проектов в стиле Claude Code. Произвольного shell нет;
  код выполняется только в песочнице.
- Computer use (управление экраном, мышью и клавиатурой) — отложен.

**Принципы:**

- Всё, что меняет данные или выходит наружу, проходит через политику доступа
  `allow` / `ask` / `deny`. Для проектов она уже есть в `ProjectPermission`;
  её же используем для остальных групп инструментов.
- Инструменты исполняются в Rust. Webview только описывает их для модели и
  показывает вызовы. Исключение — песочница кода (Web Worker с WASM).
- Офлайн-ограничение и CSP соблюдаются. Сеть идёт только через
  `services/net`, ключи хранятся в `services/secrets.rs`, WASM-рантаймы
  упаковываются в приложение.
- Без UI (вызов через внешний API) режим `ask` работает как `deny`.

## Фаза 1: Подготовка существующего кода и доработка ai-kit

Цель: чат умеет вести цикл инструментов, показывать и сохранять шаги,
спрашивать подтверждение. Реальных инструментов пока нет, только тестовые.
Пользовательское поведение чата без инструментов не меняется.

### 1.1. Доработка `@bozonx/ai-kit` ✅

Работа идёт в репозитории `../ai-kit`, затем выпускается новая версия и
обновляется зависимость в `apps/desktop-ui`. Выпущено в `@bozonx/ai-kit` 0.6.3.

1. **Подтверждение вызовов.** Пробросить `toolApproval` из AI SDK 7 в
   `generate`/`stream`. В `StreamPart` добавить часть
   `tool-approval-request` (`approvalId`, `toolCallId`, `toolName`, `args`),
   а в запрос — способ передать ответ (`approved`, `reason`). Проверить, что
   ожидание подтверждения не съедает `totalTimeoutMs`: на время ожидания
   таймер ставится на паузу, либо подтверждение идёт отдельным шагом диалога.
2. **Управление шагами.** Пробросить `activeTools` и `prepareStep` (например,
   отключить инструменты на последнем шаге, чтобы модель ответила текстом).
   Сохранить `maxSteps` как простой вариант.
3. **Итог потока.** В части `finish` (или отдельной `response`) отдавать
   `responseMessages`, чтобы потребитель мог сохранить ход, не собирая
   сообщения из дельт.
4. **Границы шагов.** Добавить часть `step-finish` (номер шага, причина
   завершения, usage шага) — нужна для UI и учёта бюджета.
5. **Файлы в ответе.** Пробросить часть `file` (модели с выводом изображений,
   например Gemini) как `{ type: 'file', mediaType, data }`.
6. **Генерация изображений.** Добавить `kit.generateImage(request)` поверх
   `generateImage` из AI SDK: новый вид модели `image` в каталоге, цены за
   изображение, `UsageSink`, ошибки в общей таксономии `AiError`.
7. **Инструменты на JSON Schema.** Реэкспортировать `jsonSchema` и
   `dynamicTool`, чтобы потребитель описывал инструменты без zod.
8. **Отказ модели от инструментов.** Ошибку провайдера вида «tools not
   supported» классифицировать отдельным видом (например `tools_unsupported`)
   по аналогии с `image_unsupported` в Tyco.
9. Тесты и README на каждое изменение.

### 1.2. Возможности модели ✅

- `LlmModel.canUseTools?: boolean` в `@tyco/shared`. Для встроенных облачных
  провайдеров по умолчанию `true`, для `openai-compatible` — `false`:
  локальные модели часто не умеют вызывать инструменты.
- `llm-catalog.ts` выставляет `capabilities.tools` из этого флага.
- Переключатель в настройках модели рядом с `canUseImages`, i18n во всех
  четырёх локалях.
- Миграция конфига не нужна: поле необязательное.

### 1.3. Модель сообщения из частей ✅

- `ChatMessage` получает `parts?: ChatMessagePart[]`:
  - `text`;
  - `reasoning` — тип зарезервирован, но пока не сохраняется: чат его не
    показывает и модели обратно не отправляет, а невидимый он только раздувает
    историю. Сохранять вместе со сворачиваемым блоком в UI;
  - `tool-call` (`toolCallId`, `toolName`, `input`, `state`: `pending` |
    `awaiting-approval` | `denied` | `done` | `error`; для показа —
    `labelKey` / `label` / `icon` инструмента на момент вызова, чтобы карточка
    читалась и после удаления инструмента);
  - `tool-result` (`toolCallId`, `output` — уже обрезанный, `isError`,
    `truncated`);
  - `file` (ссылка на файл в хранилище, не байты);
  - `sources`.
- `content` остаётся итоговым текстом ответа: на нём работают экспорт,
  поиск по истории, заголовок, копирование. Старые чаты без `parts` читаются
  как раньше.
- Синхронно обновить `src-tauri/src/models/chat.rs` (`#[serde(default)]`),
  `ai_vault` и `chats.rs`; поиск по истории индексирует только текст.
  Бэкенд части не разбирает: хранит их как JSON-объекты с обязательным полем
  `type`, поэтому новый вид части (фазы 4, 6) или чат из более новой версии не
  ломают загрузку.
- `llm-prompt.ts` собирает из частей `ModelMessage` с `tool-call` /
  `tool-result` для следующих ходов. Если текущая модель без инструментов,
  шаги сворачиваются в текст.
- `chat-export.ts`: вызовы инструментов выводятся кратким блоком.

### 1.4. Поток событий в `llm-client` ✅

- Новый метод `stream(task, prompt, options)`: асинхронный итератор
  доменных событий (`text`, `reasoning`, `tool-call`, `tool-result`,
  `approval-request`, `step-finish`, `file`, `sources`, `finish`). `run()`
  остаётся как обёртка для задач без инструментов.
- Логика перебора моделей, таймаута и `ensureCompleteAnswer` переносится без
  изменений. Учесть, что при инструментах `finishReason` последнего шага
  может быть `tool-calls`, если упёрлись в лимит шагов: это отдельная ошибка
  `step_limit` с частичным результатом, а не `invalid_output`.
- `LlmError` получает виды `tools_unsupported` и `step_limit`.

### 1.5. DI-модель цикла инструментов ✅

`apps/desktop-ui/src/lib/chat-tools/` (новый модуль):

- `chat-tool-registry.ts` — набор LLM-инструментов для запроса. Вход:
  профиль, модель, настройки. Выход: `ToolSet` для ai-kit. Источники
  подключаются как провайдеры (`ChatToolProvider`), чтобы фазы 2+ добавляли
  их без правки ядра.
- `chat-tool-policy.ts` — решение `allow` / `ask` / `deny` для вызова
  (инструмент, аргументы, профиль) и состояние «разрешить до конца сессии».
- `chat-tool-output.ts` — нормализация и обрезка результата: лимит символов,
  пометка `truncated`, подсказка модели, как запросить продолжение
  (offset/limit). Обрезка одна — при исполнении, по лимиту инструмента; в
  сообщении хранится ровно то, что видела модель.
- `chat-tool-loop.ts` — ведёт поток: обновляет части сообщения, ждёт
  подтверждения через порт `requestApproval`, применяет лимит шагов. Если в
  одной пачке вызовов пользователь выбрал «разрешить в этой сессии», остальные
  вызовы того же инструмента не переспрашиваются.
  Работает без Vue: тот же код позже обслужит запуск через внешний API, где
  `requestApproval` сразу отвечает отказом.
- Unit-тесты на каждую модель; фейковый `stream` в `lib/llm/testing`.

Интеграция: `chat-generation-model.ts` переходит с `run(..., { onChunk })` на
`stream`. Pinia store `chat.ts` только связывает зависимости.

## Фаза 2: Файловые инструменты для профилей

### 2.1. Rust: `src-tauri/src/services/ai_tools/files.rs` ✅

- Корни доступа для профиля: `workspace/` профиля (всегда `allow`) и проекты
  с их правами `read` / `write`. Модель видит пути вида
  `workspace/...` и `projects/<project-id>/...`, а не абсолютные.
- Разрешение пути: проверка корня, канонизация, запрет выхода за корень (в
  том числе через symlink), запрет скрытых служебных файлов (`project.json`,
  `.git/`).
- Операции:
  - `list_dir` (глубина, фильтр);
  - `read_file` (offset/limit по строкам, лимит размера; PDF/DOCX —
    извлечение текста). Текст PDF/DOCX извлекается в webview теми же
    `chat-pdf.ts` / `chat-docx.ts`, что и у перетащенных файлов: Rust отдаёт
    `readDocument`, затем байты через `read_ai_file_bytes`;
  - `search_files` (по имени и содержимому: `ignore` + `grep-searcher`,
    уважение `.gitignore`);
  - `write_file` (атомарно через `atomic_file.rs`);
  - `edit_file` (замена уникального фрагмента, как `str_replace`);
  - `move_path`, `delete_path` (в корзину ОС: крейт `trash`).
- IPC-команды и unit-тесты на path traversal, symlink, права и лимиты.
- Сделано: `services/ai_tools/files.rs` (корни, разрешение путей, операции),
  `file_search.rs` (обход с `.gitignore`, поиск `grep-searcher`),
  `commands/ai_files.rs`: `list_ai_file_roots`, `run_ai_file_tool`,
  `preview_ai_file_change`, `read_ai_file_bytes`, `save_ai_upload`. Rust
  сам читает профиль на каждый вызов: группа «Файлы» должна быть включена,
  `deny` проекта соблюдается здесь же, `ask` решает webview. Запись — через
  `atomic_file::write_user_file`, сохраняющий права существующего файла.

### 2.3. Позже (не в этой фазе)

Семантический поиск по проекту (`kit.embed` + локальный индекс) — только если

### 2.4. Верификация фазы 2

## Фаза 3: Пользовательские команды и инструменты плагинов

- `ChatToolProvider` «commands»: команды пользователя (скрипты, вебхуки) и
  инструменты плагинов через адаптер из 1.9.
- Явный выбор в профиле, какие команды доступны модели. По умолчанию ничего;
  политика по умолчанию `ask`.
- Для команды без `description` для LLM — поле описания в редакторе команды
  (что делает, когда использовать). Без описания команду нельзя отдать модели.
- Для `plugin-sdk`: документировать, что `description` и `inputSchema`
  используются моделью; добавить необязательный флаг
  `canRunFromChat` (по умолчанию `true` для чистых преобразований текста).
- Вывод скриптов обрезается через `chat-tool-output.ts`, таймаут и отмена —
  через существующий `cancelScriptRun`.

## Фаза 4: Поиск в интернете и загрузка страниц

### 4.1. Инструменты

- `web_search(query, count)` — список `{ title, url, snippet }`.
- `web_fetch(url, offset?)` — основной текст страницы в Markdown с
  постраничной выдачей длинных документов.
- Результаты превращаются в части `sources` и показываются под ответом.

### 4.2. Rust: `src-tauri/src/services/ai_tools/web.rs`

- Поисковые бэкенды за общим трейтом: Brave Search API, Tavily, SearXNG
  (свой адрес, без ключа). Ключи — в `secrets.rs`, запросы — через
  `services/net`.
- `web_fetch`: загрузка через `net`, извлечение основного содержимого
  (`dom_smoothie`), конвертация в Markdown (`htmd`). Ограничения: размер
  ответа, только `http(s)`, запрет локальных адресов (loopback, частные
  сети) по умолчанию.
- Тесты на извлечение текста на сохранённых HTML-фикстурах.

### 4.3. Настройки

- Глобальные настройки: поисковый бэкенд, ключ, адрес SearXNG.
- В профиле — группа «Интернет» с политикой (по умолчанию `allow` для
  поиска, `allow` для загрузки страниц).
- Встроенный поиск провайдера (Google grounding и т. п.) не используем по
  умолчанию: он привязывает к одному провайдеру и ломает цепочку запасных
  моделей. Можно добавить позже как опцию модели.

## Фаза 5: MCP

### 5.1. Rust: `src-tauri/src/services/mcp/`

- Клиент на крейте `rmcp` (официальный Rust SDK MCP).
- Транспорты: stdio (запуск процесса, переменные окружения, рабочая папка) и
  Streamable HTTP (через `services/net`).
- OAuth для удалённых серверов: токены в `secrets.rs`, браузерный вход через
  системный браузер с обратным вызовом на localhost или deep link.
- Менеджер жизненного цикла: ленивый запуск при первом использовании,
  остановка при простое и при выходе, перезапуск после падения, лог stderr в
  диагностику.
- Кэш списка инструментов, событие `tools/list_changed`.
- IPC: `mcp_list_servers`, `mcp_list_tools`, `mcp_call_tool` (с
  `AbortSignal` → `notifications/cancelled`), статус сервера.
- Кросс-платформенный запуск процессов — через `services/platform/`
  (PATH, `npx`/`uvx` на Windows и macOS).

### 5.2. Конфигурация

- Список серверов в конфиге: `id`, название, транспорт, команда/URL,
  переменные окружения (секреты — ссылками `tyco-secret:<id>`).
- Импорт из JSON в формате `mcpServers` (как у Claude Desktop / Cursor).
- В профиле — выбор серверов и, при необходимости, отдельных инструментов;
  политика на сервер с переопределением на инструмент. Подсказки MCP
  (`readOnlyHint`, `destructiveHint`) задают политику по умолчанию.

### 5.3. Frontend

- `ChatToolProvider` «mcp»: инструменты как `dynamicTool` с именами
  `<server>__<tool>` (без коллизий, в пределах ограничений провайдеров на
  имена).
- Результаты: текст и изображения (изображения — частью `file`, если модель
  их принимает).
- Ресурсы и промпты MCP — позже; на первом шаге только инструменты.

## Фаза 6: Генерация изображений

- Используется `kit.generateImage` из 1.1. Модели изображений появляются в
  настройках LLM как отдельный вид (OpenAI gpt-image, Google Imagen и т. п.;

- Инструмент `generate_image(prompt, size?, count?)` для модели чата;
  результат сохраняется в `workspace/generated/` профиля или в хранилище
  изображений чата (`chat_images`) для «Спросить у ИИ».
- Части `file` из ответов моделей с выводом изображений (Gemini)
  сохраняются так же.
- Предпросмотр в сообщении, «Открыть», «Сохранить как», вставка в следующий
  запрос как изображение.
- Стоимость генерации показывается в учёте использования.

## Фаза 7: Выполнение кода в песочнице

Назначение — вычисления и обработка файлов (таблицы, преобразования данных,
графики), а не разработка проектов.

- Pyodide в Web Worker, упакованный в приложение (без CDN). Пакеты по
  умолчанию: стандартная библиотека, `numpy`, `pandas`, `matplotlib`;
  остальное — только из локального набора.
- Опционально JS через `quickjs-emscripten`.
- Инструмент `run_code(language, code)`: stdout/stderr, результат,
  созданные файлы. Лимиты: время, память (перезапуск воркера), размер
  вывода.
- Файловая система: в виртуальную ФС монтируется копия нужных файлов

  через файловые инструменты фазы 2 с теми же правами на запись.

- Проверить, не подходит ли интерфейс `experimental_sandbox` из AI SDK 7,
  чтобы подложить под него свою реализацию; если он нестабилен — свой
  инструмент.
- Влияние на размер сборки — замерить; при необходимости рантайм
  скачивается отдельно по запросу пользователя и хранится локально.
