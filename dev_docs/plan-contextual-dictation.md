# План контекстного голосового ввода с Gemini Live

Статус: проект решения. Механизм пересмотра ранее распознанного текста ещё не
реализован. Приоритет — точность и сохранение смысла; экономия токенов достигается
прежде всего устранением повторной обработки.

## Цель

Во время диктовки показывать текст с небольшой задержкой и позволять исправлять
ранние ошибки по мере появления контекста. Сохранять корректно распознанные слова,
имена, числа, команды и код. На длинных записях не отправлять весь накопленный текст
на коррекцию после каждого обновления.

Визуальный ориентир — поведение голосового ввода в Google Antigravity. Его
внутренняя реализация нам неизвестна; план не предполагает её воспроизведения.

## Текущее поведение

- Выбор `geminiLive` направляет аудио через Rust WebSocket-транспорт в Gemini Live
  API. Модель по умолчанию — `gemini-3.5-transcribe-live`, режим — `smart`.
- Промежуточная гипотеза заменяет текущий черновик. Окончательный фрагмент
  дописывается к зафиксированному тексту. Пересмотра старых фрагментов нет.
- Завершение записи сначала ожидает финальный ответ того же Live-сеанса.
- Включённая LLM-коррекция для вставки во внешнее приложение запускает отдельную
  текстовую задачу `voiceCorrection`. Она использует свою настроенную модель и не
  получает исходное аудио. Стилизация также является отдельной операцией.
- Исправлены лишнее ожидание закрытия WebSocket после финального `turnComplete`
  и потеря ошибок подготовки и отправки аудио. Добавлены проверки соединения,
  которое остаётся открытым после завершения высказывания, и обработки ошибок.

Основные точки реализации:

- `apps/desktop-ui/src/lib/stt/gemini-live-provider.ts` — протокол Gemini Live.
- `apps/desktop-ui/src/lib/stt/live-dictation.ts` — захват и завершение диктовки.
- `apps/desktop-ui/src/lib/stt/live-transcript.ts` — сборка текста.
- `apps/desktop-ui/src/lib/stt/voice-recognition.ts` — завершение и постобработка.
- `apps/desktop-ui/src/lib/stt/dictation-controller.ts` — выбор настроек и политики.

## Решение

### 1. Сначала использовать возможности самого Gemini SMART

Сохранять один Live-сеанс и управлять границами высказываний. Короткую диктовку
обрабатывать одним высказыванием, длинную — смысловыми блоками. Естественная пауза
не должна автоматически отрезать контекст, необходимый для понимания мысли.

Google рекомендует для SMART ручное управление границами: отключение
`automaticActivityDetection` и отправку `activityStart` / `activityEnd`.
Необходимо проверить поведение именно используемого Gemini API и модели на
реальном соединении перед включением этого режима по умолчанию.

Размер блока, длительность паузы и предельную длительность высказывания подобрать
по записям. Не считать фиксированное число символов заменой определения границ
мысли. Промежуточный текст должен продолжать появляться во время записи.

### 2. Разделить область исправлений и контекст для чтения

| Область             | Начальная настройка для эксперимента         | Политика                                                        |
| ------------------- | -------------------------------------------- | --------------------------------------------------------------- |
| Изменяемый хвост    | Около 1000–1500 символов                     | Можно исправлять; границы проходят по целым предложениям        |
| Предыдущий контекст | Ещё 2000–4000 символов                       | Только для понимания; свободное переписывание запрещено         |
| Словарь сессии      | Компактный набор имён и технических терминов | Использовать для единообразного распознавания                   |
| Старые блоки        | Остальной документ                           | Повторно открывать для проверки только при конкретном основании |

Это исходные гипотезы, а не доказанные оптимальные значения. Для сравнения
проверить окна 500, 1000 и 2000 символов. Ограничение запросов контролировать также
по токенам: соотношение символов и токенов зависит от языка и содержимого.

Окно относится к дополнительной коррекции. Оно не требует пересоздания Live-сеанса
и повторной отправки всего аудиопотока.

### 3. Дополнительную коррекцию запускать по новому контексту

Сначала измерить качество SMART с управляемыми границами. Регулярный второй проход
добавлять только при подтверждённом улучшении точности.

Если он необходим:

- Запускать его после содержательного нового контекста, например одного-двух
  завершённых предложений, а не после каждого слова или промежуточного события.
- Не отправлять неизменившийся снимок текста повторно.
- Объединять накопившиеся изменения; не создавать очередь устаревших запросов.
- Учитывать, какие блоки уже проверены и какой новый контекст появился после этого.
- После «Закончить» дождаться финального распознавания и проверить оставшийся хвост.
  Не запускать автоматически второй полный проход по всем проверенным блокам.

Периодичность, параллелизм и лимиты запросов определить по измерениям задержки,
точности и стоимости. Существующая финальная `voiceCorrection` должна быть
согласована с новой схемой, чтобы не дублировать выполненную работу. Стилизация
всего документа остаётся отдельной пользовательской операцией.

### 4. Использовать аудио для проверки ошибок распознавания

Текстовая модель может сделать фразу правдоподобнее, но не может достоверно
восстановить произнесённое слово без аудио. Особенно это важно для имён, чисел,
аббревиатур, команд и кода.

Сохранять аудио локально до завершения обработки сессии, привязав его к блокам и
реальному времени захвата. Для повторной проверки передавать только нужный
аудиофрагмент с небольшим перекрытием и текстовым контекстом. Не использовать
условные временные метки сегментов текущего адаптера для нарезки аудио.

Локальное хранение не расходует API-токены. Повторная отправка аудио расходует их,
поэтому её необходимость и допустимую частоту нужно измерить. После окончания
обработки или отмены освобождать временное аудио; длительное хранение не включать
в этот план.

### 5. Поддержать точечные дальние исправления

Длина диктовки не исключает позднего уточнения: пользователь может назвать точное
имя или термин через несколько минут после первого упоминания.

При явном уточнении или выявленной терминологической несогласованности находить
соответствующие старые блоки и проверять только их, при необходимости с аудио.
Не выполнять глобальную замену похожих слов без проверки контекста. Не считать
самооценку уверенности LLM доказательством правильности исправления.

### 6. Применять изменения безопасно

- Сохранять исходный транскрипт отдельно от исправленного результата.
- Получать конкретные замены по идентификаторам блоков, а не новый документ целиком.
- Проверять исходный текст и версию блока перед применением ответа.
- Отбрасывать ответы отменённой, устаревшей или другой сессии.
- Защищать ручные правки пользователя от автоматического перезаписывания.
- Сохранять смысл и исходный язык; не добавлять факты, не переводить и не
  перефразировать текст ради стиля в рамках коррекции распознавания.
- При ошибке или таймауте сохранять доступный транскрипт и сообщать о проблеме.

## Поэтапный план реализации

### Этап 1. Набор записей и исходные измерения

- [ ] Подготовить записи с проверенными человеком эталонными транскриптами.
- [ ] Включить русский с английскими терминами, имена, числа, команды, код,
      оговорки, паузы и поздние уточнения в длинной диктовке.
- [ ] Измерить текущий Live SMART без дополнительной коррекции и с существующей
      финальной `voiceCorrection`.
- [ ] Записывать ошибки распознавания, ошибки корректора, задержку появления текста,
      время завершения и расход входных, выходных и аудиотокенов, где они доступны.

### Этап 2. Управляемые границы SMART

- [ ] Проверить контракт ручного управления высказываниями на реальном Gemini API.
- [ ] Реализовать управление границами с injected-зависимостями и ограничением
      длительности блока; Pinia оставить слоем подключения.
- [ ] Проверить непрерывность текста и сохранение последних слов на границах блоков.
- [ ] Проверить завершение, отмену, тишину, сетевые ошибки и длительную запись.
- [ ] Сравнить качество с исходным вариантом и определить необходимость второго
      прохода. Зафиксировать результаты перед следующим этапом.

### Этап 3. Модель пересматриваемых блоков

- [ ] Добавить идентификаторы и версии блоков, исходный текст, исправленный текст,
      область доступных правок и отметку ручного редактирования.
- [ ] Разделить черновик провайдера, изменяемый хвост и ранее проверенный текст.
- [ ] Реализовать выбор хвоста по границам предложений и бюджету токенов.
- [ ] Проверить сборку текста без пропусков и повторов, применение замен и
      отбрасывание устаревших ответов.

### Этап 4. Локальное аудио и выборочная перепроверка

- [ ] Привязать аудиоблоки к реальным временным меткам и ограничить использование
      памяти или временного диска.
- [ ] Реализовать получение нужного аудиофрагмента с перекрытием и очистку ресурсов.
- [ ] Сравнить текстовую и аудиокоррекцию на одинаковых примерах.
- [ ] Определить условия повторной отправки аудио и защиту от повторной проверки
      неизменившихся данных.

### Этап 5. Планировщик коррекции и завершение

- [ ] Если необходимость второго прохода подтверждена, добавить объединение новых
      данных, отмену устаревших запросов и ограничение параллелизма.
- [ ] Передавать изменяемый хвост, контекст только для чтения и словарь сессии.
- [ ] Проверять и применять адресные замены только к актуальным версиям блоков.
- [ ] Согласовать финальную обработку с `voiceCorrection`, стилизацией и назначением
      диктовки: чат, редактор или внешнее приложение.
- [ ] Исключить повторный полный проход по уже проверенному длинному документу.

### Этап 6. Дальние уточнения и выбор параметров

- [ ] Реализовать поиск конкретных старых блоков по позднему уточнению.
- [ ] Сравнить окна 500, 1000 и 2000 символов и полный проход как контрольную
      конфигурацию. Эталоном правильности остаётся человеческий транскрипт.
- [ ] Выбрать параметры сначала по точности, затем по задержке и стоимости.
- [ ] Зафиксировать измеренные значения и ограничения; до этого не считать
      предложенные размеры окна окончательными.

## Критерии готовности

- Качество улучшилось на согласованном наборе записей; отдельно учтены случаи,
  когда корректор испортил правильный текст.
- Имена, числа, команды и код проверены отдельно от общей ошибки распознавания.
- На границах блоков нет потери или дублирования слов.
- Позднее уточнение может исправить конкретный старый блок без переписывания
  остального документа.
- Ручные правки защищены, устаревшие ответы не применяются.
- Стоимость длинной диктовки не растёт из-за постоянной повторной отправки всего
  накопленного текста; неизменившиеся окна не отправляются повторно.
- Завершение ограничено по времени; ошибки сохраняют доступный результат.
- Выполнены модельные и интеграционные тесты и реальная проверка с Google и
  микрофоном. Численные пороги качества, задержки и стоимости определены после
  исходных измерений и до включения новой схемы по умолчанию.

Проверки по области изменений: `pnpm check`, `pnpm test`; при изменениях Rust —
`pnpm check:rust` и соответствующие Rust-тесты; при изменении IPC-контрактов —
`pnpm generate:desktop`. Подробности — в [testing.md](testing.md).

## Источники

- [Gemini Live Transcription](https://ai.google.dev/gemini-api/docs/live-api/live-transcribe):
  промежуточные и окончательные результаты, SMART и стратегии определения границ.
- [Gemini 3.5 Transcribe](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-transcribe):
  рекомендация ручного управления границами для SMART.
- [Google StreamingRecognitionResult](https://docs.cloud.google.com/speech-to-text/docs/reference/rest/v2/StreamingRecognitionResult):
  окончательные результаты и стабильность промежуточных гипотез.
- [Amazon Transcribe: streaming partial results](https://docs.aws.amazon.com/transcribe/latest/dg/streaming-partial-results.html):
  стабилизация частей потокового транскрипта.

Это источники принципов и контрактов. Параметры окон и план TyCo являются нашим
проектным предложением, а не требованиями этих сервисов.
