# Голосовые команды — актуальный дизайн

Статус: первая версия реализована; проверка на реальных записях ещё не проведена.
Обновлено: 2026-10-14.

Этот документ заменяет прежний план команд и голосового оверлея. Он описывает
голосовую часть поверх существующих инструментов, библиотеки команд и
исполнителя. Распознаватели плагинов и LLM-разбор остаются проектом. Текущий контракт хранения: [config-storage.md](config-storage.md).
Внешний вызов: [External control API](../docs/external-control.md).

## 1. Цель и границы

Отдельный хоткей открывает отдельный оверлей голосовых команд
и сразу начинает запись. Пользователь произносит фразу вызова, затем параметры
и текст. Ядро определяет команду и передаёт вход существующему исполнителю.

Обычная диктовка остаётся самостоятельным режимом: произнесённый в ней текст
не запускает команды. Ключевое слово внутри диктовки и постоянно слушающий
wake word в этот проект не входят.

Первая версия работает без LLM для выбора команды. Это не означает, что сами
перевод, коррекция или другие инструменты не могут использовать LLM. При локальном
STT и локальном инструменте весь вызов работает без сети. Сетевые возможности
не являются обязательной зависимостью голосового режима.

Три уровня развития:

1. Строгие фразы вызова и декларативные параметры — первая версия, включая core.
2. Необязательные пользовательские распознаватели сторонних плагинов — позже.
3. Общий LLM-разбор свободной формулировки после завершения записи — позже.

## 2. Что уже реализовано

- Библиотека `CommandConfig`: стабильный id, имя, инструмент, настройки,
  `phrases`, `enabled`, настройки вывода и внешней доступности.
- Реестр инструментов core и плагинов; общий путь выполнения команд.
- Клавиатурный оверлей с поиском, страницами и слотами `launcherPages`.
- Скрипты и вебхуки с явной подстановкой `{{TEXT}}`.
- Внешний вызов и журналирование команд.
- Захват голоса, STT и управление жизненным циклом голосовой сессии.

`phrases` участвуют в текстовом поиске клавиатурного оверлея и в строгом
голосовом resolver. Голосовой вызов включается отдельно для каждой пользовательской
команды. Встроенные перевод и вопрос в чате включены постоянно.
Размещение в оверлее задаётся ссылками в страницах, а не полем команды.
`outputAction` задаёт обработку результата команд, запущенных из оверлея.
Команды создаёт только пользователь: инструменты ядра и плагинов не добавляют
команды сами, ни при первом запуске, ни при установке плагина.

Не переносить из прежнего документа старые структуры конфига, транспортные
контракты и утверждения о реализованных этапах без проверки по коду.

## 3. Какие команды доступны голосом

Встроенные функции «переведи на…» и «спроси в чате…» всегда включены и не имеют
переключателя. Они отображаются отдельной группой в голосовом оверлее даже при
пустой пользовательской библиотеке. Если инструмент недоступен, рядом показана
причина. Автоматический запуск после завершения диктовки управляется общей
галочкой в оверлее, включённой по умолчанию.

В редактор пользовательской команды добавляется отдельный переключатель голосового вызова.
Предлагаемое поле — `isVoiceEnabled`, по умолчанию `false`.
Существующее поле `phrases` хранит явные фразы вызова.

Пользовательская команда участвует, только если:

- пользователь включил голосовой вызов;
- включена сама команда;
- инструмент доступен и допускает такой способ ввода;
- настроен хотя бы один корректный маршрут распознавания.

Для первой версии маршрут — непустые фразы и, если нужны, декларативные параметры.
В будущем им также может быть разрешённый пользователем распознаватель плагина.
Наличие инструмента в реестре само по себе не разрешает голосовой вызов.
Новые команды по умолчанию могут предлагать фразы, но не включают голос молча.

Голосовая доступность независима от страниц клавиатурного оверлея, меню действий,
`isAvailableExternally`. Распознавание проходит по
всему разрешённому голосовому каталогу, а не только текущей странице.

Имя команды предназначено для отображения. При включении голоса редактор может
предложить его как фразу; автоматического скрытого совпадения по имени нет.
Переименование не меняет фразы вызова.

## 4. Скрипты и вебхуки

Пользователь задаёт точные фразы, например «рабочая заметка», «запусти бэкап»
или «отправь в телеграм». После совпавшей фразы весь остаток становится текстовым
входом команды. Для скрипта и вебхука сохраняется существующий контракт
`{{TEXT}}`: нового неявного stdin, аргумента процесса или поля HTTP не появляется.
Если настройки не содержат `{{TEXT}}`, команда не принимает текст.

Префиксы «скрипт» и «вебхук» необязательны. Пользователь может явно сохранить
фразы «скрипт бэкап» или «вебхук уведомление», если ему так удобнее отличать
команды. Ядро не добавляет и не удаляет эти слова автоматически. Одного слова
«скрипт» недостаточно для выбора между несколькими скриптами.

Обязательный технический префикс не нужен: способ реализации действия не должен
определять, как пользователь обязан его называть. При необходимости различать
одноимённые действия редактор предлагает изменить фразу.

В первой версии фразы — обычные строки с точным порядком слов. Нет мини-языка
с альтернативами в скобках, необязательными словами или регулярными выражениями.
Каждый синоним задаётся отдельной строкой.

## 5. Core: строгая грамматика и параметры

Встроенные фразы предоставляются только для перевода и вопроса в чате.
Копирование, вставка, коррекция и другие действия доступны голосом только через
явно заданные пользователем фразы.

Core использует общий декларативный механизм, а не произвольные функции
распознавания. Порядок фиксирован:

**фраза вызова → параметры из ограниченного словаря → свободный текст**.

Примеры пользовательских высказываний:

| Высказывание                        | Фраза вызова                         | Параметры                | Текст               |
| ----------------------------------- | ------------------------------------ | ------------------------ | ------------------- |
| «Переведи на английский я опоздаю»  | «переведи на»                        | целевой язык: английский | «я опоздаю»         |
| «Переведи на испанский буду завтра» | «переведи на»                        | целевой язык: испанский  | «буду завтра»       |
| «Спроси в чате как устроен D-Bus»   | «спроси в чате»                      | нет                      | «как устроен D-Bus» |
| «Рабочая заметка купить молоко»     | «рабочая заметка» (пользовательская) | нет                      | «купить молоко»     |

Вертикальные разделители в объяснении «переведи на | английский | текст»
обозначают границы частей. Произносить их, слово «двоеточие» или делать
специальную паузу не нужно.

Параметр языка распознаётся по конечному словарю произносимых вариантов,
сопоставленных стабильным кодам языков. Варианты могут состоять из нескольких
слов. Неизвестный или отсутствующий язык не выбирается по догадке: оверлей
предлагает исправить ввод или явно выбрать доступную команду языка. При таком
выборе весь неразобранный остаток сохраняется в редактируемом входе; пользователь
проверяет его перед отдельным подтверждением запуска. Это не совпадение с готовым текстовым
аргументом, и остаток нельзя молча отправлять в произвольный перевод.

### 5.1. Совместимость с нынешними командами перевода

`core.translate` по-прежнему получает язык из `toolConfig.language`.
Общий маршрут «переведи на» компилируется из встроенных вызовов для языков
конечного словаря. Каждый вызов содержит свой язык и проходит через общий runner,
используя текущий настроенный переводчик. Эти вызовы существуют только во время
работы приложения: они не добавляются в пользовательскую библиотеку и не меняют
сохранённые команды.

Пользовательские команды перевода сохраняют собственные настройки и вызываются
по своим явным фразам. Встроенный общий маршрут к ним автоматически не добавляется,
поэтому несколько сохранённых переводов одного языка не делают стандартный вызов
неоднозначным. Если пользовательская фраза совпадает со встроенной, действуют
общие правила конфликтов и выбора кандидатов.

Контракт инструмента и структурированного входа не меняется: исполнитель
получает обычный вызов `core.translate` с фиксированным языком в конфиге.

### 5.2. Объявление грамматики

Декларативный маршрут содержит фразы по языкам, последовательность параметров,
их допустимые значения и произносимые варианты, а также правило передачи
оставшегося текста. Результат ссылается на конкретную разрешённую команду.
Ядро проверяет объявления и компилирует их в общий каталог.

Точные TypeScript-типы определяются при реализации. Не добавлять в SDK
универсальный язык грамматик заранее: первой версии достаточно фраз,
параметров с конечным словарём и конечного текстового остатка.

## 6. Общий resolver

Путь ввода:

**микрофон → STT → каталог фраз и грамматик → resolver → проверка входа → runner**.

### 6.1. Нормализация и граница аргумента

Для сравнения нормализуются регистр, пробелы, `ё/е` и пунктуация между словами.
Токены сохраняют позиции в исходной строке. Текстовый остаток извлекается из
исходного транскрипта, сохраняя регистр и внутреннюю пунктуацию; разделительная пунктуация удаляется только непосредственно после фразы
перед пробелом или концом строки. После пробела начинается исходный аргумент:
его начальные знаки (`-42`, `.env`, `--help`, Markdown) сохраняются.
Правило проверяется тестами.

Нормализация сравнения не переписывает вход инструмента. Числа словами в тексте
не преобразуются автоматически. Нет глобального удаления слов «запусти»,
«сделай», «выполни», стемминга или автоматической подстановки синонимов.
Нужные варианты задаются фразами или словарём конкретного параметра.
LLM-коррекция обычной диктовки перед распознаванием команды не выполняется.

### 6.2. Кандидаты

Для каждого маршрута возможны состояния:

- не подходит текущему транскрипту;
- подходит начало, требуется продолжение;
- найден кандидат с командой, параметрами и границей текстового остатка;
- обнаружена ошибка параметра, которую нужно показать пользователю.

Проверяются все разрешённые маршруты. Первый зарегистрированный обработчик
не получает приоритет и не захватывает ввод. Варианты одной команды объединяются.

Для финального текста предпочтение получает точный маршрут, поглотивший больше
слов фразы и обязательных параметров. Равнозначные кандидаты разных команд
означают неоднозначность, а не выбор по порядку регистрации. При конфликте
границ аргумента также требуется выбор. Нечёткий поиск может предлагать варианты,
но не разрешает автоматическое выполнение.

Самое длинное совпадение не устраняет смысловую неоднозначность общих фраз.
Например, «запиши» и «запиши идею» могут по-разному делить один и тот же текст.
Редактор предупреждает о таких вложенных маршрутах до сохранения.

### 6.3. Потоковый текст

Каждое обновление STT пересматривается целиком: это не поток окончательных слов,
ранее распознанное начало тоже может измениться. Во время записи resolver
показывает предварительную команду и вход, но ничего не выполняет и не фиксирует
выбор необратимо.

Нет правила «три слова без совпадения — отмена». Фразы и параметры бывают длиннее.
Внутренние ограничения размера каталога, вариантов и вычислений допустимы,
но достижение лимита не удаляет надиктованный текст и не запускает действие.

Выполнение разрешено только после завершения записи и получения финального
результата STT. Перед запуском повторно проверяется актуальная доступность
команды и корректность входа.

## 7. Оверлей и восстановление после ошибки

Голосовой и клавиатурный режимы используют отдельные оверлеи и общий executor. Голосовой хоткей начинает запись; клавиатурный
открывает существующий выбор команд. Во время записи видны доступные фразы,
транскрипт, предварительная команда, параметры и текст. Справа расположен
прокручиваемый список зарегистрированных голосовых команд с фразами вызова
и описаниями, отдельно от постоянной группы стандартных функций. В DEV Quick предусмотрена кнопка Voice Commands.

Первый способ завершения записи — явный: повторный хоткей или отпускание клавиши
для режима удержания. Остановка по паузе — отдельное последующее улучшение:
пауза между командой и аргументом не должна преждевременно запускать действие.

После получения финального текста:

| Результат                                             | Поведение                                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------- |
| Точное однозначное совпадение и валидный вход         | Выполнение, если включена галочка автоматического запуска; иначе ручной запуск  |
| Неоднозначность                                       | Выбор кандидата с показом его параметров и текстового входа                     |
| Только приблизительные совпадения                     | Предложения с обязательным подтверждением                                       |
| Неизвестный параметр                                  | Исправление или выбор допустимого значения                                      |
| Нет совпадения                                        | Сохранить транскрипт, предложить ручной выбор, редактирование или повтор записи |
| Команда недоступна или выполнение завершилось ошибкой | Сохранить ввод и показать причину; повторный запуск только явно                 |

Если команда выбрана вручную после неудачного распознавания, нельзя угадывать,
какую часть текста удалить. Оверлей показывает редактируемый вход до выполнения.
Повторная запись не запускается автоматически; до явной замены текущий текст
остаётся доступным. Отмена закрывает сессию без выполнения.

Для команды с обязательным текстом пустой остаток открывает подготовку ввода.
Выделение активного окна не подставляется молча вместо голосового аргумента.
Для работы с выделением нужен явный маршрут или действие пользователя.

Для команды без текстового входа непустой остаток — повод для исправления или
подтверждения, а не текст, который можно игнорировать. Фраза вроде
«запусти бэкап хотя нет не надо» не считается разрешением на автоматический запуск.
Первая версия не обещает универсального распознавания самоисправлений речи.

## 8. Подтверждения и последствия

В голосовом оверлее есть галочка «Выполнять команду после диктовки», включённая
по умолчанию. Она управляет встроенными и пользовательскими командами: после
явной остановки записи и получения финального STT точный однозначный вызов с
корректным входом выполняется сразу. Промежуточный текст ничего не запускает.
Если галочка отключена, оверлей показывает выбранную команду и редактируемый
текст, а пользователь запускает её отдельной кнопкой. Выбор галочки сохраняется
при повторных открытиях оверлея в текущем процессе приложения.

Неоднозначность, ручной выбор, исправление параметров, пустой или лишний аргумент
не приводят к автоматическому запуску. Ошибка выполнения также не запускает
автоматический повтор. Автозапуск решает настройка в оверлее, в команде
его нет.

Результат перевода из голосового режима всегда показывается в окне результата
с выбором дальнейшего действия. Настройка вывода команды не вызывает вставку или
копирование перевода автоматически. Клавиатурный запуск и остальные способы
вызова сохраняют прежние настройки вывода.

На подтверждении видны действие, параметры и отправляемый текст. Для скриптов
и вебхуков нельзя надёжно вывести последствия из их названия или инструмента.
Отправку сообщений, удаление и внешние побочные эффекты нельзя считать обратимыми
из-за наличия кнопки отмены. Задержка перед запуском может быть удобством,
но не заменяет необходимое подтверждение и не обещает отменить уже выполненное.

Любой будущий LLM-выбор требует подтверждения независимо от настройки точного
вызова. Распознаватели и модель не могут обойти разрешения и общий executor.
Отмена, повторная активация и поздние ответы STT не должны запускать старую сессию.

## 9. Распознаватели сторонних плагинов — будущее

Сторонний плагин сможет дополнительно объявить собственную функцию распознавания,
если декларативных фраз и параметров недостаточно. Это расширение SDK,
а не обязательная часть первой версии.

Функция получает транскрипт, признак финальности, язык и ограниченный контекст
разрешённых команд своего инструмента. Возвращает состояния и кандидатов
из общего контракта, включая исходные границы текста и разобранные параметры.
Ядро валидирует результат и разрешает конфликты со всеми другими кандидатами.

Функция быстрая, синхронная и без побочных действий: не выполняет команды,
не меняет конфиг и не делает сетевые или LLM-запросы. Доступ к сети и асинхронный
семантический разбор относятся к отдельной финальной стадии. Лимиты работы,
ошибки и отключение неисправного распознавателя обрабатываются ядром;
синхронный callback сам по себе не обеспечивает изоляцию или прерывание зависания.
Способ изоляции определяется до выпуска публичного SDK-контракта.

Плагин не может выбрать чужую или не разрешённую для голоса команду.
Несколько настроенных экземпляров одного инструмента сохраняют собственные
id, настройки и разрешения; распознаватель не подменяет их вызовом инструмента
напрямую. Невалидный результат не становится разрешением на запуск.

## 10. Общий LLM-разбор — будущее

Плагины смогут объявлять семантические описания, схемы входа и примеры,
а ядро собирать единый запрос по всем разрешённым вариантам. Произвольные строки
плагина не становятся системными инструкциями. Выход модели — кандидат,
не вызов функции с побочным эффектом.

LLM вызывается один раз по финальному транскрипту: по явной кнопке после
неудачного строгого разбора либо в отдельно включённом свободном режиме.
Нет запроса на каждое слово, обновление STT или каждый плагин. Автоматическое
исправление неудачного LLM-ответа циклом запросов в первую реализацию не входит.

Модель возвращает конкретный разрешённый `commandId`, структурированный вход
по допустимой схеме либо отсутствие подходящей команды. Где нужен исходный текст,
он передаётся без перефразирования и проверяется ядром. Модель не обязана выбирать
ближайшее действие. Схема, ссылки, доступность и права валидируются до подтверждения.
Ошибки, отмена и отсутствие LLM оставляют пользователя в оверлее с сохранённым вводом.

Разбор намерения и разбор аргумента — разные стадии. Существующий
`isLlmArgumentParsingEnabled` не разрешает выбирать команду через LLM и не включает
этот режим. Инструмент может отдельно разбирать вход уже выбранной команды;
порядок стадий должен исключать повторный разбор одного и того же входа.

## 11. Языки и STT

Фразы вызова и варианты параметров принадлежат языку произнесения, который может
отличаться от языка интерфейса. Пользователь может добавить несколько вариантов.
Core-подсказки и UI полностью покрывают `ru-RU`, `en-US`, `es-AR`, `tr-TR`, без
fallback. Названия языков сопоставляются кодам явно, а не через язык интерфейса.

Список разрешённых характерных фраз и имён можно передавать как подсказки STT,
если используемый провайдер это поддерживает. Это улучшение, а не обязательный
контракт: локальные и другие STT должны работать без него. Подсказки не заменяют
проверку финального текста. Не обещаем, что префикс «выполни команду» повышает
точность: такие решения проверяются на используемых моделях и записях.

## 12. План реализации и проверка

1. Добавить настройки включения голоса и подтверждения, сохранив `phrases`.
   Синхронно обновить shared-типы, схему, defaults и нормализацию Rust/TypeScript.
   Существующие команды не становятся доступными голосом автоматически.
2. Реализовать DI-модель компиляции фраз, параметров, конфликтов и resolver
   в `apps/desktop-ui/src/lib/`; Pinia оставить для реактивности и wiring.
3. Добавить строгие core-маршруты, включая постоянные встроенные вызовы перевода
   и вопроса в чате; редактор фраз и проверку пробного высказывания.
4. Подключить отдельный голосовой оверлей к существующей записи
   и runner, с предварительными кандидатами и финальным решением.
5. Реализовать подтверждение, сохранение ввода при ошибке и защиту от старых сессий.
6. Проверить на реальных записях; лишь затем проектировать SDK распознавателей
   и общий LLM-разбор по выявленным ограничениям.

Фокус unit-тестов: границы исходного текста, несколько слов в параметре,
конфликты и вложенные фразы, одинаковый язык у нескольких команд перевода,
пустой/лишний аргумент, неизвестный язык, пересмотр начала STT, недоступность
инструмента, отсутствие запуска по промежуточному тексту, отмена и поздние ответы.

Реальные записи должны включать разные поддерживаемые языки, паузы,
самоисправления, шум, сходные и неизвестные фразы. Отдельно оценивать выбор команды,
разбор параметров, границу текста и ложные автоматические запуски. Качество
транскрипции и качество resolver — разные показатели.

При реализации выполнить `pnpm check`, `pnpm test` и затронутые Rust-проверки.
Для изменения только этого дизайн-документа достаточно проверки Markdown
и diff; поведение приложения этим изменением не меняется.
