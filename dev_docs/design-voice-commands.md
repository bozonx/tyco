# Команды, оверлей команд и голосовой ввод — дизайн-документ

Статус: этапы 1 (библиотека команд), 2 (внешний вызов), 3 (оверлей команд с
клавиатуры) и 4 (инструменты) реализованы, остальные — нет.
Дата: 2026-10-03, обновлено 2026-10-04 (библиотека команд, оверлей команд,
внешний вызов; распознавание без LLM, разбор аргумента — дело инструмента;
внешний вызов реализован, поиск команды — в Rust; встроенные инструменты ядра,
команды по умолчанию, действия плагинов в меню — через команды).

## 1. Цель

Пользователь один раз описывает свои действия — скрипты, вебхуки, действия
плагинов — в **библиотеке команд** и потом вызывает их откуда удобно:

- из **меню действий над текстом** — как сейчас, команда получает текст из
  редактора;
- из **оверлея команд** по отдельному хоткею — голосом или с клавиатуры, в
  том числе без всякого текста («включи свет», «запусти бэкап»);
- **извне** — из left-hand-control (LHC), скриптов, хоткеев оконного
  менеджера — через D-Bus или `tyco-ctl`;
- позже — из **агентного чата** через вызов инструментов LLM (§12).

Голосовые команды полезнее всего, когда фраза несёт и **выбор команды**, и
**аргумент**:

- «Запиши в блокнот: купить молоко»
- «Отправь в телеграм: буду через десять минут»
- «Напомни через час позвонить маме»

Команды без аргумента («запусти бэкап») тоже поддерживаются; для них в том же
оверлее есть выбор с клавиатуры. Оверлей ориентирован на «сказал и забыл»:
автоматизации, умный дом, отправку куда-то, а не на обработку текста с
результатом.

Модель данных с самого начала строится так, чтобы её можно было использовать
во всех местах вызова, включая будущий агентный чат.

## 2. Архитектура: один реестр инструментов, одна библиотека команд, несколько мест вызова

```
              Источники инструментов
  ┌──────────────┬────────────────┬─────────────────┐
  │ ядро:        │ встроенные     │ MCP-серверы     │
  │ script,      │ плагины        │ (позже, через   │
  │ webhook,     │ (FastNote, …)  │  Rust)          │
  │ core.*       │                │                 │
  └──────┬───────┴───────┬────────┴────────┬────────┘
         └───────────────┼─────────────────┘
                         ▼
                 Реестр инструментов
                         │
          команды: созданные пользователем
          (инструмент + настройки + фразы)
          и команды по умолчанию (§3.12)
                         ▼
                 Библиотека команд
                         │
   ┌─────────────┬───────┴───────┬───────────────┬──────────────┐
   ▼             ▼               ▼               ▼              ▼
 Меню         Оверлей         Оверлей        Внешний        Агентный
 действий     команд:         команд:        вызов:         чат (позже):
 над текстом  голос           клавиатура     D-Bus,         LLM выбирает
 (текст из    (фраза →        (поиск,        tyco-ctl       команды через
 редактора)   команда,        клавиши        (LHC,          tool calling
              остаток →       1–9)           скрипты)
              аргумент)
                  │                                              ▲
                  └──── не распознано: «отправить в чат» ────────┘
```

Во всех местах вызова, кроме агентного чата, команда получает **текст** (или
ничего). Если инструменту нужен структурированный вход, текст разбирает сам
инструмент (§5.2). Агент заполняет структурированный вход напрямую.

Почему голосовой режим, а не только чат-агент:

|                                 | Режим голосовых команд           | Агентный чат                     |
| ------------------------------- | -------------------------------- | -------------------------------- |
| Скорость                        | мгновенно, если фраза совпала    | 1–5 с и больше на каждый шаг LLM |
| Предсказуемость                 | одна фраза — всегда одна команда | модель может выбрать по-разному  |
| Без LLM и без сети LLM          | работает (кроме STT)             | не работает                      |
| Стоимость                       | почти ноль                       | токены на каждый запрос          |
| Многошаговые задачи и уточнения | нет                              | да                               |

Голосовая команда — «сказал и забыл», как хоткей. Агент — разговор. Нужны оба,
и они делят одну библиотеку команд. Сейчас в `lib/chat` нет вызова
инструментов, поэтому голосовые команды делаются первыми и от агента не
зависят.

## 3. Принятые решения

### 3.1. Библиотека команд — единственное место настройки

Пользовательские скрипты и вебхуки больше не настраиваются прямо в меню
действий. Они живут в библиотеке команд (вкладка настроек «Команды»), а меню
действий, оверлей, внешний вызов и чат ссылаются на команды по id.

Почему:

- одну команду настраивают один раз, а вызывают из любого места; без
  библиотеки тот же вебхук пришлось бы заводить и в меню, и в голосовом режиме;
- секрет вебхука, логи и история привязаны к одной сущности;
- плагинные инструменты и MCP-инструменты становятся командами тем же путём,
  что и скрипты, — отдельной регистрации «для меню» и «для голоса» нет.

Меню действий над текстом становится упорядоченным списком ссылок:
встроенные действия (`standard`), действия плагинов (`plugin`) и команды из
библиотеки (`command`). Существующие script/webhook-действия переносятся в
библиотеку при загрузке конфига (§4.3).

### 3.2. Вход и вывод команды — две независимые оси

Деление «возвращает результат / не возвращает» не подходит: «отправь в
Telegram» берёт текст, но ничего не возвращает, и это нормальное действие
над текстом.

|                  | вывод — текст                       | без вывода                               |
| ---------------- | ----------------------------------- | ---------------------------------------- |
| **вход — текст** | перевод, LLM-правка, скрипт-фильтр  | отправить в Telegram, записать в заметку |
| **без входа**    | вставить дату, сгенерировать пароль | запустить бэкап, включить свет, пауза    |

- **Вход** определяется инструментом (§5.2): без входа, текст как есть или
  текст, который инструмент разбирает сам. У `script` и `webhook` это
  настройка команды «принимает текст» — один инструмент годится для обоих
  случаев.
- **Что делать с выводом** решает команда, а не место вызова: `afterRun` и
  `logOutput`. Это тот же флаг, что сейчас у script/webhook-действий, только
  переехавший на уровень команды, чтобы работать и для плагинных
  инструментов. Значения:
  - `none` — вывод отбрасывается (только тост с результатом);
  - `showMenu` — меню результата;
  - `replaceSelection` — вывод заменяет выделение в активном окне тем же
    механизмом, что глобальные действия над выделением
    (`lib/selection-replace`): статус в пузыре, отмена, проверка, что окно и
    выделение не сменились. Если текст пришёл не из выделения (голос, поле
    ввода, редактор, внешний вызов с `text`), выполняется `showMenu`;
  - `copy` — вывод кладётся в буфер обмена, тост «Скопировано».

  `replaceSelection` и `copy` нужны встроенным инструментам «текст → текст»
  (§3.7): перевод выделения из оверлея без них заканчивался бы лишним меню.

- Пустой вывод у команды с `afterRun: 'none'` — не ошибка. Предупреждение
  «нет вывода» показывается при остальных значениях.

Где какие команды видны:

- в меню действий над текстом можно добавить только команды, принимающие
  текст;
- в оверлее — все команды с `availableIn.launcher`;
- извне и в чате — по флагам `availableIn.external` и `availableIn.chat`.

### 3.3. Оверлей команд: голос и клавиатура в одном окне

Отдельного «меню быстрых действий для автоматизаций» с сеткой клавиш и
страницами нет. Вместо него — один оверлей команд, который открывается двумя
хоткеями:

- **голосовой хоткей** — оверлей открывается сразу с записью, список команд
  виден на экране;
- **хоткей выбора** — тот же оверлей без записи: поиск по вводу, у первых
  девяти команд клавиши `1`–`9`, стрелки и Enter.

Голосовые команды — по-прежнему отдельный режим, а не часть диктовки. В
диктовке приходится решать две задачи: «это команда или текст» и «какая
именно команда». Вторая решается надёжно, первая — нет, а цена ошибки высока:
фраза «сделай вывод по отчёту» в обычном тексте не должна запускать
shell-скрипт. В оверлее первой задачи нет: всё, что сказано после хоткея,
считается командой.

Слова-триггеры («сделай», «выполни», «запусти», «Тайко») в этом режиме не
обязательны. Если они есть в начале фразы, распознаватель их отбрасывает —
и в высказывании, и во фразах команд (§6), поэтому фраза «запусти бэкап»
совпадает и с «запусти бэкап», и с «бэкап».

Откуда берётся текст для команды со входом:

- голос — остаток высказывания после совпавшей фразы (§6), в том виде, как
  его выдал STT;
- клавиатура — выделенный текст в активном окне (тем же механизмом, что
  `ReplaceSelection`); если его нет — поле ввода прямо в оверлее.

Несколько меню, страницы и раскладки на 15 клавиш в tyco не делаем: это роль
Quick menu в LHC, которое вызывает команды tyco через внешний вызов (§3.4).
Пользователю без LHC хватает оверлея с поиском и порядком перетаскиванием.
Если команд станет слишком много для поиска, сначала добавим группы или теги
в библиотеке (§13).

Встраивать команды в диктовку («Тайко, …» в начале высказывания) можно
рассмотреть позже, как отдельную опцию, только с обязательным подтверждением
(§13).

### 3.4. Внешний вызов: D-Bus и `tyco-ctl`

Связь односторонняя: LHC, скрипты и хоткеи оконного менеджера вызывают
команды tyco, а tyco о LHC ничего не знает.

- **D-Bus** (`org.tyco.Interface`, Linux):
  - `RunCommand(command: s, text: s)` — запустить команду; `text` пустой,
    если аргумента нет;
  - `ListCommands() -> s` — JSON-массив `{ id, name, input }` команд с
    `availableIn.external`, чтобы LHC мог показать список для выбора.
- **`tyco-ctl`** (все платформы, через существующий activation-сокет):
  - `tyco-ctl run <command> [text...]` — слова после команды образуют текст;
    `tyco-ctl run <command> -` читает текст из stdin (предпочтительно для
    чувствительного текста: аргументы командной строки видны другим
    процессам). stdin читается только по явному `-`: процесс, запущенный
    хоткеем оконного менеджера, может унаследовать stdin, который никогда не
    закроется. Один перевод строки в конце текста отбрасывается;
  - `tyco-ctl commands` — тот же JSON, что `ListCommands`.

Пустой текст — то же, что его отсутствие. Текст, переданный команде без
входа, отбрасывается: такой команде он не нужен, а вызывающий скрипт может
передавать текст всем командам одинаково. Сообщение протокола сокета —
до 1 МиБ.

**Поиск команды по `command`:** сначала точное совпадение с id; затем
совпадение с названием после нормализации (регистр, `ё → е`, пробелы) среди
команд, которые можно вызвать извне (включена, `availableIn.external`,
инструмент доступен). Если таких несколько — ошибка «неоднозначно» со
списком их id, ничего не запускается. Если по названию нашлась только
недоступная команда — ошибка с причиной («выключена», «недоступна извне»).
В редакторе команды id виден и копируется кнопкой: для привязок в LHC
надёжнее id, название удобнее для ручных скриптов.

Поиск выполняет Rust по конфигу, который уже хранит бэкенд, а не webview:
ответ и ошибки синхронны и не зависят от round-trip в webview
(`services/external_commands.rs`).

Сейчас Rust знает инструменты по жёсткому списку `KNOWN_TOOLS`
(`script`, `webhook`). С этапа 4 инструменты плагинов и доступность `core.*`
(нужна LLM) известны только webview, поэтому быстрое окно при загрузке и
перезагрузке плагинов передаёт в Rust **каталог инструментов**
(`set_tool_catalog`): `{ id, input: 'none' | 'text' | 'parsed' | 'structured', available, reason? }` (`structured` — вход, который из текста может заполнить
только LLM: такая команда принимает текст лишь с `llmArgumentParsing`). Rust хранит его в памяти и по нему решает «инструмент
недоступен», «принимает ли команда текст» (`ListCommands`, фон или оверлей).
Пока каталог не пришёл (первые секунды после запуска), команда незнакомого
Rust инструмента получает ошибку «инструменты ещё загружаются»; `script` и
`webhook` известны Rust всегда. Нормализация названия задана дважды:
`normalize_name` в Rust и `normalizeCommandName` в `lib/commands`.

**Поведение:**

- вызов возвращается сразу после того, как команда найдена и принята к
  запуску; «не найдена», «неоднозначно», «выключена», «недоступна извне»,
  «инструмент недоступен» — синхронная ошибка D-Bus / ненулевой код выхода
  `tyco-ctl`;
- текст проходит тот же путь, что голосовой аргумент: если инструмент
  разбирает текст сам (§5.2), разбор выполняется в tyco (с этапа 4);
- команда, которой не нужно ничего спрашивать или показывать (есть текст или
  он не нужен, без подтверждения, `afterRun: 'none'`), выполняется **в
  фоне**, без окна: Rust шлёт событие `app://command-run` в webview быстрого
  окна (оно существует всегда, даже скрытое). Пока команда быстрая, ничего не
  показывается; затем пузырь статуса (как у замены выделения) сообщает
  результат, а ошибки дублируются системным уведомлением — ведь окна tyco на
  экране нет;
- остальные открывают **оверлей команд** сразу на этой команде
  (`InitParams.launcherRequest`): команде со входом без `text` текст берётся
  из выделения, а если его нет — из поля ввода; `confirm: 'always'` —
  подтверждение; `afterRun: 'showMenu'` — выполнение и меню результата;
- каждое выполнение записывается в `actions.log` с источником `external`, как
  запуск из оверлея (§7.3).

### 3.5. Команды форматирования диктовки — отдельная тема

«Новая строка» и «новый абзац» внутри диктовки — это другой класс команд. Они
не проходят через распознавание команд: у них фиксированный маленький
словарь, точное совпадение и срабатывание только отдельным сегментом (пауза до
и после). Проговаривать знаки препинания («точка», «запятая») не нужно:
пунктуацию расставляют STT-провайдер и LLM-коррекция. В этот документ они не
входят.

### 3.6. Инструмент и команда

Две сущности:

- **Инструмент** — что приложение умеет делать. Его предоставляет ядро, плагин
  или MCP-сервер. Формат совместим с MCP tool: id, описание для LLM, JSON-схема
  входа (`inputSchema`), плюс схема настроек (`configFields`) и разбор текста
  (`parseText`, §5.2), которых в MCP нет.
- **Команда** — то, что создаёт пользователь в библиотеке: название,
  описание, фразы для распознавания, выбранный инструмент, заполненные
  настройки, что делать с выводом, флаг подтверждения, где команда доступна
  (оверлей, извне, чат).

Настройки и вход — разные вещи:

- **настройки** задаются один раз в редакторе команды (папка заметок, URL
  вебхука, команда скрипта);
- **вход** приходит при каждом вызове: из редактора, из сказанной фразы, из
  выделения, из внешнего вызова или от LLM-агента (текст заметки).

Из одного инструмента можно сделать несколько команд с разными настройками:

| Команда         | Фразы                 | Инструмент                   | Настройки                   |
| --------------- | --------------------- | ---------------------------- | --------------------------- |
| Рабочая заметка | `(запиши              | добавь) в рабочий [блокнот]` | `FastNote.write`            | папка `~/work`, дописать в daily |
| Идея            | `запиши идею`, `идея` | `FastNote.write`             | папка `~/ideas`, новый файл |
| Бэкап           | `(запусти             | сделай) бэкап`               | `script`                    | `~/bin/backup.sh`, без текста    |

Распознаватель, оверлей и агент видят плоский список команд и не знают,
откуда взялся инструмент.

**В оверлей, во внешний вызов и в чат попадают только команды.** Возможности
приложения и плагинов становятся инструментами, а не командами: инструмент
сам по себе нигде не виден, пока из него нет команды. Чтобы оверлей не был
пустым из коробки, инструменты объявляют команды по умолчанию (§3.12).

Оверлей — не палитра действий приложения в духе VS Code («открыть
настройки», «история», «переключить тему»). Такие пункты в библиотеку команд
не добавляем: это навигация по UI, им не нужны фразы, настройки и внешний
вызов. Если палитра действий приложения понадобится, это отдельный список в
том же окне (§13).

**Агент получает только команды, а не «сырые» инструменты.** Инструмент
`script` без настроек — это «выполни любую shell-команду», такое LLM давать
нельзя. Пользователь явно создаёт команду и отмечает, что она доступна в чате.

### 3.7. Источники инструментов

1. **Ядро: `script` и `webhook`.** Исполнители — `lib/custom-actions/`
   и `src-tauri/src/services/custom_actions.rs`; меню действий вызывает их
   через команду. Это «запасной выход»: всё, для чего нет инструмента,
   пользователь делает скриптом, который может вызвать любую CLI или API.
2. **Ядро: встроенные возможности приложения** (`core.*`, §5.3). Тонкие
   адаптеры над уже существующим кодом, без нового поведения:

   | Инструмент       | Вход  | Вывод | Код, который вызывается                           | Настройки          |
   | ---------------- | ----- | ----- | ------------------------------------------------- | ------------------ |
   | `core.insert`    | текст | нет   | вставка в окно (`typeIntoWindowAndClose`)         | —                  |
   | `core.copy`      | текст | нет   | буфер обмена (`putIntoClipboardAndClose`)         | —                  |
   | `core.correct`   | текст | текст | `correctText`, как в `selection-replace`          | —                  |
   | `core.translate` | текст | текст | `translateTo(language)`                           | язык перевода      |
   | `core.aiTask`    | текст | текст | `aiCustomPrompt(prompt)`                          | инструкция для LLM |
   | `core.askInChat` | текст | нет   | открыть чат с текстом (`startChatWithAttachment`) | —                  |

   Перевод и AI-задача хранят в команде **язык** и **текст инструкции**, а не
   номер слота, как глобальные действия над выделением (`SelectionAction`):
   слоты можно переставить или очистить, и команда «Перевести на английский»
   молча начала бы переводить на другой язык. Редактор команды предлагает
   заполнить поля из слотов (выбор языка из `toTranslateLanguages`, «взять
   инструкцию из AI-задачи»), но копирует значение. Перевод, коррекция и
   AI-задача без настроенной LLM помечаются недоступными, как команды
   выключенного плагина (§5.2).

3. **Встроенные плагины** регистрируют инструменты через `PluginContext`
   (§5). Они остаются TypeScript-кодом внутри приложения, потому что им нужен
   доступ к UI, меню и редактору. Переносить их в MCP-серверы смысла нет.
4. **MCP-серверы** (позже). Rust запускает stdio-сервер, получает список его
   tools, и они появляются в реестре. Настройки инструмента пустые, параметры
   сервера (команда запуска, переменные окружения, секреты) задаются на уровне
   сервера. Это готовые интеграции (Notion, Todoist, календари и т. д.) без
   собственного магазина плагинов.

**Что остаётся вне инструментов.** Инструмент — это «вход → действие → вывод»
без собственного UI. Всё, что работает с редактором или открывает своё окно
выбора, остаётся как есть:

- **стандартные пункты меню действий** (`StandardMainAction`). Пункты
  «Перевод» и «AI-задача» открывают выбор языка и задачи, «Коррекция» —
  режим коррекции с диффом. Инструменты `core.*` их не заменяют, а дают то же
  действие без UI с заранее выбранным языком или задачей. «Вставить» и
  «Скопировать» тоже остаются стандартными пунктами: они всегда есть в меню и
  особо обрабатываются в `DiffMenu`, `PreviewMenu`, `InsertMenu`;
- **меню правки, регистра и форматирования** (`registerEditItems` и др.,
  например RussianStress) — операции над текстом в редакторе;
- **кнопки тулбара** (`registerToolbarItems`) — вызывают инструмент плагина
  напрямую, с текстом редактора и настройками плагина, без команды.

**Действия плагинов в меню переходят на команды.** Если действие плагина —
это «текст → действие» без своего UI (FastNote, SearchInInternet), плагин
объявляет его только как инструмент с командой по умолчанию (§3.12), а не
как `ActionItem`. Пункт меню — ссылка `command` на эту команду. Так у плагина
одна регистрация вместо двух, и пункт меню автоматически доступен в оверлее,
голосом и извне. `registerActionsItems` и `PluginMainAction` остаются только
для действий с собственным UI (подменю, модальное окно). Сейчас таких нет,
поэтому делаем это сразу, на этапе 4, пока плагинов три.

### 3.8. Плагины встроенные, установки в рантайме нет

Плагины по-прежнему вкомпилированы в сборку (`apps/desktop-ui/src/plugins.ts`).
Сторонние JS-плагины в рантайме не загружаем:

- CSP запрещает inline- и динамические скрипты (`script-src`), а ослаблять её
  не хотим;
- чужой код в webview получает доступ к IPC; изоляция (iframe/worker с узким
  API) — отдельный большой проект.

Сторонние интеграции подключаются через MCP-серверы (§3.7): это отдельные
процессы, ими управляет Rust, и CSP webview они не затрагивают.

### 3.9. Распознавание выбирает только команду, без LLM

Распознаватель решает одну задачу: **какая команда сказана**. Всё, что
осталось после фразы команды, — сырой текст-аргумент, который передаётся
команде без изменений. Как его понимать, решает инструмент (§5.2).

- У каждой команды есть **несколько фраз**, с альтернативами и необязательными
  словами (§6.2). Пользователь не обязан помнить точное название.
- Сопоставление **локальное и детерминированное**: нормализация, стемминг,
  префиксное сопоставление по токенам с небольшим допуском на ошибки STT.
  Работает без сети и мгновенно; одна и та же фраза всегда даёт один и тот же
  результат.
- **Подсказки для STT.** При открытии голосового оверлея слова из фраз команд
  передаются провайдеру как ключевые термины (`keyterms` в `@bozonx/ai-kit`:
  `keyterm` у Deepgram, `keyterms_prompt` / `word_boost` у AssemblyAI,
  `prompt` у OpenAI-совместимых). Это повышает точность на названиях
  («бэкап», «Obsidian», имена) там, где ошибки возникают изначально.
- **LLM в распознавании нет.** Причины:
  - задержка 1–3 с ломает «сказал и забыл», причём именно на неуверенных
    фразах — пользователь не понимает, почему одна команда срабатывает сразу,
    а другая с паузой;
  - уверенность, которую сообщает LLM, плохо откалибрована, пороги на ней не
    построить;
  - неясный запрос и так уходит к LLM через «Отправить в чат» (§3.11), а с
    агентом — в полноценный путь с выбором команд. Второй, промежуточный путь
    к LLM внутри оверлея не нужен.
- Неуверенность распознавателя закрывается интерфейсом, а не угадыванием:
  подтверждение, список кандидатов, обучение на выборе пользователя (§6.6).

### 3.10. Подтверждение вместо угадывания

Решение зависит от качества совпадения (§6.5):

- точное и однозначное → выполнить;
- нечёткое или два близких кандидата → показать подтверждение;
- нет совпадения → оставить в оверлее список команд с поиском, транскрипт и
  кнопку «Отправить в чат».

У команды есть флаг `confirm: 'auto' | 'always'`. Для инструмента `script`, для
всех MCP-инструментов и для команд с разбором аргумента через LLM (§5.2) по
умолчанию `always`: действие нельзя отменить, а результат разбора стоит
показать. Флаг действует при любом способе вызова, кроме меню действий над
текстом: там пользователь уже явно выбрал пункт.

**Окно отмены.** Команда, запущенная голосом без подтверждения, выполняется
не сразу: оверлей показывает «Выполняю „Бэкап“… [Отменить]» в течение
`voiceCommands.undoWindowMs` (по умолчанию 1500 мс, `0` — выключено). Это
дешёвая страховка от ошибок STT без лишнего шага для пользователя. Для
клавиатуры и внешнего вызова окна отмены нет: там выбор явный.

### 3.11. Переход в чат

Если команда не распознана или пользователь сам выбрал «Отправить в чат»,
транскрипт открывается в чате как новое сообщение. До появления агента чат
просто ответит текстом. С агентом он сможет сам выбрать команды, так что
сложные запросы уйдут туда без изменений в оверлее.

### 3.12. Команды по умолчанию

Инструмент может объявить одну или несколько **команд по умолчанию**
(`defaultCommands`, §5.1) — готовые пресеты, которые не требуют настройки:
«Найти в интернете», «Заметка», «Дописать в дневник», «Перевести на
английский», «Исправить текст». Без них оверлей из коробки показывал бы только
script/webhook-команды пользователя.

- Команда по умолчанию добавляется в библиотеку **один раз**, когда её
  инструмент впервые появляется в реестре (запуск приложения для `core.*`,
  включение плагина). Это обычная команда: пользователь может её
  переименовать, изменить, выключить или удалить.
- Id детерминированный: `default:<toolId>:<localId>`, например
  `default:FastNote.write:note`. Id засеянных команд записываются в
  `UserConfig.seededCommands`; удалённая пользователем команда не
  появляется снова. Это тот же приём, что `mainActionRegistrations` для
  пунктов плагинов в меню.
- Название сохраняется текстом на текущем языке интерфейса (по `nameKey`):
  внешний вызов ищет команду по названию в Rust и не знает i18n-ключей. При
  смене языка интерфейса названия не меняются, как у команд пользователя.
- `availableIn.launcher` и `availableIn.external` — `true`, `confirm` —
  `auto`, фразы — из `phrasesKey` на текущем языке.
- `menu: { replaces?, preferredKey? }` — команда сразу получает пункт в меню
  действий. `replaces` — id прежнего пункта плагина (`FastNote:fastNote`):
  если он стоит в `mainActions`, его место занимает ссылка на команду, и
  клавиша пункта у пользователя не меняется. Если не стоит и пункт плагина
  ещё не был размещён (`mainActionRegistrations`), команда ставится по
  `preferredKey`, как сейчас `assignPluginActions`.
- Засевает и сохраняет конфиг webview **быстрого окна**, через обычное
  сохранение конфига: инструменты плагинов знает только webview, а быстрое
  окно создаётся при запуске и живёт всегда. Главное окно тоже загружает
  плагины, но только читает конфиг — иначе два окна засевали бы
  одновременно. Rust видит команды после сохранения.
- Инструменту, которому без настроек делать нечего (`script`, `webhook`,
  MCP-инструменты), команды по умолчанию не нужны.

Что засевается в первой версии:

| Инструмент                | Команды по умолчанию                                               | Пункт меню                                                  |
| ------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------- |
| `core.correct`            | «Исправить текст»                                                  | нет (в меню — стандартная коррекция)                        |
| `core.translate`          | «Перевести на &lt;язык&gt;» — по одной на каждый заполненный слот  | нет                                                         |
| `core.askInChat`          | «Спросить в чате»                                                  | нет                                                         |
| `FastNote.write`          | «Заметка», «Дописать в дневник» (настройки как у нынешних пунктов) | вместо `FastNote:fastNote` и `FastNote:fastNoteAppendDaily` |
| `SearchInInternet.search` | «Найти в интернете»                                                | вместо `SearchInInternet:searchInInternet`                  |

Для `core.translate` берутся слоты, заполненные в момент засевания; язык,
добавленный позже, получает команду только если пользователь создаст её сам.
`core.aiTask` не засевается: команда хранит копию инструкции, и после
правки AI-задачи в настройках копия молча разошлась бы с ней. Пусть
пользователь сам создаст команду, когда она ему нужна. Не засеваются и `core.insert`, `core.copy`: в меню это
стандартные пункты, а в оверлее вставлять или копировать выделение
бессмысленно. Такие команды пользователь создаёт сам, например «вставь …»
голосом (§14).

### 4.1. Команды

```ts

   */

  name: string

  type: 'command'
  commandId: string
}

export type MainActionConfig =
  StandardMainAction | PluginMainAction | CommandMainAction

  triggerWords: Record<string, string[]>

   * added to the built-in table
   */
  aliases: Record<string, string[]>
```

Присутствие в меню действий задаётся не флагом, а ссылкой в `mainActions`:
порядок пунктов меню остаётся там же, где сейчас.

### 4.2. Настройки встроенных инструментов

`toolConfig` у `script` и `webhook` — поля нынешних `ScriptMainAction` и
`WebhookMainAction` без `type`, `id`, `name`, `afterRun` и `logOutput`, плюс
новое поле `takesText: boolean` (по умолчанию `true`). Общий редактор полей
(`CustomActionFields.vue`) переезжает во вкладку «Команды».

`takesText: false` — команда без входа: `{{TEXT}}` в команде или шаблоне
запроса не допускается, редактор показывает ошибку.

`toolConfig` встроенных инструментов ядра (§3.7):

```ts
export interface TranslateToolConfig {
  /** Target language code, copied from a slot when the command is made */
  language: string
}

export interface AiTaskToolConfig {
  /** Instruction for the LLM, as the rule of an AI task */
  prompt: string
}
```

У `core.insert`, `core.copy`, `core.correct` и `core.askInChat` настроек нет
(`{}`). Пустой `language` или `prompt` — ошибка в редакторе, команда не
сохраняется.

`toolConfig` плагинного инструмента — значения его `configFields`. Поле,
которого нет в `toolConfig` или которое пустое, берётся из настроек плагина
(`getMyConfig`). Так команды по умолчанию с `toolConfig: {}` ведут себя ровно
как нынешние пункты меню, а пользователь переопределяет в команде только то,
что нужно (например, папку заметок).

### 4.3. Миграция

При загрузке конфига в Rust (`services/config_migration.rs`: конфигом,
резервной копией и версией владеет бэкенд) каждое `script`/`webhook`-действие
из `mainActions`:

1. превращается в `CommandConfig` с тем же `id` и `name`, `toolId` по типу,
   `toolConfig` из его полей, `takesText: true`, теми же `afterRun` и
   `logOutput`, `phrases: []`, `confirm: 'auto'` (поведение в меню не
   меняется), `llmArgumentParsing: false`, `availableIn` — всё `false`;
2. заменяется в `mainActions` на `{ type: 'command', commandId: id }`.

`id` сохраняется, поэтому секрет вебхука (`webhookSecretId(id)`) находится по
тому же ключу и переносить его не нужно. Миграция идемпотентна: повторная
загрузка ничего не меняет.

Миграция односторонняя: старая сборка не знает пункт `command` и молча
потеряет script/webhook-действия. Поэтому:

- в конфиг добавляется `configVersion` (номер схемы); миграция повышает его;
- перед первой записью мигрированного конфига рядом сохраняется копия
  исходного файла (`userConfig.v<старая версия>.bak`), один раз;
- сборка, встретившая `configVersion` новее своего, не перезаписывает конфиг
  (`save_user_config` возвращает ошибку) и показывает предупреждение в
  настройках.

Номер схемы задан дважды: `CONFIG_VERSION` в `packages/shared` и в
`config_migration.rs`; их нужно менять вместе.

**Версия 2** (этап 4). Rust ничего не переносит, только повышает версию и
сохраняет резервную копию: команды по умолчанию и замену пунктов плагинов в
меню выполняет webview при загрузке плагинов (§3.12), потому что только он
знает инструменты плагинов. Версия всё равно повышается: сборка версии 1 не
знает `core.*`, `FastNote.write`, `afterRun: 'replaceSelection' | 'copy'` и
при сохранении потеряла бы пункты FastNote и SearchInInternet в меню —
`mainActionRegistrations` уже не даст поставить их обратно.

### 4.4. Прочее

Хоткеи оверлея хранятся вместе с остальными глобальными хоткеями
(`UserConfig.hotkeys`) под id действий `voiceCommand` и `commandLauncher`.

`availableIn.chat` в первой версии сохраняется в конфиге, но в редакторе
команды не показывается и ни на что не влияет: агента ещё нет. По умолчанию
`false`. `availableIn.launcher` и `availableIn.external` у новых команд по
умолчанию `true`; оба флага есть в редакторе команды. У команд, перенесённых
миграцией, оба `false`: поведение в меню не меняется, а в другие места
команда попадает, только когда пользователь её туда добавит. У команд по
умолчанию (§3.12) оба `true`: ради этого они и засеваются.

```ts
  now: Date
  signal: AbortSignal
  /** Absent when no LLM is configured; the parser must then work without it */
  llm?: {
    /** Fills `schema` from `text` with structured output */
    extract(
      text: string,
      schema: JsonSchema,
      instructions?: string
    ): Promise<Record<string, unknown>>
  }
}

export type ParseResult =
  | { ok: true; input: Record<string, unknown>; summary?: string }
  | { ok: false; messageKey?: string; message?: string }

export interface ToolCall {
  input: Record<string, unknown>
  /** `toolConfig` of the command over the plugin settings (§4.2) */
  config: Record<string, unknown>
  /** Where the call came from; `CommandRunSource` gains `menu` and `toolbar` */
  source: 'menu' | 'toolbar' | 'launcher' | 'external' | 'chat'
  signal: AbortSignal
}

export interface ToolResult {
  ok: boolean
  /** Shown in the toast; i18n key or plain text */
  messageKey?: string
  message?: string
  /** Text output: handled by `afterRun`, logged, or returned to the agent */
  content?: string
}

export interface PluginContext {
  // ...existing members
  registerTools(tools: ToolDefinition[]): void
}
```

Инструмент сам не закрывает окно, не показывает меню результата и не пишет в
историю: этим занимается `command-runner` по `afterRun`. Тосты успеха и
ошибки — через `ToolResult.message*`, чтобы при фоновом внешнем вызове они
ушли в пузырь статуса и системное уведомление, а не в тост скрытого окна.

### 5.3. Встроенные инструменты ядра

`script`, `webhook` и `core.*` описываются тем же `ToolDefinition` и
регистрируются в реестре при создании (`lib/tools/builtin-tools.ts`,
`lib/tools/core-tools.ts`). Зависимости — функции из `useCallAi`, IPC и
чата — передаются в фабрику, как в остальных DI-моделях, поэтому
инструменты тестируются без Pinia и Tauri.

`core.correct`, `core.translate` и `core.aiTask` возвращают текст и ничего не
показывают сами: прогресс — «Выполняю…» в оверлее или пузырь статуса при
`replaceSelection`, ошибка LLM — через `ToolResult`. `core.insert`,
`core.copy` и `core.askInChat` работают с окнами, поэтому при вызове извне в
фоне всегда показывают результат (вставка в активное окно, открытое окно
чата).

### 5.4. Перевод FastNote и SearchInInternet на инструменты

- **SearchInInternet** регистрирует `SearchInInternet.search`
  (`TEXT_INPUT_SCHEMA`, `configFields` — URL поисковика) с командой по
  умолчанию «Найти в интернете», `menu.replaces: 'SearchInInternet:searchInInternet'`,
  `preferredKey: 'v'`. Кнопка тулбара вызывает `run` с текстом редактора и
  настройками плагина.
- **FastNote** регистрирует `FastNote.write` (`TEXT_INPUT_SCHEMA`,
  `configFields` — те же поля, что в настройках плагина: режим сохранения,
  шаблоны имени и содержимого, папка). Команды по умолчанию: «Заметка»
  (`toolConfig: {}`, `menu.replaces: 'FastNote:fastNote'`, клавиша `c`) и
  «Дописать в дневник» (`saveMode: 'append'` и шаблоны нынешнего
  `fastNoteAppendDaily`, `menu.replaces: 'FastNote:fastNoteAppendDaily'`,
  клавиша `d`). `clearInputAfterSave` остаётся настройкой плагина и
  применяется только при `source` `menu` или `toolbar`: у оверлея и внешнего
  вызова поля редактора нет.
- `registerActionsItems` эти плагины больше не вызывают. RussianStress не
  меняется: его пункт — в меню правки.

### 5.2. Откуда берётся вход: текст разбирает инструмент

Все места вызова, кроме агентного чата, дают команде одно и то же — **текст
или ничего**. Распознаватель не знает структуру входа и не пытается её
заполнить. Как превратить текст во вход, решает инструмент:

| Инструмент                                                | Голос, меню, извне                                 |
| --------------------------------------------------------- | -------------------------------------------------- |
| `NO_INPUT_SCHEMA`                                         | без текста                                         |
| `TEXT_INPUT_SCHEMA`                                       | текст как есть → `{ text }`                        |
| другая схема + `parseText`                                | текст → `parseText` → вход                         |
| другая схема без `parseText`, `llmArgumentParsing: true`  | текст → `llm.extract` по `inputSchema` → вход      |
| другая схема без `parseText`, `llmArgumentParsing: false` | недоступна; только в чате, в настройках помечается |

Почему так:

- инструмент лучше всех знает свою предметную область. Напоминанию нужен
  парсер времени («через час», «завтра в 9»), задаче в Todoist — дата и
  проект; универсальные слоты в распознавателе пришлось бы расширять под
  каждый новый случай;
- распознаватель остаётся простым и одинаковым для всех команд;
- LLM, если и нужна, работает на узкой задаче — разобрать аргумент уже
  выбранной команды по её схеме. Задержка здесь приемлема: команда известна,
  оверлей показывает «Разбираю…», а неверный разбор видно на подтверждении;
- плагин сам выбирает, как разбирать: детерминированно, через LLM или
  детерминированно с LLM как запасным вариантом. Без настроенной LLM
  `context.llm` отсутствует, и плагин должен либо справиться сам, либо
  вернуть понятную ошибку.

Порядок в `command-runner`:

1. получить текст (голос, выделение, поле ввода, внешний вызов);
2. разобрать по таблице выше; ошибка разбора → оверлей с сообщением и
   редактируемым текстом, ничего не запускается;
3. проверить вход по `inputSchema`;
4. подтверждение, если нужно: показывает команду и `summary` от разбора
   («Напоминание в 15:40: позвонить маме»), а не только сырой текст;
5. выполнить.

Агентный чат пропускает шаги 1–2: LLM-агент заполняет `inputSchema` сам.

Если плагин отключён или MCP-сервер не запущен, его команды остаются в
библиотеке, но помечаются как недоступные: не участвуют в распознавании, не
показываются в оверлее, пункт меню действий скрыт, внешний вызов возвращает
ошибку.

## 6. Распознавание

Вход — финальный текст от STT. Выход — команда, оценка совпадения и
аргумент.

### 6.1. Нормализация и токены

Высказывание разбивается на токены; для каждого токена хранится его
положение в исходной строке. Аргумент вырезается из **исходного**
транскрипта по этим положениям — с регистром и пунктуацией, как их выдал STT.
Нормализация нужна только для сравнения:

1. нижний регистр, `ё → е`, убрать пунктуацию, схлопнуть пробелы;
2. **алиасы**: встроенная таблица транслитераций и типичных вариантов STT
   (`telegram` / `телеграмм` → `телеграм`, `notion` → `ноушн`) плюс
   пользовательские `voiceCommands.aliases`;
3. **числа**: числительные словами → цифры («десять» → `10`) для двух
   поддерживаемых языков;
4. **стемминг**: Snowball-стеммер для русского и английского («запиши»,
   «записать», «запишите» → одна основа). Для других языков — без стемминга,
   только нормализация. Библиотека — офлайн npm-пакет, выбирается при
   реализации.

Фразы команд проходят ту же нормализацию один раз, при изменении библиотеки.

### 6.2. Фразы

Фраза — строка с мини-синтаксисом:

- `(запиши|добавь|сохрани)` — альтернативы;
- `[в]`, `[пожалуйста]` — необязательные слова;
- название команды тоже считается фразой.

Фразы разворачиваются в варианты при компиляции библиотеки (с ограничением
числа вариантов на фразу, иначе ошибка в редакторе). Слова-триггеры
отбрасываются в начале и высказывания, и каждого варианта фразы, поэтому
`запусти бэкап` совпадает с «бэкап».

Фраза команды ищется **в начале** высказывания; всё после неё — аргумент.
Фраза в конце («… в телеграм») в первой версии не поддерживается (§13).

### 6.3. Сопоставление по токенам

Для каждого варианта каждой фразы проверяем, совпадает ли начало
высказывания с ним, токен за токеном:

- токены совпадают, если равны их основы после стемминга;
- для длинных токенов допускается опечатка: расстояние Левенштейна по основе
  ≤ 1 при длине ≥ 5 и ≤ 2 при длине ≥ 8. Короткие токены — только точно:
  иначе «свет» и «сеть» совпадут;
- между токенами фразы допускается один лишний токен высказывания (слово-
  паразит «ну», «вот», «пожалуйста»), со штрафом;
- все обязательные токены варианта должны найтись по порядку, иначе вариант
  не совпал.

Оценка варианта: `1.0` за каждый точный токен, `0.7` за токен с опечаткой,
`−0.3` за пропущенный лишний токен; итог делится на длину варианта. Совпадение
**точное**, если все токены точные и лишних нет.

### 6.4. Выбор кандидата

1. Среди совпавших вариантов выигрывает **самый длинный** (больше токенов
   фразы): «запиши идею купить молоко» — команда «Идея» с аргументом «купить
   молоко», а не «Запиши» с аргументом «идею купить молоко».
2. При равной длине — больший score.
3. Если два кандидата разных команд остаются равными — неоднозначность.

### 6.5. Решение

- **Выполнить** (с окном отмены, §3.10): лучший кандидат точный, нет
  второго кандидата другой команды с той же длиной.
- **Подтвердить**: совпадение с опечатками или неоднозначность — оверлей
  показывает кандидатов, Enter выполняет первого, стрелки выбирают другого.
- **Не распознано**: нет совпадений — список с поиском, транскрипт,
  «Отправить в чат».

Дополнительные проверки входа:

- команда без входа, а остаток длиннее двух токенов → подтверждение: скорее
  всего, это другая команда или лишние слова;
- команда со входом, а остаток пустой → поле ввода в оверлее (или выделение
  при вызове с клавиатуры).

Коэффициенты и пороги подбираются по таблице фраз в юнит-тестах matcher.

### 6.6. Обучение на выборе пользователя

- Если пользователь подтвердил нечёткое совпадение, предложить добавить
  произнесённую фразу (известен совпавший отрезок) к фразам команды.
- Если команда не распознана и пользователь выбрал её из списка, предложить
  добавить фразу: поле заполнено транскриптом, пользователь обрезает
  аргумент.

Предложение — ненавязчивая строка в оверлее с кнопкой, а не модальное окно.

### 6.7. Живое распознавание

Распознаватель вызывается и на промежуточном транскрипте: оверлей
показывает предполагаемую команду и аргумент, пока пользователь говорит.
Выполняется команда только по финальному транскрипту. Это же служит основой
для автоостановки по паузе (§13).

### 6.8. Проверки в настройках

- предупреждение, если один вариант фразы (после нормализации) есть у двух
  команд;
- информация, если вариант фразы одной команды — префикс варианта другой:
  сработает правило самого длинного совпадения, но пользователь должен об
  этом знать;
- ошибка, если фраза разворачивается в слишком много вариантов;
- предупреждение, если две команды с `availableIn.external` называются
  одинаково после нормализации: вызов по названию будет неоднозначным (§3.4).

## 7. Пользовательский поток

### 7.1. Оверлей команд

1. Голосовой хоткей → компактный оверлей: индикатор записи, живой транскрипт
   с предполагаемой командой (переиспользуем `voice-session` /
   `live-dictation`) и список команд. Хоткей выбора → тот же оверлей без
   записи, фокус в поле поиска.
2. В любой момент можно нажать `1`–`9` или выбрать команду стрелками и Enter —
   запись прекращается, выбранная команда запускается.
3. Остановка записи: повторное нажатие хоткея, Enter или пауза
   (настраивается).
4. Распознавание (§6). Оверлей показывает выбранную команду и аргумент.
5. Разбор аргумента, если инструмент его требует (§5.2): «Разбираю…», затем
   `summary`.
6. Если нужно подтверждение: Enter — выполнить, Esc — отмена, стрелки — другой
   кандидат. Аргумент можно поправить с клавиатуры перед выполнением.
7. Без подтверждения — окно отмены (§3.10).
8. Выполнение, затем по `afterRun`: тост с результатом или меню результата.
   Оверлей закрывается.

Ошибки: нет STT-ключа или сети → понятное сообщение и ссылка в настройки,
выбор с клавиатуры продолжает работать. Команда не найдена → список с поиском
и кнопка «Отправить в чат»; транскрипт сохраняется. Ошибка разбора аргумента
→ сообщение инструмента и редактируемый текст.

### 7.2. Меню действий над текстом

Без изменений для пользователя: пункт-команда получает текст редактора, после
выполнения — меню результата, тост или ничего, по `afterRun`. Для команд с
`parseText` текст редактора разбирается так же, как голосовой аргумент.

### 7.3. История

Каждое выполнение команды из оверлея и извне записывается в журнал действий
`actions.log` (записи `[Command: …]`: откуда вызвана, id, результат, текст,
причина ошибки), чтобы было видно, почему сработала та или иная команда. С
появлением голоса и разбора аргумента в запись добавятся фраза и
разобранный вход. Отдельного экрана истории команд пока нет (§13); текст,
который команда получила, попадает и в обычную историю редактора как
отправленный, как у остальных действий.

Аргумент и вывод могут содержать секреты: перед записью они проходят через
существующий детектор секретов (`services/secret_detector.rs`), а вывод
пишется только при `logOutput` (в записи выполнения скрипта или вебхука).

## 8. Настройки

**Вкладка «Команды»** — библиотека, единственное место, где создаются и
редактируются пользовательские команды:

- Список: название, фразы, инструмент, вход (нет / текст / разбор), где
  доступна, включена ли. Порядок — перетаскиванием (`lib/sortable`); он же
  задаёт порядок в оверлее и клавиши `1`–`9`.
- Редактор: название, id (только чтение, кнопка «Копировать» — для LHC и
  скриптов), описание, фразы (список тегов, с подсказкой по синтаксису
  `( | )` и `[ ]`), инструмент и его поля, «принимает текст» (для
  script/webhook), «разбирать аргумент с помощью LLM» (только для
  инструментов со структурированным входом без `parseText`), что делать с
  выводом, логировать вывод, подтверждение, «в оверлее» / «извне».
- Для `script` и `webhook` — общий редактор полей, вынесенный из вкладки
  основных действий. Для `core.translate` — выбор языка (из слотов перевода
  или любой), для `core.aiTask` — поле инструкции и «Взять из AI-задачи».
  Для плагинных инструментов — их `configFields`; пустое поле показывает
  значение из настроек плагина как подсказку (§4.2).
- «Создать команду» начинается с выбора инструмента: список инструментов
  реестра с описаниями, недоступные — с причиной.
- Команда по умолчанию в списке ничем не отличается от остальных, кроме
  подсказки «Добавлена &lt;плагином / приложением&gt;». Команды недоступного
  инструмента (плагин выключен, нет LLM) показываются приглушёнными с
  причиной.
- Кнопка «Проверить фразу»: ввести текст и увидеть, какая команда выберется,
  какой вариант фразы совпал, с каким score, решение (§6.5) и аргумент; для
  инструментов с разбором — результат разбора. Без запуска команды.
- Параметры оверлея: оба хоткея, слова-триггеры по языкам, алиасы, окно
  отмены, подсказки фраз для STT.

**Вкладка основных действий** больше не редактирует скрипты и вебхуки. Кнопка
«Добавить» предлагает встроенные действия, действия плагинов с собственным UI
(сейчас таких нет) и команды из библиотеки, принимающие текст, плюс «Создать команду…», которая открывает
редактор команды и после сохранения сразу добавляет ссылку в меню. Удаление
пункта из меню не удаляет команду из библиотеки. Удаление команды из
библиотеки убирает и ссылки на неё.

MCP-серверы позже получают свою вкладку: список серверов, команда запуска,
переменные окружения и секреты, статус, список инструментов.

`lib/voice-commands/` покрывается юнит-тестами. Matcher и resolver
тестируются таблицами «фраза → ожидаемая команда, решение и аргумент» на
нескольких языках, включая ошибки STT и транслитерацию; миграция — таблицами
«старый `mainActions` → команды и ссылки»; засевание — таблицами «конфиг и
реестр → команды, `seededCommands`, `mainActions`», включая удалённую
команду по умолчанию и пункт плагина на нестандартной клавише.

Rust:

- `services/external_commands.rs` — поиск команды по id или названию,
  список для `ListCommands`, выбор между фоном и оверлеем, каталог
  инструментов из webview вместо `KNOWN_TOOLS`; миграция конфига —
  `services/config_migration.rs`;
- `services/dbus.rs` — методы `RunCommand` и `ListCommands`;
- `crates/activation-protocol` — запросы `RunCommand { target, text }` и
  `ListCommands`, поле `output` в ответе; команды `tyco-ctl run` и
  `tyco-ctl commands`;
- запуск передаётся в webview событием `app://command-run`, как
  `ReplaceSelection`, или активацией оверлея с `launcherRequest`; список для
  `ListCommands` Rust строит сам из конфига;
- отмена скрипта — `cancel_script_action` по `runId` из запроса
  `execute_script_action`;
- хоткеи — существующий `services/hotkeys.rs`, скрипты — `custom_actions.rs`,
  вебхуки — `services/net`, детектор секретов для истории —
  `services/secret_detector.rs`. MCP-клиент — отдельный сервис позже (§12).

## 10. Безопасность

- `script` выполняется с правами пользователя. По умолчанию для новых команд —
  подтверждение; окно подтверждения показывает, что будет запущено: команду
  скрипта или метод и URL вебхука.
- Выполнение можно отменить из оверлея: скрипт, которого ещё ждут,
  завершается, запрос вебхука прерывается. Скрипт, оставленный работать в
  фоне (без вывода, дольше 3 с), не отменяется.
- Аргумент подставляется в команду скрипта только в экранированном виде
  (`{{TEXT}}` заменяется на строку в кавычках) или передаётся через
  `TYCO_TEXT` и stdin — никогда как сырая строка (защита от инъекций через
  голос, внешний вызов или ответ LLM).
- В вебхуках аргумент подставляется в `payloadTemplate` с JSON-экранированием.
- Вход, полученный из `parseText` или `llm.extract`, валидируется по
  `inputSchema` до вызова, как и вход от агента.
- Внешний вызов доступен любому процессу пользователя на сессионной шине или
  на локальном activation-сокете. Это не расширяет права: такой процесс и так
  может запустить что угодно от имени пользователя. Поэтому `RunCommand`
  запускает только команды с `availableIn.external`, соблюдает `confirm` и не
  позволяет передать настройки — только `text`.
- Агенту доступны только команды с `availableIn.chat`, а не «сырые»
  инструменты.
- Аргументы и вывод в истории проходят через детектор секретов (§7.3).
- Ключи внешних сервисов хранятся в Rust-хранилище секретов
  (`services/secrets.rs`) и привязаны к origin сервиса. Плагин видит только
  `tyco-secret:<id>`. Секреты MCP-серверов передаются в переменные окружения
  процесса из Rust и в webview не попадают.
- Плагины получают только функции из `PLUGIN_DESKTOP_FUNCTIONS`. Новые
  возможности (в том числе `llm.extract` в `ToolParseContext`) добавляются
  явно.

## 11. Этапы

1. **✅ Библиотека команд.** Вынести исполнители script/webhook и редактор полей  
   в общие модули, ввести `CommandConfig`, `CommandMainAction`,
   `configVersion`, миграцию с резервной копией, вкладку «Команды» и выбор
   команд во вкладке основных действий. Поведение меню действий для
   пользователя не меняется. Полезно само по себе, даже без голоса.
   Фразы, описание, подтверждение и «в оверлее» / «извне» уже есть в модели,
   но в редакторе появятся вместе с этапами, которые их используют.
2. **✅ Внешний вызов.** `RunCommand` / `ListCommands` в D-Bus, `tyco-ctl run` /
   `tyco-ctl commands`, поиск по id и названию. После этого LHC может
   вызывать команды.
   Реализация: `services/external_commands.rs` (поиск, список, маршрут),
   фоновый запуск — `lib/commands/external-run.ts` в быстром окне, остальное —
   оверлей с `launcherRequest` (§3.4). В редакторе команды — флаг «Доступна
   извне» и предупреждение об одинаковых названиях (§6.8, последний пункт).
3. **✅ Оверлей команд с клавиатуры.** Хоткей выбора, список, поиск, `1`–`9`,
   ввод текста для команд со входом, подтверждение, история.
   Реализация: режим `commandLauncher` в быстром окне (хоткей по умолчанию не
   назначен, `tyco-ctl activate commandLauncher`), модель
   `lib/command-launcher/launcher-model.ts`. Пока в поле поиска пусто, `1`–`9`
   запускают команду, после ввода цифра идёт в поиск, а `Alt+1`–`9` запускают
   всегда. Подтверждение и ввод текста — один шаг: поле с текстом (выделение
   или пусто) и Enter. Выделение захватывается асинхронно; если оно пришло,
   пока поле пустое, оно подставляется в поле. При ошибке команды текст
   остаётся в поле для повтора. История — записи `[Command: …]` в
   `actions.log` (источник, id, результат, текст через детектор секретов);
   отдельного экрана истории команд пока нет. В редакторе команды появились
   «В оверлее команд», «Спрашивать подтверждение» и описание (оно видно в
   оверлее и участвует в поиске). Подтверждение показывает, что будет
   запущено. Если выделение пришло, пока оверлей ждёт текст, а
   пользователь ничего не ввёл, команда без подтверждения сразу выполняется
   на нём — как если бы выделение было на месте в момент выбора; команда с
   подтверждением только получает текст в поле. Выполняющуюся команду можно
   отменить. Удаление команды из библиотеки спрашивает подтверждение.
4. **✅ Инструменты.** По шагам, каждый — отдельный коммит, и после каждого  
   поведение меню для пользователя не меняется:
   1. `ToolDefinition`, реестр, `registerTools`, `ToolCall.source`; `script`
      и `webhook` как встроенные инструменты; `command-runner` вызывает
      инструмент через реестр вместо `isKnownTool`; `parseText` и
      `tool-input`.
   2. Каталог инструментов в Rust вместо `KNOWN_TOOLS` (§3.4).
   3. Инструменты ядра `core.*` (§3.7, §5.3), `afterRun: 'replaceSelection' | 'copy'` (§3.2), поля `core.translate` и `core.aiTask` в редакторе
      команды, выбор инструмента при создании команды.
   4. Команды по умолчанию и `seededCommands` (§3.12), `CONFIG_VERSION` 2
      (§4.3).
   5. FastNote и SearchInInternet на инструментах, их пункты меню — через
      команды по умолчанию (§5.4).

      Реализация. Реестр — `lib/tools/tool-registry.ts` (Pinia-обёртка
      `stores/tools.ts`, чтения реактивные), разбор входа и проверка по схеме —
      `lib/tools/tool-input.ts`, `script`/`webhook` — `lib/tools/builtin-tools.ts`,
      `core.*` — `lib/tools/core-tools.ts`. Функции `command-config` получают
      реестр вторым аргументом (`ToolLookup`). Кроме полей из §5.1 у
      `ToolDefinition` есть `inputSchemaFor(config)` (вход `script`/`webhook`
      зависит от `takesText`), `defaultAfterRun` (инструменты «текст → текст»
      создают команды с `replaceSelection`) и `descriptionKey` (описание в выборе
      инструмента); у `ToolCall` — `command` (id, имя, `logOutput`) и
      `wantsOutput`; у `ToolResult` — `level`, `cancelled` и `keepWindow` (окно
      не закрывается: FastNote из меню, вставка, браузер уже открыт).

      `afterRun: 'replaceSelection'` идёт через selection run с действием
      `command:<id>` (`lib/selection-replace`, источник в журнале — `selection`):
      оверлей, если текст — нетронутое выделение, прячется и вызывает
      `replace_selection_with_command`; внешний вызов без текста сразу
      запускает selection run (так работает и `tyco-ctl replace command:<id>`).
      Текст из поля ввода, редактора или внешнего вызова — меню результата.
      `copy` кладёт вывод в буфер через `copy_text`, не трогая окна.

      Каталог инструментов шлёт быстрое окно после загрузки плагинов и при
      каждом изменении (в том числе доступности LLM). Команды по умолчанию
      засевает быстрое окно (`lib/commands/default-commands.ts`): перед
      засеванием оно читает актуальный конфиг (`get_user_config`), потому что
      изменения из главного окна до него не доходят. В `seededCommands` кроме id
      команд записывается маркер инструмента `default:<toolId>`: инструмент
      засевается один раз, поэтому язык перевода, добавленный позже, и команда,
      которую инструмент объявит потом, не появляются сами (§13). Инструменты
      выключенного плагина не засеваются, пока плагин не включат. Кнопки тулбара
      плагинов вызывают инструмент через `lib/plugins/toolbar-tool.ts`.
      Недоступность `core.correct`/`core.aiTask` — пустая цепочка моделей задачи
      в настройках LLM; `core.translate` — то же только для провайдера `llm`.
5. **Распознавание.** `normalize`, `stemmer`, `phrase-pattern`, `matcher`,
   `resolver`, `phrase-lint` с табличными тестами; «Проверить фразу» в
   настройках.
6. **Голос в оверлее.** Голосовой хоткей, запись, подсказки `keyterms` для
   STT, живое распознавание, окно отмены, обучение на выборе, переход в чат.
7. **Новые инструменты второй очереди** (§14): напоминания, задачи в файле,
   медиа, «Открыть». FastNote, поиск, перевод, AI-задача, вставка и буфер
   обмена уже есть после этапа 4.
8. **Разбор аргумента через LLM.** `llm.extract` в `ToolParseContext`,
   `llmArgumentParsing` у команд; первый потребитель — напоминания.
9. **Агентный чат и MCP** (§12).
10. **Плагины внешних сервисов** по спросу.

## 12. Агентный чат и MCP (отложено)

Отдельный проект поверх реестра инструментов и библиотеки команд. Оверлей и
внешний вызов от него не зависят.

- **Вызов инструментов в `lib/llm`.** Передача списка команд с
  `availableIn.chat` как tools (`description` + `inputSchema`), разбор вызовов
  инструментов в ответе модели. Нужно проверить, что `@bozonx/ai-kit`
  поддерживает tool calling у используемых провайдеров, или расширить его.
- **Цикл агента в `lib/chat`.** Сообщение → ответ модели → вызовы инструментов
  → результаты → следующий шаг, с лимитом шагов и отменой.
- **UI в чате.** Вызов инструмента показывается в ленте (команда, вход,
  результат). Подтверждение по флагу `confirm` — прямо в чате.
- **Флаг «в чате»** появляется в редакторе команды вместе с агентом.
- **MCP-клиент в Rust.** Новый сервис: запуск stdio-серверов, жизненный цикл,
  `tools/list` и `tools/call`, таймауты, логи. Webview обращается к нему через
  IPC, сам процессы не запускает. Remote MCP (HTTP) — через тот же сетевой
  прокси Rust.
- **Skills.** Инструкции для агента («как оформить заметку в Notion», «как
  разобрать письмо»): markdown с описанием, который подмешивается в контекст по
  запросу. Нужны только агенту, голосовому режиму — нет. Делать после того, как
  агент заработает.

## 13. Отложено и открытые вопросы

- **Команды внутри диктовки** («Тайко, …» в начале высказывания) — только с
  подтверждением и отдельной настройкой. Нужно проверить, как STT распознаёт
  имя; помогут те же `keyterms`.
- **Фраза команды в конце высказывания** («буду через десять минут — в
  телеграм»): суффиксное сопоставление. Добавить, если появится спрос.
- **Семантическое сопоставление** («вруби свет» → «включи свет») без LLM:
  маленькая мультиязычная embedding-модель в Rust, офлайн. Только если
  фраз, алиасов и обучения на выборе окажется мало.
- **Палитра действий приложения** («открыть настройки», «история», «тема»)
  в том же окне, отдельным списком от команд (§3.6). Делать, только если
  попросят: большинство таких действий и так на хоткеях или в меню.
- **Новые команды по умолчанию для существующих пользователей.** Если
  инструмент позже добавит ещё одну команду по умолчанию, она засеется у
  всех, у кого её id нет в `seededCommands`, — то есть и у тех, кто давно
  пользуется плагином. Решить, нужно ли это, когда появится первый такой
  случай.
- **`replaceSelection` при голосовом вызове.** Сейчас голосовой аргумент —
  это не выделение, и `replaceSelection` откатывается к `showMenu`. Возможно,
  для «переведи выделенное» стоит брать выделение, если остаток фразы пуст.
- **Группы или теги команд** в библиотеке и фильтр в оверлее — когда команд
  станет слишком много для поиска. Несколько отдельных меню или страниц с
  раскладкой клавиш не делаем: это роль Quick menu в LHC.
- **Экран истории команд** — просмотр записей `[Command: …]` с фильтром по
  команде и источнику, если журнала `actions.log` окажется мало.
- **Ответ внешнему вызову с результатом:** сейчас `RunCommand` не ждёт
  выполнения. Если понадобится использовать вывод команды в скриптах —
  отдельный метод с ожиданием и таймаутом.
- **MCP-инструменты без настроек:** создавать команду для каждого вручную или
  разрешать агенту весь сервер целиком с подтверждением на каждый вызов.
- **Остановка записи по паузе** — подобрать длительность и решить, нужна ли
  она по умолчанию.
- **Общий парсер времени** для плагинов (`через час`, `завтра в 9`): если
  он понадобится нескольким инструментам, вынести в `lib/` и дать плагинам
  через `ToolParseContext`.

| Интеграция             | Пример фразы                        | Заметки                                                                   |
