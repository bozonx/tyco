# Команды, оверлей команд и голосовой ввод — дизайн-документ

Статус: принятые решения, к реализации не приступали.
Дата: 2026-10-03, обновлено 2026-10-04 (библиотека команд, оверлей команд,
внешний вызов).

## 1. Цель

Пользователь один раз описывает свои действия — скрипты, вебхуки, действия
плагинов — в **библиотеке команд** и потом вызывает их откуда удобно:

- из **меню действий над текстом** — как сейчас, команда получает текст из
  редактора;
- из **оверлея команд** по отдельному хоткею — голосом или с клавиатуры, в
  том числе без всякого текста («включи свет», «запусти бэкап»);
- **извне** — из left-hand-control (LHC), скриптов, хоткеев оконного
  менеджера — через D-Bus или `tyco-ctl`;
- позже — из **агентного чата** через вызов инструментов LLM (§12).

Голосовые команды полезнее всего, когда фраза несёт и **выбор команды**, и
**аргумент**:

- «Запиши в блокнот: купить молоко»
- «Отправь в телеграм: буду через десять минут»
- «Напомни через час позвонить маме»

Команды без аргумента («запусти бэкап») тоже поддерживаются; для них в том же
оверлее есть выбор с клавиатуры. Оверлей ориентирован на «сказал и забыл»:
автоматизации, умный дом, отправку куда-то, а не на обработку текста с
результатом.

Модель данных с самого начала строится так, чтобы её можно было использовать
во всех местах вызова, включая будущий агентный чат.

## 2. Архитектура: один реестр инструментов, одна библиотека команд, несколько мест вызова

```
              Источники инструментов
  ┌──────────────┬────────────────┬─────────────────┐
  │ встроенные   │ встроенные     │ MCP-серверы     │
  │ script,      │ плагины        │ (позже, через   │
  │ webhook      │ (FastNote, …)  │  Rust)          │
  └──────┬───────┴───────┬────────┴────────┬────────┘
         └───────────────┼─────────────────┘
                         ▼
                 Реестр инструментов
                         │
          пользователь настраивает команды:
          инструмент + настройки + фразы
                         ▼
                 Библиотека команд
                         │
   ┌─────────────┬───────┴───────┬───────────────┬──────────────┐
   ▼             ▼               ▼               ▼              ▼
 Меню         Оверлей         Оверлей        Внешний        Агентный
 действий     команд:         команд:        вызов:         чат (позже):
 над текстом  голос           клавиатура     D-Bus,         LLM выбирает
 (текст из    (фразы →        (поиск,        tyco-ctl       команды через
 редактора)   сопоставление,  клавиши        (LHC,          tool calling
              LLM запасной)   1–9)           скрипты)
                  │                                              ▲
                  └──── не распознано: «отправить в чат» ────────┘
```

Почему голосовой режим, а не только чат-агент:

|                                 | Режим голосовых команд           | Агентный чат                     |
| ------------------------------- | -------------------------------- | -------------------------------- |
| Скорость                        | мгновенно, если фраза совпала    | 1–5 с и больше на каждый шаг LLM |
| Предсказуемость                 | одна фраза — всегда одна команда | модель может выбрать по-разному  |
| Без LLM и без сети LLM          | работает (кроме STT)             | не работает                      |
| Стоимость                       | почти ноль                       | токены на каждый запрос          |
| Многошаговые задачи и уточнения | нет                              | да                               |

Голосовая команда — «сказал и забыл», как хоткей. Агент — разговор. Нужны оба,
и они делят одну библиотеку команд. Сейчас в `lib/chat` нет вызова
инструментов, поэтому голосовые команды делаются первыми и от агента не
зависят.

## 3. Принятые решения

### 3.1. Библиотека команд — единственное место настройки

Пользовательские скрипты и вебхуки больше не настраиваются прямо в меню
действий. Они живут в библиотеке команд (вкладка настроек «Команды»), а меню
действий, оверлей, внешний вызов и чат ссылаются на команды по id.

Почему:

- одну команду настраивают один раз, а вызывают из любого места; без
  библиотеки тот же вебхук пришлось бы заводить и в меню, и в голосовом режиме;
- секрет вебхука, логи и история привязаны к одной сущности;
- плагинные инструменты и MCP-инструменты становятся командами тем же путём,
  что и скрипты, — отдельной регистрации «для меню» и «для голоса» нет.

Меню действий над текстом становится упорядоченным списком ссылок:
встроенные действия (`standard`), действия плагинов (`plugin`) и команды из
библиотеки (`command`). Существующие script/webhook-действия переносятся в
библиотеку при загрузке конфига (§4.3).

### 3.2. Вход и вывод команды — две независимые оси

Деление «возвращает результат / не возвращает» не подходит: «отправь в
Telegram» берёт текст, но ничего не возвращает, и это нормальное действие
над текстом.

|                  | вывод — текст                       | без вывода                               |
| ---------------- | ----------------------------------- | ---------------------------------------- |
| **вход — текст** | перевод, LLM-правка, скрипт-фильтр  | отправить в Telegram, записать в заметку |
| **без входа**    | вставить дату, сгенерировать пароль | запустить бэкап, включить свет, пауза    |

- **Вход** определяется инструментом: `inputSchema` (`NO_INPUT_SCHEMA` или
  `TEXT_INPUT_SCHEMA`, §5). У `script` и `webhook` это настройка команды
  «принимает текст» — один инструмент годится для обоих случаев.
- **Что делать с выводом** решает команда, а не место вызова: `afterRun`
  (`none` или `showMenu`) и `logOutput`. Это тот же флаг, что сейчас у
  script/webhook-действий, только переехавший на уровень команды, чтобы
  работать и для плагинных инструментов.
- Пустой вывод у команды с `afterRun: 'none'` — не ошибка. Предупреждение
  «нет вывода» показывается только при `showMenu`.

Где какие команды видны:

- в меню действий над текстом можно добавить только команды со входом-текстом;
- в оверлее — все команды с `availableIn.launcher`;
- извне и в чате — по флагам `availableIn.external` и `availableIn.chat`.

### 3.3. Оверлей команд: голос и клавиатура в одном окне

Отдельного «меню быстрых действий для автоматизаций» с сеткой клавиш и
страницами нет. Вместо него — один оверлей команд, который открывается двумя
хоткеями:

- **голосовой хоткей** — оверлей открывается сразу с записью, список команд
  виден на экране;
- **хоткей выбора** — тот же оверлей без записи: поиск по вводу, у первых
  девяти команд клавиши `1`–`9`, стрелки и Enter.

Голосовые команды — по-прежнему отдельный режим, а не часть диктовки. В
диктовке приходится решать две задачи: «это команда или текст» и «какая
именно команда». Вторая решается надёжно, первая — нет, а цена ошибки высока:
фраза «сделай вывод по отчёту» в обычном тексте не должна запускать
shell-скрипт. В оверлее первой задачи нет: всё, что сказано после хоткея,
считается командой.

Слова-триггеры («сделай», «выполни», «запусти», «Тайко») в этом режиме не
обязательны. Если они есть в начале фразы, распознаватель их отбрасывает.

Откуда берётся текст для команды со входом-текстом:

- голос — остаток фразы после совпавшего префикса (§6);
- клавиатура — выделенный текст в активном окне (тем же механизмом, что
  `ReplaceSelection`); если его нет — поле ввода прямо в оверлее.

Несколько меню, страницы и раскладки на 15 клавиш в tyco не делаем: это роль
Quick menu в LHC, которое вызывает команды tyco через внешний вызов (§3.4).
Пользователю без LHC хватает оверлея с поиском и порядком перетаскиванием.
Если команд станет слишком много для поиска, сначала добавим группы или теги
в библиотеке (§13).

Встраивать команды в диктовку («Тайко, …» в начале высказывания) можно
рассмотреть позже, как отдельную опцию, только с обязательным подтверждением
(§13).

### 3.4. Внешний вызов: D-Bus и `tyco-ctl`

Связь односторонняя: LHC, скрипты и хоткеи оконного менеджера вызывают
команды tyco, а tyco о LHC ничего не знает.

- **D-Bus** (`org.tyco.Interface`, Linux):
  - `RunCommand(command: s, text: s)` — запустить команду; `text` пустой,
    если аргумента нет;
  - `ListCommands() -> s` — JSON-массив `{ id, name, input }` команд с
    `availableIn.external`, чтобы LHC мог показать список для выбора.
- **`tyco-ctl`** (все платформы, через существующий activation-сокет):
  - `tyco-ctl run <command> [text]`, текст можно передать и через stdin;
  - `tyco-ctl commands` — тот же JSON, что `ListCommands`.

**Поиск команды по `command`:** сначала точное совпадение с id; затем
совпадение с названием после нормализации (регистр, `ё → е`, пробелы). Если
по названию нашлось несколько команд — ошибка «неоднозначно», ничего не
запускается. В редакторе команды id виден и копируется кнопкой: для привязок
в LHC надёжнее id, название удобнее для ручных скриптов.

**Поведение:**

- вызов возвращается сразу после того, как команда найдена и принята к
  запуску; «не найдена», «неоднозначно», «выключена», «недоступна извне» —
  синхронная ошибка D-Bus / ненулевой код выхода `tyco-ctl`;
- результат выполнения — тост или системное уведомление и запись в историю,
  как при запуске из оверлея; `afterRun: 'showMenu'` открывает меню
  результата;
- команде со входом-текстом без переданного `text` текст берётся из
  выделения, а если его нет — открывается оверлей с полем ввода;
- `confirm: 'always'` соблюдается: открывается оверлей с подтверждением.

### 3.5. Команды форматирования диктовки — отдельная тема

«Новая строка» и «новый абзац» внутри диктовки — это другой класс команд. Они
не проходят через распознавание намерений: у них фиксированный маленький
словарь, точное совпадение и срабатывание только отдельным сегментом (пауза до
и после). Проговаривать знаки препинания («точка», «запятая») не нужно:
пунктуацию расставляют STT-провайдер и LLM-коррекция. В этот документ они не
входят.

### 3.6. Инструмент и команда

Две сущности:

- **Инструмент** — что приложение умеет делать. Его предоставляет ядро, плагин
  или MCP-сервер. Формат совместим с MCP tool: id, описание для LLM, JSON-схема
  входа (`inputSchema`), плюс схема настроек (`configFields`), которой в MCP
  нет.
- **Команда** — то, что создаёт пользователь в библиотеке: название,
  описание, фразы для распознавания, выбранный инструмент, заполненные
  настройки, что делать с выводом, флаг подтверждения, где команда доступна
  (оверлей, извне, чат).

Настройки и вход — разные вещи:

- **настройки** задаются один раз в редакторе команды (папка заметок, URL
  вебхука, команда скрипта);
- **вход** приходит при каждом вызове: из редактора, из сказанной фразы, из
  выделения, из внешнего вызова или от LLM-агента (текст заметки).

Из одного инструмента можно сделать несколько команд с разными настройками:

| Команда         | Фразы                                 | Инструмент       | Настройки                        |
| --------------- | ------------------------------------- | ---------------- | -------------------------------- |
| Рабочая заметка | «запиши в рабочий», «рабочая заметка» | `fastNote.write` | папка `~/work`, дописать в daily |
| Идея            | «запиши идею», «идея»                 | `fastNote.write` | папка `~/ideas`, новый файл      |
| Бэкап           | «запусти бэкап», «сделай бэкап»       | `script`         | `~/bin/backup.sh`, без текста    |

Распознаватель, оверлей и агент видят плоский список команд и не знают,
откуда взялся инструмент.

**Агент получает только команды, а не «сырые» инструменты.** Инструмент
`script` без настроек — это «выполни любую shell-команду», такое LLM давать
нельзя. Пользователь явно создаёт команду и отмечает, что она доступна в чате.

### 3.7. Источники инструментов

1. **Встроенные:** `script` и `webhook`. Это тот же код, что сейчас выполняет
   пользовательские действия в меню (`lib/action-menu/custom-actions.ts`,
   `src-tauri/src/services/custom_actions.rs`). Он становится исполнителем
   инструментов; меню действий вызывает его через команду. Это «запасной
   выход»: всё, для чего нет инструмента, пользователь делает скриптом,
   который может вызвать любую CLI или API.
2. **Встроенные плагины** регистрируют инструменты через `PluginContext`
   (§5). Они остаются TypeScript-кодом внутри приложения, потому что им нужен
   доступ к UI, меню и редактору. Переносить их в MCP-серверы смысла нет.
3. **MCP-серверы** (позже). Rust запускает stdio-сервер, получает список его
   tools, и они появляются в реестре. Настройки инструмента пустые, параметры
   сервера (команда запуска, переменные окружения, секреты) задаются на уровне
   сервера. Это готовые интеграции (Notion, Todoist, календари и т. д.) без
   собственного магазина плагинов.

Действия плагинов в меню (`PluginMainAction`) пока остаются как есть: это
действия над текстом с собственным UI (например, подменю). Плагин может
дополнительно объявить инструмент, и тогда пользователь делает из него
команду. Слияние этих двух регистраций — в §13.

### 3.8. Плагины встроенные, установки в рантайме нет

Плагины по-прежнему вкомпилированы в сборку (`apps/desktop-ui/src/plugins.ts`).
Сторонние JS-плагины в рантайме не загружаем:

- CSP запрещает inline- и динамические скрипты (`script-src`), а ослаблять её
  не хотим;
- чужой код в webview получает доступ к IPC; изоляция (iframe/worker с узким
  API) — отдельный большой проект.

Сторонние интеграции подключаются через MCP-серверы (§3.7): это отдельные
процессы, ими управляет Rust, и CSP webview они не затрагивают.

### 3.9. Распознавание: фразы, нечёткое сопоставление, LLM как запасной вариант

- У каждой команды есть **несколько фраз**. Пользователь не обязан помнить
  точное название.
- **Уровень 1 — локальное нечёткое сопоставление.** Работает без сети,
  мгновенно, детерминированно.
- **Уровень 2 — LLM-классификатор**, вызывается, только когда первый уровень
  не уверен. Использует существующий `lib/llm` со структурированным ответом:
  выбор из enum id команд плюс `none`.
- Классификатор спрятан за интерфейсом `IntentClassifier`. Jev от TypeSafe AI
  (типизированные решения с калиброванной уверенностью) концептуально
  подходит, но пока доступен только в раннем доступе и только в облаке. Его
  можно добавить второй реализацией позже, без изменения остального кода.
- Если LLM не настроена или нет сети, работает только первый уровень.

### 3.10. Подтверждение вместо угадывания

Решение зависит от уверенности:

- высокая и однозначная → выполнить;
- средняя или два близких кандидата → показать подтверждение;
- низкая или `none` → оставить в оверлее список команд с поиском и кнопку
  «Отправить в чат».

У команды есть флаг `confirm: 'auto' | 'always'`. Для инструмента `script` и
для всех MCP-инструментов по умолчанию `always`: действие нельзя отменить.
Флаг действует при любом способе вызова, кроме меню действий над текстом:
там пользователь уже явно выбрал пункт.

### 3.11. Переход в чат

Если команда не распознана или пользователь сам выбрал «Отправить в чат»,
транскрипт открывается в чате как новое сообщение. До появления агента чат
просто ответит текстом. С агентом он сможет сам выбрать команды, так что
сложные запросы уйдут туда без изменений в оверлее.

## 4. Модель данных

`packages/shared/src/user-config.ts`.

### 4.1. Команды

```ts
export interface CommandConfig {
  /**
   * Stable; kept from the migrated action so the webhook secret id stays the
   * same
   */
  id: string
  name: string
  /** Tells the LLM what the command does; the fallback and the agent use it */
  description?: string
  /** Phrases that select this command by voice; the name is matched as well */
  phrases: string[]
  /** `script`, `webhook`, `<pluginName>.<toolId>` or `mcp:<server>.<tool>` */
  toolId: string
  /** Values for the tool's config fields */
  toolConfig: Record<string, unknown>
  /** What to do with text the tool returns */
  afterRun: CustomActionAfterRun
  logOutput: boolean
  confirm: 'auto' | 'always'
  /** Where the command can be invoked, besides the action menu */
  availableIn: { launcher: boolean; external: boolean; chat: boolean }
  enabled: boolean
}

export interface CommandMainAction {
  type: 'command'
  commandId: string
}

export type MainActionConfig =
  StandardMainAction | PluginMainAction | CommandMainAction

export interface VoiceCommandsSettings {
  /** Leading words stripped before matching, per UI language */
  triggerWords: string[]
  /** Use the LLM when local matching is not confident */
  llmFallback: boolean
}

export interface UserConfig {
  // ...existing members
  commands: CommandConfig[]
  voiceCommands: VoiceCommandsSettings
}
```

Присутствие в меню действий задаётся не флагом, а ссылкой в `mainActions`:
порядок пунктов меню остаётся там же, где сейчас.

### 4.2. Настройки встроенных инструментов

`toolConfig` у `script` и `webhook` — поля нынешних `ScriptMainAction` и
`WebhookMainAction` без `type`, `id`, `name`, `afterRun` и `logOutput`, плюс
новое поле `takesText: boolean` (по умолчанию `true`). Общий редактор полей
(`CustomActionFields.vue`) переезжает во вкладку «Команды».

`takesText: false` — команда без входа: `{{TEXT}}` в команде или шаблоне
запроса не допускается, редактор показывает ошибку.

### 4.3. Миграция

При загрузке конфига (`normalizeMainActions`) каждое `script`/`webhook`-
действие из `mainActions`:

1. превращается в `CommandConfig` с тем же `id` и `name`, `toolId` по типу,
   `toolConfig` из его полей, `takesText: true`, теми же `afterRun` и
   `logOutput`, `phrases: []`, `confirm: 'auto'` (поведение в меню не
   меняется), `availableIn` — всё `false`;
2. заменяется в `mainActions` на `{ type: 'command', commandId: id }`.

`id` сохраняется, поэтому секрет вебхука (`webhookSecretId(id)`) находится по
тому же ключу и переносить его не нужно. Миграция идемпотентна: повторная
загрузка ничего не меняет.

### 4.4. Прочее

Хоткеи оверлея хранятся вместе с остальными глобальными хоткеями
(`UserConfig.hotkeys`) под id действий `voiceCommand` и `commandLauncher`.

`availableIn.chat` в первой версии сохраняется, но ни на что не влияет: агента
ещё нет. По умолчанию `false`. `availableIn.launcher` и
`availableIn.external` у новых команд по умолчанию `true`.

## 5. API инструментов для плагинов

`apps/desktop-ui/src/types/plugins.ts`:

```ts
/** Input schemas the voice matcher understands without the LLM */
export const NO_INPUT_SCHEMA = { type: 'object', properties: {} } as const
export const TEXT_INPUT_SCHEMA = {
  type: 'object',
  properties: { text: { type: 'string' } },
  required: ['text'],
} as const

export interface ToolDefinition {
  /** Local to the plugin; the full id becomes `<pluginName>.<id>` */
  id: string
  labelKey?: string
  label?: string
  icon?: string
  /** Shown to the LLM, in English, like an MCP tool description */
  description: string
  /** JSON Schema of the per-call input, as in MCP */
  inputSchema: JsonSchema
  /** Rendered in the command editor, same format as plugin settings */
  configFields?: InputConfigItem[]
  /** Phrases suggested when the user creates a command for this tool */
  defaultPhrasesKey?: string
  run(call: ToolCall): Promise<ToolResult>
}

export interface ToolCall {
  input: Record<string, unknown>
  config: Record<string, unknown>
  signal: AbortSignal
}

export interface ToolResult {
  ok: boolean
  /** Shown in the toast; i18n key or plain text */
  messageKey?: string
  message?: string
  /** Text output: goes to the result menu, the log or the agent */
  content?: string
}

export interface PluginContext {
  // ...existing members
  registerTools(tools: ToolDefinition[]): void
}
```

Оверлей и меню действий в первой версии работают с двумя схемами входа:
`NO_INPUT_SCHEMA` и `TEXT_INPUT_SCHEMA`. В голосе остаток фразы после
совпавшего префикса становится `text`. Инструменты с другой схемой
(напоминание: время + текст) можно вызвать голосом только через LLM: она
заполняет поля по `inputSchema`. Без LLM такие команды в оверлее доступны
только для голоса с LLM, в меню действий и для внешнего вызова — нет; в
настройках они помечаются.

Если плагин отключён или MCP-сервер не запущен, его команды остаются в
библиотеке, но помечаются как недоступные: не участвуют в распознавании, не
показываются в оверлее, пункт меню действий скрыт, внешний вызов возвращает
ошибку.

## 6. Распознавание

Вход — финальный текст от STT. Шаги:

1. **Нормализация:** нижний регистр, `ё → е`, убрать пунктуацию, схлопнуть
   пробелы.
2. **Отбросить слова-триггеры** в начале фразы («сделай», «выполни»,
   «запусти», «Тайко» и их варианты, которые выдаёт STT).
3. **Сопоставление по префиксу.** Для каждой фразы каждой команды ищем,
   насколько хорошо начало высказывания совпадает с фразой (по токенам, с
   допуском на окончания и опечатки: Левенштейн по токенам или триграммы).
   Остаток после совпавшего префикса — аргумент.
4. **Оценка:** лучший кандидат, его score и отрыв от второго.
5. **Решение** по порогам (§3.10). Если уверенности не хватает и
   `llmFallback` включён:
6. **LLM-классификатор.** В промпт идут id, названия, описания, фразы и схемы
   входа команд. Ответ: `{ commandId: <enum ids | "none">, input: object,
confidence: number }`. Ответ вне схемы или `input`, не прошедший валидацию по
   `inputSchema`, считается `none`.

Пороги подбираются по тестовой таблице фраз (юнит-тесты matcher). Для команд с
`NO_INPUT_SCHEMA` остаток должен быть пустым или очень коротким: иначе это,
скорее всего, другая команда.

**Проверки в настройках:**

- предупреждение, если одна фраза (после нормализации) есть у двух команд;
- предупреждение, если фраза одной команды — префикс фразы другой;
- предупреждение, если две команды с `availableIn.external` называются
  одинаково после нормализации: вызов по названию будет неоднозначным (§3.4).

**Обучение на подтверждениях (опционально):** если пользователь подтвердил
команду для непредусмотренной формулировки, предложить добавить её в фразы.

## 7. Пользовательский поток

### 7.1. Оверлей команд

1. Голосовой хоткей → компактный оверлей: индикатор записи, живой транскрипт
   (переиспользуем `voice-session` / `live-dictation`) и список команд.
   Хоткей выбора → тот же оверлей без записи, фокус в поле поиска.
2. В любой момент можно нажать `1`–`9` или выбрать команду стрелками и Enter —
   запись прекращается, выбранная команда запускается.
3. Остановка записи: повторное нажатие хоткея, Enter или пауза
   (настраивается).
4. Распознавание (§6). Оверлей показывает выбранную команду и аргумент.
5. Если нужно подтверждение: Enter — выполнить, Esc — отмена, стрелки — другой
   кандидат. Аргумент можно поправить с клавиатуры перед выполнением.
6. Выполнение, затем по `afterRun`: тост с результатом или меню результата.
   Оверлей закрывается.

Ошибки: нет STT-ключа или сети → понятное сообщение и ссылка в настройки,
выбор с клавиатуры продолжает работать. Команда не найдена → список с поиском
и кнопка «Отправить в чат»; транскрипт сохраняется.

### 7.2. Меню действий над текстом

Без изменений для пользователя: пункт-команда получает текст редактора, после
выполнения — меню результата, тост или ничего, по `afterRun`.

### 7.3. История

Каждое выполнение команды из оверлея и извне записывается в историю (откуда
вызвана, фраза, команда, аргумент, результат), чтобы было видно, почему
сработала та или иная команда.

## 8. Настройки

**Вкладка «Команды»** — библиотека, единственное место, где создаются и
редактируются пользовательские команды:

- Список: название, фразы, инструмент, вход (текст / нет), где доступна,
  включена ли. Порядок — перетаскиванием (`lib/sortable`); он же задаёт
  порядок в оверлее и клавиши `1`–`9`.
- Редактор: название, id (только чтение, кнопка «Копировать» — для LHC и
  скриптов), описание, фразы (список тегов), инструмент и его поля, «принимает
  текст» (для script/webhook), что делать с выводом, логировать вывод,
  подтверждение, «в оверлее» / «извне» / «в чате».
- Для `script` и `webhook` — общий редактор полей, вынесенный из вкладки
  основных действий.
- Кнопка «Проверить фразу»: ввести текст и увидеть, какая команда выберется, с
  каким score и аргументом. Без запуска команды.
- Параметры оверлея: оба хоткея, слова-триггеры, LLM как запасной вариант.

**Вкладка основных действий** больше не редактирует скрипты и вебхуки. Кнопка
«Добавить» предлагает встроенные действия, действия плагинов и команды из
библиотеки со входом-текстом, плюс «Создать команду…», которая открывает
редактор команды и после сохранения сразу добавляет ссылку в меню. Удаление
пункта из меню не удаляет команду из библиотеки. Удаление команды из
библиотеки убирает и ссылки на неё.

MCP-серверы позже получают свою вкладку: список серверов, команда запуска,
переменные окружения и секреты, статус, список инструментов.

```
  command-launcher/

```

`lib/action-menu/custom-actions.ts` перестаёт создавать пункты из
script/webhook-настроек; пункт `command` строится через `command-runner`.

Каждый модуль в `lib/tools/`, `lib/commands/`, `lib/command-launcher/` и
`lib/voice-commands/` покрывается юнит-тестами. Matcher и resolver
тестируются таблицами «фраза → ожидаемая команда и аргумент» на нескольких
языках; миграция — таблицами «старый `mainActions` → команды и ссылки».

Rust:

- `services/dbus.rs` — методы `RunCommand` и `ListCommands`;
- `crates/activation-protocol` — запросы `RunCommand { command, text }` и
  `ListCommands`; `tyco-ctl run` и `tyco-ctl commands`;
- запрос пересылается в webview событием, как `ReplaceSelection`; список
  команд для `ListCommands` webview отдаёт в Rust при каждом изменении
  библиотеки, чтобы ответ не зависел от round-trip в webview;
- хоткеи — существующий `services/hotkeys.rs`, скрипты — `custom_actions.rs`,
  вебхуки — `services/net`. MCP-клиент — отдельный сервис позже (§12).

## 10. Безопасность

- `script` выполняется с правами пользователя. По умолчанию для новых команд —
  подтверждение, в редакторе показывается точная команда.
- Аргумент подставляется в команду скрипта только в экранированном виде
  (`{{TEXT}}` заменяется на строку в кавычках) или передаётся через
  `TYCO_TEXT` и stdin — никогда как сырая строка (защита от инъекций через
  голос, внешний вызов или ответ LLM).
- В вебхуках аргумент подставляется в `payloadTemplate` с JSON-экранированием.
- Внешний вызов доступен любому процессу пользователя на сессионной шине или
  на локальном activation-сокете. Это не расширяет права: такой процесс и так
  может запустить что угодно от имени пользователя. Поэтому `RunCommand`
  запускает только команды с `availableIn.external`, соблюдает `confirm` и не
  позволяет передать настройки — только `text`.
- Агенту доступны только команды с `availableIn.chat`, а не «сырые»
  инструменты. Вход от LLM валидируется по `inputSchema` до вызова.
- Ключи внешних сервисов хранятся в Rust-хранилище секретов
  (`services/secrets.rs`) и привязаны к origin сервиса. Плагин видит только
  `tyco-secret:<id>`. Секреты MCP-серверов передаются в переменные окружения
  процесса из Rust и в webview не попадают.
- Плагины получают только функции из `PLUGIN_DESKTOP_FUNCTIONS`. Новые
  возможности добавляются туда явно.

## 11. Этапы

1. **Библиотека команд.** Вынести исполнители script/webhook и редактор полей
   в общие модули, ввести `CommandConfig`, `CommandMainAction`, миграцию,
   вкладку «Команды» и выбор команд во вкладке основных действий. Поведение
   меню действий для пользователя не меняется. Полезно само по себе, даже без
   голоса.
2. **Внешний вызов.** `RunCommand` / `ListCommands` в D-Bus, `tyco-ctl run` /
   `tyco-ctl commands`, поиск по id и названию. После этого LHC может
   вызывать команды.
3. **Оверлей команд с клавиатуры.** Хоткей выбора, список, поиск, `1`–`9`,
   ввод текста для команд со входом, подтверждение, история.
4. **Инструменты.** `ToolDefinition`, реестр, `registerTools`; `script` и
   `webhook` как встроенные инструменты; команды из плагинных инструментов.
5. **Распознавание.** `normalize`, `matcher`, `resolver` с тестами; без LLM.
6. **Голос в оверлее.** Голосовой хоткей, запись, «Проверить фразу», переход
   в чат.
7. **LLM как запасной вариант.** `IntentClassifier` на `lib/llm`, заполнение
   входа по `inputSchema`.
8. **Первые плагинные инструменты:** FastNote, поиск в интернете, AI-задача,
   перевод (см. §14).
9. **Агентный чат и MCP** (§12).
10. **Плагины внешних сервисов** по спросу.

## 12. Агентный чат и MCP (отложено)

Отдельный проект поверх реестра инструментов и библиотеки команд. Оверлей и
внешний вызов от него не зависят.

- **Вызов инструментов в `lib/llm`.** Передача списка команд с
  `availableIn.chat` как tools (`description` + `inputSchema`), разбор вызовов
  инструментов в ответе модели. Нужно проверить, что `@bozonx/ai-kit`
  поддерживает tool calling у используемых провайдеров, или расширить его.
- **Цикл агента в `lib/chat`.** Сообщение → ответ модели → вызовы инструментов
  → результаты → следующий шаг, с лимитом шагов и отменой.
- **UI в чате.** Вызов инструмента показывается в ленте (команда, вход,
  результат). Подтверждение по флагу `confirm` — прямо в чате.
- **MCP-клиент в Rust.** Новый сервис: запуск stdio-серверов, жизненный цикл,
  `tools/list` и `tools/call`, таймауты, логи. Webview обращается к нему через
  IPC, сам процессы не запускает. Remote MCP (HTTP) — через тот же сетевой
  прокси Rust.
- **Skills.** Инструкции для агента («как оформить заметку в Notion», «как
  разобрать письмо»): markdown с описанием, который подмешивается в контекст по
  запросу. Нужны только агенту, голосовому режиму — нет. Делать после того, как
  агент заработает.

## 13. Отложено и открытые вопросы

- **Команды внутри диктовки** («Тайко, …» в начале высказывания) — только с
  подтверждением и отдельной настройкой. Нужно проверить, как STT распознаёт
  имя, и использовать подсказку ключевых слов провайдера.
- **Jev** как реализация `IntentClassifier`, когда станет общедоступен.
- **Действия плагинов в меню и инструменты плагинов:** объединить
  регистрацию, чтобы плагин объявлял инструмент один раз, а `PluginMainAction`
  остался только для действий с собственным UI.
- **Группы или теги команд** в библиотеке и фильтр в оверлее — когда команд
  станет слишком много для поиска. Несколько отдельных меню или страниц с
  раскладкой клавиш не делаем: это роль Quick menu в LHC.
- **Ответ внешнему вызову с результатом:** сейчас `RunCommand` не ждёт
  выполнения. Если понадобится использовать вывод команды в скриптах —
  отдельный метод с ожиданием и таймаутом.
- **MCP-инструменты без настроек:** создавать команду для каждого вручную или
  разрешать агенту весь сервер целиком с подтверждением на каждый вызов.
- **Остановка записи по паузе** — подобрать длительность и решить, нужна ли
  она по умолчанию.

## 14. Предлагаемые инструменты

Порядок — по соотношению пользы и сложности. Многие внешние интеграции можно
получить через готовые MCP-серверы, а не писать плагином.

### Первая очередь (на базе того, что уже есть)

| Плагин / инструмент                 | Пример фразы                       | Что делает                                                                                   |
| ----------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------- |
| **FastNote** `fastNote.write`       | «запиши в блокнот купить молоко»   | Новая заметка или дописать в существующую; пресеты Obsidian, Logseq, папки по датам уже есть |
| **SearchInInternet** `search.web`   | «найди рецепт борща»               | Открыть поиск с аргументом; настройка — поисковик                                            |
| **AI-задача** `ai.task`             | «спроси нейросеть как …»           | Выполнить AI-задачу с аргументом или открыть чат                                             |
| **Перевод** `translation.translate` | «переведи на английский я опоздаю» | Перевести и вставить или скопировать результат                                               |
| **Вставка** `text.insert`           | «напиши …»                         | Вставить аргумент в активное окно (как быстрая диктовка)                                     |

### Вторая очередь (локальные, без внешних сервисов)

| Плагин / инструмент       | Пример фразы                                     | Что делает                                                                                               |
| ------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| **Напоминания и таймеры** | «напомни через двадцать минут проверить духовку» | Локальный таймер в Rust + системное уведомление (`desktop_notifications.rs`); вход — время + текст (LLM) |
| **Задачи в файле**        | «добавь задачу купить подарок»                   | Чек-лист в Markdown или `todo.txt`; работает с Obsidian/Logseq                                           |
| **Медиа**                 | «пауза», «следующий трек»                        | Linux — MPRIS через D-Bus; позже Windows/macOS                                                           |
| **Открыть**               | «открой браузер», «открой проект tyco»           | Запуск приложения, URL или папки из пользовательского списка                                             |
| **Буфер обмена**          | «скопируй …»                                     | Положить аргумент в буфер обмена                                                                         |

### Третья очередь (внешние сервисы: плагин или MCP)

| Интеграция             | Пример фразы                        | Заметки                                                     |
| ---------------------- | ----------------------------------- | ----------------------------------------------------------- |
| **Telegram**           | «отправь в телеграм …»              | Bot API, сообщение себе или в выбранный чат; простой плагин |
| **Notion**             | «добавь в Notion в покупки молоко»  | Есть MCP-сервер; страница и база — во входе, заполняет LLM  |
| **Todoist / TickTick** | «задача на завтра позвонить в банк» | MCP или REST-плагин; дата во входе                          |
| **Home Assistant**     | «включи свет в кабинете»            | REST API или MCP; простые сценарии хорошо ложатся на вебхук |
| **Календарь**          | «встреча завтра в десять с Петей»   | CalDAV или Google Calendar, чаще через MCP                  |
| **Email**              | «письмо Ивану …»                    | Черновик через `mailto:`; отправка — через MCP              |
| **Issue-трекеры**      | «создай задачу в GitHub …»          | GitHub, GitLab, Jira — есть MCP-серверы                     |

Внешние плагины ходят в сеть только через Rust-прокси (`lib/net`), ключи — в
