# Активация по хоткею: архитектура и оставшиеся задачи

Продолжение `dev_docs/quick-input-plan.md`. Тот план отвечал на вопрос
«как не терять символы»; этот — на вопрос «как окно вообще вызывается»
и «как это разложить, чтобы потом лёг Windows и macOS».

Шаг 2 исходного плана (поле быстрого ввода вне роутера) выполнен, см. раздел
«Что уже сделано». Остальное — ниже, в порядке, в котором имеет смысл делать.

## Принятые решения

### Одно окно, два профиля геометрии

Окно остаётся одно (`main`). Второе окно означало бы второй webview, а вместе
с ним вторую загрузку локальных моделей LLM и Whisper — они живут в webview
через transformers.js. Это дороже, чем неудобство общего окна.

Вместо двух окон — два профиля геометрии одной поверхности:

| Профиль | Режимы                              | Геометрия                                                               |
| ------- | ----------------------------------- | ----------------------------------------------------------------------- |
| `panel` | editor / write / voice / correction | layer-shell: anchor bottom, полупрозрачная полоса, без рамки и таскбара |
| `sheet` | history / config / chat             | та же поверхность, anchor снят (композитор центрует), размер больше     |

`gtk_layer_init_for_window` вызывается один раз в `setup()`, до первого показа.
Профиль применяется в момент активации, **до** `window.show()`, пока окно
скрыто. Фолбэк без layer-shell (GNOME/Mutter, X11) — `set_size` + `set_position`.

Следствие: `decorations: false` навсегда, значит для `sheet` придётся рисовать
свой заголовок и перетаскивание во фронтенде.

### Захват хоткея — платформенный, доставка сигнала — общая

Кросс-платформенного способа поймать глобальный хоткей, который работает
на Wayland, не существует: `tauri-plugin-global-shortcut` под капотом делает
X11-грабы, и в нативной Wayland-сессии нажатия до него не доходят. Поэтому
захват — трейт с несколькими реализациями, а всё, что после него, — общее.

Все пути сходятся в одну функцию `runtime::activate(app, Activation)`.

| Транспорт                                             | Когда                                                | Порядок задержки |
| ----------------------------------------------------- | ---------------------------------------------------- | ---------------- |
| Хоткей в самом процессе (portal / `global-shortcut`)  | основной путь                                        | ~0               |
| D-Bus `org.tyco.Interface.SwitchMode`                 | внешняя автоматизация, запас, если портал не завёлся | единицы мс       |
| Тонкий CLI `tyco-ctl` через локальный сокет           | кросс-платформенная автоматизация и бинды WM         | единицы мс       |
| Аргументы основного бинарника через `single-instance` | холодный старт                                       | сотни мс         |

Запуск второго экземпляра основного бинарника тянет за собой загрузку GTK
и webkit только ради того, чтобы передать аргументы и умереть. Эти сотни
миллисекунд ложатся **до** `show()` — ровно в тот промежуток, который в отчёте
измерялся как потерянные символы. Поэтому это путь холодного старта, а не
основной. `tyco-ctl` — отдельный крошечный крейт воркспейса, не линкующий
ни GTK, ни webkit. После достижения функционального паритета он заменяет
`run-ui.sh` в пользовательской документации и примерах биндов. До этого
`run-ui.sh` остаётся временным Linux-only способом вызвать D-Bus и не удаляется.

### Два класса вызова

- `keyboard-first` (editor, write, chat) — окно обязано забрать клавиатуру
  немедленно, `keyboard_mode = Exclusive`. Ради этого прогрев и постоянно
  смонтированное поле.
- `context-first` (correction, aiTasks, voice, select) — исходник берётся
  из выделения, пользователь не печатает. Панель показывается
  с `keyboard_mode = None`, не отбирая клавиатуру у исходного окна.

`START_MODES` сейчас этого не различает, и режима `correction` в нём нет
вовсе — есть только `CorrectionMenu`. Его нужно завести как полноценный режим
активации.

Деление на два класса переживает смену платформы: на Windows `context-first`
означает `WS_EX_NOACTIVATE`, на macOS — `NSPanel` с маской
`NonactivatingPanel`. Без этого показ панели отнимет фокус у исходного окна
и выделение, ради которого вызов и делался, перестанет быть актуальным.

### Биндинг предлагает приложение, владеет им система

Общее направление всех трёх ОС — право решать, какая комбинация кому
достанется, переезжает от приложения к системе. Отсюда два правила.

Первое: **настройки хоткеев живут в UI tyco всегда**, на всех платформах.
Пользователь не должен знать, что под капотом разные механизмы.

Второе: **у каждого действия есть дефолт, предложенный приложением**. Экран,
встречающий пустым полем «назначьте комбинацию», — главный источник того, что
функцией не пользуются. Экран, где всё уже работает и можно поменять, — нет.

Различается только то, что происходит после сохранения:

| Платформа              | Кто владеет биндингом | Что видит пользователь                               |
| ---------------------- | --------------------- | ---------------------------------------------------- |
| Wayland + портал       | композитор            | один диалог подтверждения при первом запуске         |
| Wayland без портала    | конфиг композитора    | строка для конфига и кнопка «скопировать»            |
| X11                    | tyco                  | ничего, работает сразу                               |
| Windows                | tyco                  | ничего; ошибка сразу, если комбинация занята         |
| macOS `keyboard-first` | tyco                  | ничего, работает сразу                               |
| macOS `context-first`  | система (Services)    | назначает в System Settings, tyco ведёт туда кнопкой |

### Разрешения: что чем оплачивается

Требования к правам создаёт не захват хоткея, а работа с чужим окном —
чтение выделения и вставка текста обратно. Это стоит держать раздельно,
потому что от этого зависит, что и когда просить у пользователя.

| Что                    | Linux                                                                            | Windows | macOS         |
| ---------------------- | -------------------------------------------------------------------------------- | ------- | ------------- |
| Захват хоткея          | ничего (портал / X11-граб / бинд в WM)                                           | ничего  | ничего        |
| Чтение выделения       | ничего (PRIMARY / xdotool)                                                       | ничего  | Accessibility |
| Вставка текста обратно | X11 — ничего; Wayland — доступ к `/dev/uinput` (группа `input` или udev-правило) | ничего  | Accessibility |

Группа `input` нужна ровно в одном месте — `ydotool` на Wayland (задача 9).
Для захвата хоткея она не требуется ни в одном из закладываемых вариантов.
Чтение `/dev/input/event*` напрямую дало бы захват без портала, но ценой прав
уровня кейлоггера, без раскладки (только scancode) и без возможности «съесть»
нажатие — этот путь в план не закладывается.

На macOS Accessibility придётся просить один раз, и просить осмысленно:
не на старте, а в момент первого вызова, которому оно нужно, с объяснением
зачем. Иначе запрос «доступ к управлению компьютером» от программы для ввода
текста выглядит непонятно и его отклоняют.

## ✅ Задача 1. Прогрев окна при старте

Реализация добавлена: три цикла через 400 мс, паузы 250 мс после
выполнения каждой операции в главном потоке. Прогрев не меняет `AppState`
и не отправляет события параметров. Исходная видимость восстанавливается;
активация или закрытие окна отменяют оставшиеся операции прогрева.
Отмена и последовательность покрыты Rust-тестами. Проверка потери символов
на реальном UI и сравнение прогрева с фокусом/без фокуса пока не проведены.

Исходное требование: в `services/runtime.rs`, в `setup()`,
отложенным потоком прогнать 3 цикла `show`/`hide` с паузой 250 мс, через 400 мс
после старта. Образец — `LAB_WARMUP` в `prototypes/tauri-quick/src/main.rs`.

Прогрев не должен трогать состояние: нынешний `show_main_window` пишет
`params.mode` и `is_window_shown` и шлёт `emit_params`. Нужен отдельный путь,
только `window.show()` / `window.hide()`, без `AppState` и без событий
во фронтенд.

Критерий: первый вызов по хоткею после запуска не теряет символов.

Открытый вопрос: достаточно ли одного маппинга без реального фокуса. Если да —
мигание при старте убирается. Проверяется в лаборатории до переноса.

## ✅ Задача 2. Единая точка активации

Реализация добавлена: D-Bus, трей и CLI используют `runtime::activate`.
Типы и разбор аргументов вынесены в `services/activation.rs`.
Поддерживаются позиционный режим, `--mode MODE` и `--mode=MODE`,
включая холодный старт. Неизвестные режимы отклоняются.
Существующие режимы дополнены `history` и `config` во фронтенде и Rust.

До layer-shell применяется геометрия обычного окна: `panel` — 800×600
(под текущую вёрстку), `sheet` — 1000×800, центрирование до показа.
Для контекстных вызовов отключена фокусируемость окна. Профили layer-shell
и их платформенные гарантии остаются в задаче 6.
Параметры и переданный D-Bus контекст публикуются после показа.
Ошибки активации возвращаются вызывающему транспорту.

Исходное описание: показ был размазан по трём местам: `runtime::show_main_window`, обработчик
`switch_mode` в `services/dbus.rs` (который поверх `show_main_window` ещё раз
делает `show` и `set_focus`), и трей. Свести в одну функцию:

```rust
pub struct Activation {
    pub mode: StartMode,
    pub intent: ActivationIntent,   // KeyboardFirst | ContextFirst
    pub source: ActivationSource,   // Hotkey | Dbus | Cli | Tray
}

pub fn activate(app: &AppHandle, activation: Activation) -> Result<(), AppError>
```

Порядок внутри важен: применить профиль геометрии, показать окно, и только
потом — всё остальное. Разобрать аргументы командной строки в обработчике
`single_instance` (`src-tauri/src/lib.rs:62`, сейчас там `_args`).

## ✅ Задача 3. `tyco-ctl` и захват контекста без задержки показа

Реализация добавлена: `tyco-ctl` — отдельный crate без Tauri/GTK/webkit,
который передаёт типизированный JSON-запрос через loopback-сокет. Основной
процесс снимает идентификатор активного окна до показа, читает PRIMARY в фоне
и публикует результат отдельным событием с защитой от устаревших захватов.
README переведён на `tyco-ctl`, временный `run-ui.sh` удалён; D-Bus сохранён.

`run-ui.sh` перед D-Bus вызовом запускает `xdotool getactivewindow` и `xclip`.
Два процесса на критическом пути, до того как окно начало показываться.

Добавить в workspace отдельный бинарный крейт `tyco-ctl`. Команда
`tyco-ctl activate <mode>` отправляет типизированный запрос уже запущенному
Tyco через локальный сокет и возвращает ненулевой код при неизвестном режиме,
недоступном сокете или отклонённой активации. CLI не захватывает контекст,
не запускает GTK/webkit и не содержит платформенной логики — она остаётся
в основном процессе.

Захват контекста надо разделить на дешёвый снимок и потенциально медленное
чтение. Идентификатор активного окна снимается в основном процессе
**до** `show()`/фокуса Tyco; после показа это уже может быть окно самого Tyco.
Чтение выделенного текста запускается параллельно и результат досылается
во фронтенд отдельным событием. Поэтому пользователь может печатать, пока
готовится контекст, но исходное окно определяется без гонки.

Трейт `ForegroundContext` предоставляет отдельно синхронный
`capture_source()` и асинхронный `capture_selection(source)`. На X11 источник
определяется через xdotool, выделение читается через xclip; на Wayland источник
недоступен, остаётся только PRIMARY через `wl-paste`.

На macOS у этого трейта есть бесплатная реализация для `context-first`:
если вызов пришёл через NSServices (см. задачу 4), система **сама передаёт
выделенный текст** в приложение, и Accessibility для чтения не нужен вовсе.
`capture_selection()` в этом случае возвращает уже переданный контекст.

После реализации и проверки паритета:

- заменить в README пример `./run-ui.sh editor` на
  `tyco-ctl activate editor`;
- перевести рекомендуемые бинды sway/Hyprland и других WM на `tyco-ctl`;
- удалить `run-ui.sh`; D-Bus оставить как Linux API совместимости и внешний
  транспорт, но не как основной пользовательский путь;
- добавить интеграционные тесты протокола сокета: каждый `StartMode`, ошибки
  разбора, отсутствие основного процесса и доставка запроса в `activate()`.

Критерий: тёплый вызов через `tyco-ctl` начинает показ окна без запуска
`xdotool`/`xclip` в CLI; исходное окно и выделение приходят асинхронно и не
перепутываются с окном Tyco.

## ✅ Задача 4. Провайдеры хоткеев

Linux-часть реализована. В Wayland-сессии создаётся долгоживущая сессия
`org.freedesktop.portal.GlobalShortcuts`, в X11 используется
`tauri-plugin-global-shortcut`; выбор делается по `XDG_SESSION_TYPE` в рантайме.
Неизвестный тип сессии оставляет внешние транспорты (`tyco-ctl` и D-Bus).
Привязки с дефолтами для всех режимов хранятся в `userConfig.hotkeys`, старые
конфиги дополняются миграцией. Провайдеры живут на уровне процесса и вызывают
общий `runtime::activate` с источником `Hotkey`.

Windows/macOS-провайдеры и NSServices остаются частью будущего
кросс-платформенного слоя из задачи 10: текущая конфигурация bundle проекта
собирает только Linux-цели.

Трейт `HotkeyProvider`, реализация выбирается в рантайме по сессии
(`XDG_SESSION_TYPE`), а не по `cfg!`. Все реализации работают при скрытом
или свёрнутом в трей окне: подписка живёт в процессе, а не в окне. Единственный
путь, требующий запуска процесса, — холодный старт через `single-instance`.

1. **XDG portal `org.freedesktop.portal.GlobalShortcuts`** — Linux Wayland.
   KDE Plasma 6 реализует, GNOME — начиная с 48. `BindShortcuts` передаёт id
   действия, человекочитаемое описание и `preferred_trigger`; портал один раз
   показывает диалог подтверждения, после чего биндинг виден и редактируем
   в системных настройках. То есть системные настройки — место, где хоткей
   потом меняется, а не где он изначально задаётся.
   **Проверить до того, как закладываться**: требуется `.desktop` с app id,
   совпадающим с идентификатором приложения, и для не-flatpak сборки это
   работает не везде.
2. **`tauri-plugin-global-shortcut`** — X11, Windows, macOS. Владение
   комбинацией — «кто первый успел». И `XGrabKey` (`BadAccess`),
   и `RegisterHotKey` (ошибка возврата) позволяют узнать, что комбинация
   занята: это надо показывать в момент назначения, а не молча не работать.
   На macOS надёжного детекта конфликта нет.
3. **NSServices** — macOS, только класс `context-first`. Сервис объявляется
   в `Info.plist`, попадает в System Settings → Keyboard → Shortcuts → Services
   и в контекстное меню любого приложения, а выделенный текст система передаёт
   сама. Для `keyboard-first` не годится: там нет исходного текста.
4. **Внешний триггер** — уже существующий D-Bus плюс `tyco-ctl`, остаётся
   всегда. Он же штатный путь для sway/Hyprland, где портала нет и бинд
   в конфиге композитора — ожидаемое поведение, а не костыль.

Привязки хранятся в `userConfig`. Пока провайдер 1 не проверен — рабочим
остаётся D-Bus плюс бинд в настройках WM.

## ✅ Задача 5. UI настройки хоткеев

Реализован отдельный экран настроек со списком всех режимов, общим
рекордером и сбросом к предзаполненным значениям. Нормализация комбинаций и
типы результата вынесены в `@tyco/shared`. X11 применяет изменение сразу и
сообщает о конфликте; portal сообщает о системном подтверждении и применяет
изменённые preferred triggers после перезапуска; для внешнего провайдера UI
генерирует готовую строку sway/Hyprland и позволяет скопировать её.

Следствие раздела «Биндинг предлагает приложение, владеет им система».
Экран настроек со списком действий активации (по одному на `StartMode`),
у каждого — поле-рекордер комбинации и предзаполненный дефолт.

- Рекордер общий для всех платформ, нормализованное представление комбинации
  живёт в `@tyco/shared`.
- Результат назначения приходит от `HotkeyProvider` и различается: «готово»,
  «занято другим приложением», «подтвердите в системном диалоге»,
  «скопируйте строку в конфиг композитора».
- Для последнего случая — готовая строка под текущий композитор и кнопка
  копирования; для macOS `context-first` — кнопка, открывающая нужный раздел
  System Settings.
- Все подписи — через i18n, `pnpm check:i18n`.

## ✅ Задача 6. layer-shell и профили геометрии

Реализация добавлена: окно настроено без рамки и панели задач, GTK layer-shell
инициализируется до первого показа, а `activate()` применяет профиль и режим
клавиатуры до `show()`. Если layer-shell не поддерживается композитором,
остаётся обычное центрируемое окно.

Шаг 3 исходного плана, расширенный до двух профилей.

- В `tauri.conf.json` для окна `main`: `transparent: true`,
  `decorations: false`, `skipTaskbar: true`.
- Новый модуль по образцу `prototypes/tauri-quick/src/layer.rs`: шесть функций
  системной `libgtk-layer-shell` через `extern "C"`, без отдельного крейта.
  Линковка — строкой в `build.rs`. Сборочная зависимость `gtk-layer-shell`
  добавляется в требования в README.
- Вызов из `setup()` до первого показа окна. Профиль (`panel` / `sheet`)
  применяется в `activate()` до `show()`.
- Клавиатура переключается между `None` и `Exclusive` по `intent` вызова.
- Откат: `gtk_layer_is_supported()` возвращает false на GNOME — там обычное
  окно. Молчаливая деградация, не ошибка запуска.

После этого шага activation token не нужен — но только на композиторах
с layer-shell.

## Задача 7. UI профиля `sheet`

Следствие `decorations: false`: для истории, настроек и чата нужны свой
заголовок, кнопка закрытия и область перетаскивания (`data-tauri-drag-region`).
Плюс компактная вёрстка `panel`: сейчас `QuickPanel` рассчитан на окно 800×600,
а не на полосу внизу экрана.

## Задача 8. Повторный замер на настоящем UI

Шаг 4 исходного плана. Лаборатория гоняла голый HTML; boot Vue, pinia и i18n
добавят своё время.

Прокинуть в приложение метки t0-t5 и команды `show`/`result`
из `prototypes/tauri-quick/src/metrics.rs` и `src/ipc.rs`, под флагом сборки
или переменной окружения. Бенч `prototypes/tauri-quick/examples/bench.rs`
переиспользуется как есть.

Критерий: 20 попыток подряд, задержка первой клавиши 100 мс, пауза между
вызовами 10 с — ноль потерянных символов. Замер повторить на release-сборке:
все цифры отчёта получены в debug.

## Задача 9. Вставка обратно в исходное окно

Шаг 5 исходного плана. `src-tauri/src/commands/window.rs:39` по умолчанию
использует `xdotool`, который работает только на X11. Нужен `ydotool`
(с правами на uinput) либо `zwp_virtual_keyboard`. Это единственное место
во всём плане, требующее группы `input` / udev-правила, — и требование надо
проверять лениво, в момент первой вставки, с понятной подсказкой, а не
отказом запускаться.

Там же два `thread::sleep(300)` (строки 52 и 68) — гонка того же класса,
что чинилась в задачах 1 и 3, только в обратную сторону: правильнее ждать
события фокуса, а не спать.

Приятное следствие задачи 6: layer-поверхность не становится «активным окном»
в понимании композитора, поэтому исходный toplevel остаётся активным
и переактивировать его по `window_id` не нужно.

## Задача 10. Слой `platform/`

Собрать платформенные реализации в `src-tauri/src/platform/{linux,windows,macos}`
за четырьмя трейтами. Выбор — в `setup()`. Фронтенд о платформе не знает
ничего: он получает `mode` и `intent`.

| Трейт                                         | Linux                    | Windows                     | macOS                                                |
| --------------------------------------------- | ------------------------ | --------------------------- | ---------------------------------------------------- |
| `PanelSurface` (геометрия, захват клавиатуры) | gtk-layer-shell / фолбэк | `WS_EX_NOACTIVATE`, topmost | `tauri-nspanel`, `NonactivatingPanel`                |
| `HotkeyProvider`                              | portal / global-shortcut | `RegisterHotKey`            | `RegisterEventHotKey`; `context-first` — NSServices  |
| `ForegroundContext`                           | xdotool / wl-paste       | `GetForegroundWindow`       | NSServices отдаёт текст сам, иначе Accessibility API |
| `TextInjector`                                | ydotool / xdotool        | `SendInput`                 | `CGEvent` (Accessibility)                            |

Accessibility на macOS относится к `ForegroundContext` и `TextInjector`,
а не к `HotkeyProvider`: сам по себе хоткей разрешений не требует.

Известные ограничения, которые не надо считать багами:

- Windows: хоткей не сработает и вставка не пройдёт, когда активно окно
  приложения с правами администратора (UIPI), если tyco не elevated.
  Часть комбинаций (`Win+L` и прочие) система держит за собой.
- macOS: надёжного детекта конфликта комбинаций нет, назначение молча
  не сработает — единственная платформа, где нельзя показать ошибку сразу.
