# План: переносимая папка пользовательских данных

Статус: черновик плана, к реализации не приступали.
Дата: 2026-11-01
Связанные документы: `dev_docs/config-storage.md`, `dev_docs/cross-platform.md`,
`dev_docs/desktop-api.md`, `dev_docs/state-management.md`.

## 1. Цель

Пользователь хранит всё, что он создал и настроил, в одной папке и
синхронизирует её любым средством (Syncthing, Nextcloud, Dropbox, общий диск).
На другом компьютере TyCo, подключённый к той же папке, работает с теми же
настройками, командами, профилями, чатами и историей.

Всё, что относится к конкретной машине (логи, кэш, данные webview, ключи,
горячие клавиши, системные пути), остаётся в стандартных папках ОС и не
синхронизируется.

Не цель: собственный сервер синхронизации, синхронизация ключей, слияние двух
независимых наборов данных при подключении папки.

## 2. Принципы

- **Одна папка пользователя, остальное — по правилам ОС.** Пользовательские
  данные не разносятся по XDG/AppData, а лежат одной кучей в `user_dir`.
  Системные файлы остаются в `config_dir`, `state_dir`, `cache_dir`, `log_dir`.
- **У каждого поля и файла одно место.** Никаких «локальных переопределений
  поверх общего конфига»: поле принадлежит либо пользователю, либо устройству.
- **В папке пользователя только данные.** Резервные и битые копии, файлы
  транзакций, индексы-кэши и блокировки живут в `state_dir`.
- **Формат рассчитан на запись с нескольких устройств.** Общих файлов, которые
  дописывают все устройства, нет: журналы — по файлу на устройство, сущности —
  по файлу на сущность.
- **IPC и модель настроек в webview не меняются.** Webview по-прежнему видит
  один `UserConfig`; делит его на части и собирает обратно только backend.

## 3. Целевая раскладка

```
config_dir (~/.config/com.tyco.app, %APPDATA%\com.tyco.app)
  device.json          настройки устройства, deviceId, userDataPath
  secrets.json         id и origin ключей этого устройства

data_dir = user_dir по умолчанию (~/.local/share/com.tyco.app, %APPDATA%\com.tyco.app)
  tyco-user.json       маркер папки: версия формата папки
  config.json          настройки пользователя
  history/editor/<deviceId>.jsonl
  chats/<id>.json
  chats/images/
  plugins/<key>.json
  ai-vault/            профили (если aiVault.path не задан)

state_dir (~/.local/state/com.tyco.app, %LOCALAPPDATA%\com.tyco.app)
  logs/
  webview/             теперь и на Linux (сейчас лежит в data_dir)
  index/chats.json     производный индекс чатов, пересобирается
  index/ai-vault/...   индексы чатов профилей
  recovery/            .broken-*, .repaired-*, копии перед salvage JSONL
  transactions/        chat-transaction.pending и подобные
  plugins/<key>.previous

cache_dir             без изменений
```

Когда пользователь выбирает свою папку, `user_dir` указывает на неё, а
`data_dir` остаётся пустым (или его можно не создавать). По умолчанию
`user_dir == data_dir`, поэтому без выбора папки раскладка остаётся привычной
для ОС: на Windows пользовательские данные попадают в Roaming `%APPDATA%`, как
и положено.

## 4. Этап 1 — разделение данных, новые пути, формат и UI

Цель этапа: выполнить все структурные преобразования. После него папку уже
можно переносить и подключать на другой машине, а формат не порождает
конфликтов, даже если оба устройства работают одновременно. На этапе 2
останется только реакция на изменения извне.

### 4.1. Пути (`src-tauri/src/services/storage`)

1. В `AppPaths` добавить `user_dir: PathBuf`. Его источник —
   `device.json.userDataPath`; если поле пустое, это `data_dir`. Dev-режим
   (`TYCO_DEV_HOME`) кладёт `user_dir` внутрь dev-home.
2. Ввести функции `user_dir(app)` и `user_sub_dir(app, sub)` вместо
   `app_data_dir` / `app_data_sub_dir` для пользовательских файлов. После
   переноса на `data_dir` не должно ссылаться ничего, кроме вычисления
   `user_dir` по умолчанию.
3. Перевести на `user_dir`:
   - `settings/persist.rs` — `config.json` (сейчас `app_config_dir`);
   - `editor_history.rs` — история редактора;
   - `chat_history.rs` — `chats/`;
   - `ai_vault/location.rs`, `ai_vault.rs`, `history_store.rs` — `ai-vault/`
     по умолчанию;
   - `lib.rs:129` — `plugins/`.
4. Перенести webview на Linux из `data_dir` в `state_dir`
   (`AppPaths::webview_dir`), как уже сделано на Windows. Тогда в `data_dir`
   не останется ничего системного.
5. Перенести вспомогательные файлы в `state_dir`:
   - копии `.broken-*`, `.repaired-*` и копии перед salvage (`atomic_file.rs`,
     `settings/persist.rs`) — в `state_dir/recovery/<относительный путь>`;
   - `chat-transaction.pending` — в `state_dir/transactions/`;
   - `plugins/<key>.previous` — в `state_dir/plugins/`.
     Временные файлы атомарной записи остаются рядом с целевым файлом (иначе
     rename не будет атомарным). Их имя получает узнаваемый префикс
     `.tyco-tmp-`, чтобы их можно было исключить из синхронизации.
6. `secrets.json` остаётся в `config_dir` (`secrets.rs`): это метаданные
   ключей именно этого устройства.
7. `StorageInfo` / `StorageKind` получают вид `User`. `get_storage_info`
   показывает папку пользователя отдельно от системных папок; после изменения
   выполнить `pnpm generate:desktop`.

### 4.2. Разделение конфига

1. В `packages/shared/src/user-config-schema.json` добавить ключевое слово
   `"x-scope": "device"`. Поле или секция без него — пользовательские. Оба
   адаптера схемы (TS и Rust) учат это ключевое слово; общие fixtures в
   `packages/shared/fixtures` проверяют, что runtime'ы делят конфиг одинаково.
2. Начальный список полей устройства:
   - `hotkeys` — целиком;
   - горячие клавиши страниц лаунчера: `launcherPages[].hotkey` переносится в
     `hotkeys.launcherPages.<pageId>`, потому что поле устройства не может
     жить внутри пользовательской сущности. До релиза это допустимо без
     миграции (см. `config-storage.md`: формат 1 выходит с первым релизом);
   - `windowInsertion` — целиком;
   - `externalAccess` — разрешения внешнего доступа задаются на каждой
     машине отдельно (`isAvailableExternally` у команд остаётся
     пользовательским);
   - `appearance.uiScalePercent` — зависит от монитора;
   - `aiVault.path` — внешний абсолютный путь имеет смысл только на одной
     машине; пустое значение по-прежнему означает `user_dir/ai-vault`;
   - `stt.providers.sherpaOnnx` — адрес локального сервера.
     Список перед реализацией сверяется со схемой полностью. Открытые вопросы
     по нему — в разделе 6.
3. Backend:
   - загрузка: прочитать `config.json` и `device.json`, нормализовать каждый
     по своей части схемы, собрать единый `UserConfig`;
   - сохранение: разделить по `x-scope`, записать каждую изменившуюся часть
     атомарно. Существующее трёхстороннее слияние окон работает над
     объединённым конфигом, как сейчас;
   - оба файла несут `configVersion`; правило `configIsNewer` действует для
     каждого из них.
4. `device.json` хранит также служебные поля устройства, которые не входят в
   `UserConfig` и не видны в настройках: `deviceId` (UUID, создаётся при
   первом запуске) и `userDataPath`.
5. Восстановление (repair) и карантин битых файлов работают для обоих файлов
   одинаково, копии пишутся в `state_dir/recovery`.

### 4.3. Формат файлов, устойчивый к синхронизации

1. **История редактора.** `editor-history.jsonl` заменяется на
   `history/editor/<deviceId>.jsonl`.
   - Устройство пишет только в свой файл, а читает все файлы папки и
     объединяет записи по времени.
   - Очистка по `retentionDays` и `maxItems` переписывает только свой файл,
     а при чтении фильтр применяется ко всем файлам.
   - Явная очистка истории дописывает в свой файл запись
     `{"type":"clear","before":<ms>}`; читатель берёт максимальный `before`
     по всем файлам. Чужие файлы не удаляются и не переписываются.
2. **Чаты.** `chats/index.json` перестаёт быть данными:
   - источник правды — `chats/<id>.json` (поля `createdAt`, `updatedAt`,
     `lastMessageAt` и заголовок уже есть в файле чата или добавляются в него);
   - индекс хранится в `state_dir/index/chats.json` и пересобирается при
     старте, если его нет или список файлов и их mtime не совпадают;
   - транзакция «чат + индекс» упрощается: атомарно пишется файл чата, а
     индекс обновляется после записи и может отставать;
   - то же самое делается для чатов профилей в `ai-vault`.
3. **Картинки чатов** — один файл на картинку, имя по содержимому, как сейчас
   (`chat-images.md`). Чат, чья картинка ещё не доехала, показывает
   заглушку, а не ошибку.
4. **Маркер `tyco-user.json`**: `{ "formatVersion": 1 }`. Если версия формата
   новее, чем знает сборка, папка открывается только на чтение — так же, как
   работает `configIsNewer`.
5. **Пути внутри `user_dir`** хранятся относительными. Абсолютные пути, которые
   остались в пользовательских полях (например, `workingDirectory` у
   скриптовых команд), не переписываются; если такой путь не существует,
   выдаётся понятная ошибка.

### 4.4. Ключи

- Значения ключей и `secrets.json` остаются на устройстве.
- Если конфиг ссылается на ключ, которого на этом устройстве нет, это
  отдельное состояние «ключ не задан на этом устройстве», а не ошибка. UI
  провайдеров, переводчиков, STT и webhook показывает его и предлагает ввести
  ключ.
- Сборка неиспользуемых webhook-секретов при старте учитывает только секреты
  этого устройства (так и работает сейчас) и ничего не удаляет из
  `config.json` из-за отсутствующего ключа.

### 4.5. Смена папки (backend)

Команда `relocate_user_data` по образцу `relocate_ai_vault`
(`config-storage.md`, раздел «Lifetime and locations»):

- **пустая папка** → перенос: известные записи `user_dir` по одной
  переименовываются или копируются, проверяются и удаляются; при сбое
  выполняется откат;
- **папка с `tyco-user.json`** → подключение существующих данных без
  переноса. Текущие данные остаются на старом месте нетронутыми, и UI сообщает,
  где они;
- **папка с посторонними файлами** → отказ, UI предлагает подпапку `TyCo`;
- **«вернуть в стандартное место»** — перенос в `data_dir` по тем же правилам.

Переносятся только известные записи (`config.json`, `history/`, `chats/`,
`plugins/`, `ai-vault/`, если vault лежит внутри, и `tyco-user.json`).
После успешной смены `userDataPath` записывается в `device.json`, и
приложение перезапускается. Горячее переключение хранилищ не делаем: так
надёжнее, а смена папки — редкая операция. Блокировки vault, настроек и истории
берутся в том же порядке, что и в `relocate_ai_vault`.

`tyco-ctl` и D-Bus эту команду не получают.

### 4.6. UI

- В настройках, рядом с `StorageLocations.vue`, появляется блок «Папка данных»:
  текущий путь, кнопки «Перенести в папку…», «Подключить существующую…»,
  «Вернуть в стандартное место», «Открыть».
- Подсказка объясняет, что синхронизируется (настройки, команды, профили,
  чаты, история) и что остаётся на устройстве (горячие клавиши, вставка в окна,
  ключи, масштаб, логи).
- Поля устройства в формах настроек помечаются значком или подписью «только
  на этом устройстве».
- Диалог подтверждения перед перезапуском и сообщение о результате, включая
  частичный откат.
- Состояние «ключ не задан на этом устройстве» (см. 4.4).
- Все новые строки добавляются во все локали (`pnpm check:i18n`).

Логика живёт в модели `apps/desktop-ui/src/lib/storage/` с внедрёнными
зависимостями и unit-тестами; store только подключает её.

### 4.7. Тесты и документы этапа 1

- Rust unit-тесты: разрешение `user_dir`, разделение и сборка конфига,
  история из нескольких файлов устройств и запись `clear`, пересборка индекса
  чатов, `relocate_user_data` (перенос, подключение, отказ, откат).
- Сценарий «два устройства»: два `deviceId` над одним временным `user_dir`
  пишут поочерёдно — файлы не пересекаются.
- Общие fixtures разделения конфига для TS и Rust.
- Обновить `config-storage.md` (таблица путей, разделение конфига),
  `cross-platform.md` (webview на Linux), `desktop-api.md` (новая команда).

**Критерий готовности этапа 1:** папку пользователя можно перенести, на второй
машине подключить и получить те же данные. Ни один файл в папке не пишется
двумя устройствами, а в папке нет ничего, кроме данных и `.tyco-tmp-*`
(во время записи).

## 5. Этап 2 — поддержка программ синхронизации

Цель этапа: приложение корректно реагирует на изменения, которые синхронизация
принесла извне, пока оно запущено, и разбирает конфликтные копии.

### 5.1. Слежение за папкой

- Watcher (`notify`) на `user_dir` с debounce. События от собственных записей
  отфильтровываются (по хэшу содержимого последней записи).
- Изменился `config.json` → слияние (5.2), затем событие в webview: настройки
  обновляются без перезапуска через существующую публикацию настроек.
- Изменились `chats/*.json` → инвалидация индекса и событие обновления списка
  чатов; открытый чат перечитывается, если его не редактируют.
- Изменились `history/editor/*.jsonl` чужих устройств → событие обновления
  истории.
- Изменился `ai-vault/` → обновление профилей.

### 5.2. Слияние конфига

- В `state_dir/config.base.json` хранится последняя версия `config.json`,
  которую это устройство прочитало или записало.
- Перед каждым сохранением файл на диске сравнивается с базой. Если они
  различаются, выполняется трёхстороннее `merge(base, local, disk)`
  существующим механизмом слияния окон, затем запись и обновление базы.
- При внешнем изменении выполняется то же слияние с текущим состоянием в памяти.
- Если одно и то же поле изменили по-разному на двух машинах: побеждает
  изменение, которое на этом устройстве только что сделал пользователь;
  проигравшая версия файла сохраняется в `state_dir/recovery/`, а UI
  показывает уведомление. Механизм окон при этом по-прежнему отклоняет
  конфликт явно — правило касается только внешних изменений.

### 5.3. Конфликтные копии синхронизаторов

Распознавать и разбирать копии:

- Syncthing: `*.sync-conflict-<date>-<time>-<device>.*`;
- Dropbox: `* (… conflicted copy …).*`;
- Nextcloud/ownCloud: `* (conflicted copy …).*` и `*_conflict-*`.

Разбор:

- `config.json` → трёхстороннее слияние с базой, как в 5.2;
- `chats/<id>.json` → слияние сообщений по id, метаданные берутся из версии с
  большим `updatedAt`;
- `history/editor/*.jsonl` → не должно возникать (каждый файл пишет одно
  устройство), но на всякий случай строки объединяются без дублей;
- `plugins/<key>.json` → побеждает более новая версия, проигравшая уходит в
  `recovery/`.

После разбора конфликтная копия удаляется. То, что не удалось разобрать,
остаётся на месте, а пользователь получает уведомление.

### 5.4. Прочее

- Удаление чата на одном устройстве и одновременная правка его на другом:
  файл воскресает, это допустимо. Отдельные tombstone для чатов не делаем.
- Неполная синхронизация (чат пришёл, картинка ещё нет) → заглушка и
  повторное чтение при событии watcher.
- По желанию пользователя (кнопка в блоке «Папка данных») создаётся
  `.stignore` с `.tyco-tmp-*`. Это удобство для Syncthing; корректность на
  нём не держится.
- Опционально: `--user-dir` / `TYCO_USER_DIR` для запуска с другой папкой
  без изменения `device.json`.

### 5.5. Тесты и документы этапа 2

- Unit-тесты слияния с базой: непересекающиеся правки, одинаковое поле,
  отсутствие базы.
- Разбор конфликтных копий каждого синхронизатора на fixtures имён и
  содержимого.
- Integration-тест watcher (`integration_*`): внешняя запись приводит к
  событию и к обновлённому состоянию, а собственная запись событий не порождает.
- Документ для пользователей: как настроить Syncthing и что не синхронизируется.

**Критерий готовности этапа 2:** два одновременно запущенных экземпляра на
общей синхронизируемой папке видят изменения друг друга без перезапуска,
непересекающиеся правки настроек не теряются, а конфликтные копии разбираются
автоматически.

## 6. Открытые вопросы

- Состав полей устройства: нужны ли переносимые горячие клавиши по умолчанию
  с настройкой для каждой платформы вместо полностью локальных `hotkeys`?
- Настройки плагинов (`plugins.<id>.settings`) непрозрачны для ядра. Нужно ли
  SDK, чтобы плагин мог объявить поле устройства (например, путь к файлу
  заметок)?
- `workingDirectory` скриптовых команд: разрешить путь относительно `user_dir`?
- Экспорт и импорт ключей с паролем — отдельная задача после этапа 2.
- Portable-режим на Windows (маркер рядом с exe задаёт `user_dir`) почти
  бесплатен после этапа 1. Делать ли его в этапе 2?
