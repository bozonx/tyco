внешние процессы и не заменяет межмашинный CAS; полностью одновременные
внешние записи остаются ограничением файловой синхронизации.

## 1. Цель и рамки

Всё, что пользователь создал и настроил, лежит в обычных файлах, которые
удобно синхронизировать большинством программ синхронизации. TyCo на другом
компьютере, подключённый к тем же папкам, работает с теми же настройками,
командами, профилями, чатами и историей. То, что относится к машине (ключи,
горячие клавиши, пути, логи, кэш, webview), остаётся в папках ОС.

Ориентир — Obsidian: хранилище — просто папка с файлами, без базы данных;
состояние устройства отдельно. **TyCo ничего не знает о внешних программах**
(синхронизаторах, git и т. п.): не интегрируется с ними и не даёт под них
настроек. Мы только даём структуру файлов, удобную для синхронизации:

- файл на сущность, журнал на устройство, генерируемые id, детерминированный
  маркер основного хранилища — одновременные правки с двух машин редко
  попадают в один файл;
- служебные файлы не лежат в синхронизируемых папках; единственное
  исключение — временный файл атомарной записи `.tyco-tmp-*` рядом с
  целевым (иначе rename не атомарен), он живёт доли секунды, и его можно
  исключить в синхронизаторе;
- файл, который TyCo не узнаёт по имени, не читается и не удаляется;
- запись поверх файла, изменённого вне TyCo, не затирает его молча.

Максимально надёжная синхронизация (ревизии, CAS, удаления) — задача
будущего TyCo Cloud (раздел 7).

Не цель: журнал изменений или БД на клиенте, синхронизация ключей, слияние
двух независимых наборов данных при первом подключении, второй экземпляр
приложения, связи между хранилищами.

## 2. Принципы

- **Папка данных и подключённые хранилища доверенные, как домашний
  каталог.** Кто пишет в них, тот меняет команды, плагины и профили на всех
  машинах. UI предупреждает, если папка доступна на запись другим (Linux;
  на Windows ACL не проверяются сознательно).
- **У каждого поля и файла одно место.** Поле принадлежит либо пользователю
  (`config.json`), либо устройству (`device.json`). Значение устройства для
  общей сущности хранится у устройства по id сущности (пути FastNote,
  значения переменных, пути внешних проектов, список подключённых
  хранилищ).
- **Ссылки идут только от устройства к общим данным.**
- **Отсутствие — не удаление.** Ссылка на общую сущность забывается, только
  когда сущность удалена на этом устройстве; ссылка на отсутствующее
  скрывается.
- **Id сущностей генерируются и не меняются.** Две машины не создадут одну
  сущность с одним id; имя для UI — отдельное поле.
- **В синхронизируемых папках только данные.** Резервные копии, транзакции,
  индексы, блокировки — в `state_dir`. Исключение — `.tyco-tmp-*` (раздел 1).
- **Ничего не создаётся молча на месте пропавшего.** Не найденная выбранная
  папка — «не подключено».
- **Синхронизируемые корни не вложены друг в друга.**
- **Хранилища изолированы.** Профиль одного хранилища не видит и не
  трогает профили, проекты и файлы другого.
- **Без настройки всё работает.** Одна папка данных, хранилище внутри.

## 3. Модель

| Что                             | Где                                          | Синхронизирует         |
| ------------------------------- | -------------------------------------------- | ---------------------- |
| Папка устройства (`device_dir`) | папки ОС                                     | никто                  |
| Состояние (`state_dir`)         | папки ОС                                     | никто                  |
| Папка данных (`user_dir`)       | по умолчанию папки ОС, можно выбрать         | пользователь           |
| Основное хранилище              | всегда `user_dir/ai-vault`, не настраивается | вместе с папкой данных |
| Подключённые хранилища          | любые папки, список на устройстве            | пользователь, отдельно |
| Внешний проект                  | любая папка, путь на устройстве              | пользователь, отдельно |

**Хранилище (vault)** — переносимый корень: профили, проекты, чаты
профилей, память. Чаты профилей хранятся в хранилище профиля, в том числе
рабочего.

**Папка данных и клиент** — настройки, провайдеры, команды, инструменты,
плагины, общие чаты, история редактора. Всё это под управлением клиента:
хранилище не содержит своих провайдеров, команд и плагинов. Профиль
использует то, что есть в клиенте; если нужного нет, работает с тем, что
есть (модель по умолчанию, недоступные команды не предлагаются).

Сценарии:

1. **Ничего не настроено.** Одна папка данных, хранилище внутри.
2. **Всё синхронизируется.** Папка данных выбрана в синхронизируемом
   месте; путь на машинах может отличаться (путь — поле устройства).
3. **Личное и рабочее.** Личные профили — в основном хранилище; рабочие —
   в подключённом хранилище, которое синхронизируется отдельно и подключено
   только на нужных машинах.
4. **Проект с кодом.** Внешний проект: описание в хранилище, папка на
   каждой машине своя или не указана («не подключён на этом устройстве»).

## 4. Историческое состояние до выполнения плана

### 4.1. Раскладка

```
device_dir (Linux: ~/.config/com.tyco.app;
            Windows: %LOCALAPPDATA%\com.tyco.app\device)
  device.json          поля x-scope: device, deviceId, machineId,
                       userDataPath, pluginPaths, pluginCommandPaths,
                       aiProjectPaths.<vaultId>.<projectId>,
                       aiVault.path (убирается в 5.2)
  secrets.json         id и origin ключей этого устройства

user_dir (по умолчанию ~/.local/share/com.tyco.app, %APPDATA%\com.tyco.app)
  tyco-user.json       маркер: formatVersion, dataId
  config.json          настройки пользователя
  history/editor/<deviceId>.jsonl
  chats/<id>.json, chats/images/
  plugins/<key>.json, plugins/<key>.previous
  ai-vault/            основное хранилище
    tyco-vault.json    маркер: formatVersion, vaultId (= data-<dataId>)
    profiles/<id>/     profile.json, SOUL.md, chats/, memory/, workspace/
    projects/<id>/     project.json и файлы внутреннего проекта

state_dir (~/.local/state/com.tyco.app, %LOCALAPPDATA%\com.tyco.app)
  logs/, webview/, config.base.json, history/editor/local.jsonl,
  index/ (индексы чатов по хэшу пути хранилища, orphan-images.json),
  recovery/, transactions/
```

На Windows `device_dir` — подпапка `device\` в Local: Roaming уезжает на
другие машины вместе с `deviceId`.

### 4.2. Реализовано

- **Подключение папки данных.** Маркер `tyco-user.json`; выбранная папка без
  маркера или пропавшая — «не подключена» с действиями «Повторить» /
  «Подключить другую» / «Использовать стандартную»; маркер новее сборки —
  только чтение. `relocate_user_data` (`move`, `connect`, `resetToDefault`,
  `useDefault`), сервис `data_root_relocation.rs`. Смена — через перезапуск.
- **Конфиг.** Разделение по `x-scope: device`; `config.json` сохраняется
  трёхсторонним слиянием с `config.base.json`, проигравшая версия — в
  `recovery/`. Внешняя правка применяется без перезапуска.
- **Устройство.** Смена `machineId` даёт новый `deviceId`. Ключи: id общий,
  значение и origin — на устройстве. Пути FastNote на устройстве.
- **Форматы.** История — журнал на устройство; чаты — файл на чат, индекс в
  `state_dir`; картинки без ссылок удаляются через 7 дней после
  обнаружения. Читатели принимают только имена своего формата; остальные
  файлы, в том числе конфликтные копии синхронизаторов, пропускаются
  (`storage/user_files.rs`). Атомарная запись с повтором rename (Windows).
- **Переносимость команд.** Переменные `{{var:NAME}}`, поле `platforms`.
- **Хранилище.** Маркер `tyco-vault.json`; маркер основного хранилища
  детерминирован. Внешний путь хранилища — поле устройства `aiVault.path`
  с переносом (`ai_vault/location.rs`, `relocation.rs`) — **убирается в
  5.2**. Внешние проекты: описание в хранилище, путь в `device.json`. Запись
  памяти поверх внешней правки отклоняется (`MemoryReadVersions`). Ссылки
  на отсутствующие профили скрываются.
- **Watcher** (`storage/watcher.rs`): `notify` + опрос, SHA-256, фильтр
  своих записей, шина `StorageEvent`; обходит только области данных TyCo.
- Руководство пользователя `docs/data-folder.md`.

## 5. Выполненные требования

### 5.1. Генерируемые id профилей и проектов

**Проблема.** Сейчас id — slug из имени (`createVaultId`,
`lib/ai-profiles/vault-id.ts`) или папка, вписанная пользователем
(`vault-folder-field.ts`); случайный суффикс — только для имён без
латинского написания. Две машины до синхронизации создают «Assistant» →
обе пишут в `profiles/assistant/`, синхронизатор смешивает файлы двух
разных профилей.

**Решение.** Id нового профиля и проекта всегда `profile-<8 hex>` /
`project-<8 hex>` (как сейчас для нелатинских имён), пользователь его не
вводит и не меняет. Поле папки из форм убирается; `slugifyVaultName`,
`createVaultFolderField` удаляются, если больше не нужны. Существующие id
читаются как есть. Backend проверяет формат id только на допустимые символы
(`validate_id`), не на шаблон. Если папка с таким id уже есть, id
генерируется заново (создание не перезаписывает существующую папку).

**Тесты:** два создания с одинаковым именем — разные id; совпадение
сгенерированного id с существующей папкой — новый id; форма без поля
папки; старые id читаются.

### 5.2. Основное хранилище всегда в папке данных

**Решение.** Основное хранилище — всегда `user_dir/ai-vault`, переносится
только вместе с папкой данных. Кому нужно внешнее — подключает его
(5.4) и создаёт профили там; основное может оставаться пустым.

- Убрать `aiVault.path` из схемы конфига, `ai_vault/location.rs`,
  `ai_vault/relocation.rs`, их команды и UI «Папка данных → Дополнительно →
  хранилище»; `pnpm generate:desktop`.
- Общий сервис переноса `data_root_relocation.rs` остаётся (папка данных).
- До релиза — без миграции: значение `aiVault.path`, если есть,
  отбрасывается нормализацией конфига.
- Watcher: отдельный корень внешнего основного хранилища убирается; корни
  подключённых хранилищ добавляет 5.4.
- Между 5.2 и 5.4 внешнего хранилища нет вовсе — до релиза допустимо;
  5.2 и 5.4 выпускаются в одном релизе.

### 5.3. Проверка версии при сохранении профиля, `SOUL.md` и проекта

**Проблема.** `save_profile`, `write_profile_soul`, `save_project`
(`ai_vault/operations.rs`) перезаписывают файл тем, что прислала форма. Если
правка с другой машины доехала, пока форма открыта, она молча теряется.

**Решение** (как у памяти, `MemoryReadVersions`):

- `get_profile`, `read_profile_soul`, `list_projects` возвращают `revision`
  — SHA-256 файла (для `SOUL.md` пустая строка — «файла нет»).
- Сохранение принимает `expectedRevision`; под блокировкой хранилища хэш
  сверяется, при расхождении — ошибка `staleRevision`, ничего не записано.
  Без `expectedRevision` (внутренние вызовы) проверки нет.
- Успешное сохранение возвращает новую `revision`, форма запоминает её:
  watcher отфильтрует собственную запись и не пришлёт событие, а без новой
  ревизии второе сохранение из той же формы получило бы `staleRevision`.
- UI: «Профиль изменён на другом устройстве или вне TyCo» — «Перечитать»
  / «Сохранить мои». Форма без правок перечитывается молча по событию
  watcher.

**Тесты:** Rust — отклонение после внешней правки, проход без неё,
отсутствующий `SOUL.md`, два сохранения подряд с возвращённой ревизией;
модель формы — оба действия.

### 5.4. Подключённые хранилища: личное и рабочее

**Модель.**

1. Список устройства `aiVaults.attached: [{ path }]` (`x-scope: device`):
   какие папки подключены, решает каждая машина. Имя для UI («Работа») —
   поле `name` маркера хранилища, одинаковое на всех машинах.
2. **Подключение** — «Подключить хранилище…» в разделе профилей: папка с
   маркером подключается; пустая получает маркер (новое хранилище,
   случайный `vaultId`); папка с посторонними файлами — предложение
   подпапки. Отключение убирает путь из списка, файлы не трогаются.
   Вложенность проверяется (5.5).
3. **Два хранилища с одним `vaultId`** (папку скопировали) — второе не
   подключается, UI объясняет. Правило включает основное хранилище: копию
   `ai-vault` с маркером `data-<dataId>` своей папки данных подключить
   нельзя.
4. **Изоляция.** Каждое хранилище самодостаточно: профили, проекты, чаты
   профилей, память. Агент профиля работает только с проектами и файлами
   своего хранилища: `projectPermissions` ссылаются на проекты своего
   хранилища, инструменты хранилища получают корень своего хранилища.
   Связей между хранилищами нет. Изоляция логическая, не песочница:
   команды, скрипты и плагины клиента общие для всех профилей и
   ограничены только своими правами.
5. **Ссылки из `config.json` указывают хранилище.** В ссылки на профиль
   (элементы сеток `profileChat` / `profile`, `chatPrompts.items[].profileId`)
   и `lastProfileChatIds` добавляется необязательный `vaultId`. Пустой —
   основное хранилище; явный `data-<dataId>` основного нормализация
   приводит к пустому, чтобы у ссылки была одна форма. Ссылка на
   неподключённое хранилище скрывается, не удаляется: элемент сетки не
   отображается и не занимает место, при подключении возвращается на своё
   место.
6. **Состояния.** Не найденное хранилище — «не подключено на этом
   устройстве» с «Указать папку» и «Убрать из списка»; ничего не
   создаётся. Маркер новее сборки — требуется обновление TyCo; файлы не читаются и не изменяются.
7. **Доверие.** Хранилище, доступное на запись другим (Linux), —
   предупреждение: профили из него вызывают команды этой машины.
8. **Backend.** `resolve_vault` / `with_vault_of` по `vaultId`; команды
   хранилища принимают `vaultId` (пустой — основное). Блокировка — своя у
   каждого хранилища. Watcher следит за всеми хранилищами; `StorageEvent`
   хранилища несёт поле `vaultId` и путь относительно корня хранилища
   (не префикс `ai-vault/<vaultId>/` в пути — его разбор неоднозначен).
   Индексы чатов в `state_dir/index/` — по `vaultId`, не по хэшу пути:
   смена пути хранилища не перестраивает индекс; «Убрать из списка»
   удаляет индекс хранилища.
9. **UI.** Профили и проекты сгруппированы по хранилищу; при создании —
   выбор хранилища; при совпадении имён профилей показывается имя
   хранилища.

**Порядок.** 5.5 (`check_sync_roots`) — до подключения → формат ссылок с
`vaultId` в схеме и нормализации обоих runtime'ов (до релиза — без
миграции) → backend → UI.

**Тесты:** ссылка на профиль неподключённого хранилища сохраняется; доступ
к проекту другого хранилища отклоняется; отключение не трогает файлы; пути
проектов разных хранилищ не смешиваются; копия с тем же `vaultId`, в том
числе копия основного, не подключается; `data-<dataId>` в ссылке
нормализуется в пустой; события подключённого хранилища несут `vaultId`.

### 5.5. Проверка вложенности синхронизируемых корней

Делается до 5.4: подключение хранилищ опирается на эту проверку.

**Проблема.** `check_external_path` (`ai_vault/marker.rs`) отклоняет только
хранилище внутри папки данных, но не обратное (выбрано `~/Sync`, а папка
данных — `~/Sync/TyCo`) и не смену папки данных на папку внутри хранилища.
Тогда watcher видит одни файлы дважды, а перенос одного корня тащит другой.

**Решение.** Одна функция `check_sync_roots`: папка данных и подключённые
хранилища попарно не лежат друг в друге (включая хранилище в хранилище).
Пути канонизируются: symlink разворачиваются, на Windows сравнение без
учёта регистра и без префикса `\\?\`. Вызывается при выборе и переносе
папки данных (новое место не должно оказаться внутри подключённого
хранилища) и при подключении хранилища. Внешние проекты внутри корней не
запрещаются (5.6).

**Тесты:** корень внутри корня в обе стороны; хранилище в хранилище; путь
через symlink; разный регистр на Windows.

### 5.6. Предупреждение: внешний проект внутри синхронизируемой папки

Внешний проект означает «файлы ведёт пользователь». Если путь лежит внутри
папки данных или хранилища, файлы проекта синхронизируются вместе с ней.

- `create_project` / `save_project` не отказывают; `list_projects`
  возвращает `isInsideSyncedFolder`.
- Форма и список проектов: «Папка лежит внутри папки данных TyCo
  (хранилища) и будет синхронизироваться вместе с ней. Если это не нужно,
  выберите папку снаружи».

### 5.7. Журналы истории старых устройств (не срочно)

Журнал устройства, которое больше не используется, остаётся навсегда.

- «Папка данных → Дополнительно»: список журналов («это устройство» / имя
  устройства), число записей, время последней записи; «Удалить историю
  устройства» для чужого журнала.
- Имя: служебная запись `{"type":"device","name":"<hostname>"}` при смене
  имени; читатель берёт последнюю.

После каждого пункта — `docs/data-folder.md` и `dev_docs/config-storage.md`.
Когда план выполнен — перенести итог в `config-storage.md`.

## 7. TyCo Cloud (отдалённое расширение)

Нативная синхронизация по подписке. Серверная БД хранит журнал ревизий
(`entity_path`, `revision`, `content_hash`, `is_deleted`, устройство),
контент — в объектном хранилище. `CloudSyncClient` в Rust подключается к
шине `StorageEvent`, пишет с ожидаемой ревизией (CAS), получает новые
ревизии по WebSocket и записывает файлы атомарно; дальше работает watcher.
Удаления — tombstone на сервере, не на диске. Единица синхронизации — корень
(папка данных или хранилище). Проектирование — отдельным документом.

## 8. Решено и не входит

- Интеграция с внешними программами синхронизации и управления файлами
  (git и др.), инструкции и файлы настроек под них.
- Синхронизация ключей — системное хранилище каждой машины.
- Одобрение плагинов, скриптов и команд на каждом устройстве.
- Внешний путь основного хранилища — вместо него подключённые хранилища.
- Связи между хранилищами: доступ профиля к проектам другого хранилища.
- Режим «только чтение» для хранилища.
- Поле устройства у плагина в SDK — единственный случай (FastNote) решён в
  хосте.
- Запрещённые имена переменных — окружение получает префикс `TYCO_VAR_`.
- `--user-data-dir`, переменная окружения папки данных, второй экземпляр
  приложения, portable-режим на Windows.
- Копирование горячих клавиш с другого устройства, слияние Markdown.
- Tombstone-файлы на диске: удалённый на одной машине и одновременно
  изменённый на другой чат воскресает — допустимо.
