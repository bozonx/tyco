## 1. Цель

Всё, что пользователь создал и настроил, лежит в одной папке, которую можно
синхронизировать внешними средствами (Syncthing, Nextcloud, Dropbox,
OneDrive, общий диск). TyCo на другом компьютере, подключённый к той же
папке, работает с теми же настройками, командами, профилями, чатами и
историей. То, что относится к конкретной машине (ключи, горячие клавиши,
пути, логи, кэш, webview), остаётся в папках ОС и не синхронизируется.

Не цель: журнал изменений или база данных на клиенте, синхронизация ключей,
слияние двух независимых наборов данных при первом подключении папки.
Поддержка синхронизаторов — «без фанатизма»: формат файлов не даёт
конфликтов там, где это дёшево, а там, где конфликт возможен, данные не
теряются и конфликт виден пользователю.

## 2. Принципы

- **Папка пользователя доверенная, как домашний каталог.** Кто пишет в неё,
  тот меняет команды (в том числе shell-скрипты), плагины и настройки на всех
  машинах. TyCo не требует подтверждать пришедшее через синхронизацию; UI
  предупреждает, если папка доступна на запись другим (Linux).
- **У каждого поля и файла одно место.** Поле принадлежит либо пользователю
  (`config.json`), либо устройству (`device.json`); переопределений нет.
  Значение устройства, относящееся к общей сущности, хранится у устройства по
  id сущности (пути FastNote, значения переменных, пути внешних проектов).
- **Ссылки идут только от устройства к общим данным.** Общие данные не
  ссылаются на данные устройства, иначе нормализация на другой машине удалит
  «несуществующую» ссылку для всех.
- **Отсутствие — не удаление.** Ссылка устройства на общую сущность
  отбрасывается, только когда сущность удалена здесь же, или при чтении
  полного и корректного общего файла, в котором её нет. Файл, который ещё не
  доехал или не читается, ничего не удаляет.
- **Общие идентификаторы не зависят от устройства** и создаются один раз.
  Если две машины могут создать один и тот же файл независимо (маркер vault
  по умолчанию), его содержимое детерминировано: одинаковые байты не дают
  конфликтной копии.
- **В папке пользователя только данные.** Резервные и битые копии, транзакции,
  индексы, блокировки — в `state_dir`.
- **Формат рассчитан на запись с нескольких устройств.** Журналы — по файлу на
  устройство, сущности — по файлу на сущность. Единственный общий файл,
  который переписывают все, — `config.json`; он сохраняется через
  трёхстороннее слияние.
- **Ничего не создаётся молча на месте пропавших данных.** Не найденная
  выбранная папка (данных, vault, внешнего проекта) показывается как «не
  подключено», а не заменяется пустой.
- **Webview видит один `UserConfig`.** Делит его на части и собирает обратно
  только backend.

## 3. Раскладка

```
device_dir (Linux: ~/.config/com.tyco.app;
            Windows: %LOCALAPPDATA%\com.tyco.app\device)
  device.json          конфиг устройства (поля x-scope: device), deviceId,
                       machineId, userDataPath, pluginPaths,
                       pluginCommandPaths, aiProjectPaths
  secrets.json         id и origin ключей этого устройства

user_dir = data_dir по умолчанию (~/.local/share/com.tyco.app, %APPDATA%\com.tyco.app)
  tyco-user.json       маркер: formatVersion, dataId
  config.json          настройки пользователя
  history/editor/<deviceId>.jsonl
  chats/<id>.json, chats/images/
  plugins/<key>.json, plugins/<key>.previous
  ai-vault/            vault по умолчанию (если aiVault.path пуст)
    tyco-vault.json    маркер: formatVersion, vaultId
    profiles/<id>/     profile.json, SOUL.md, chats/, memory/, workspace/
    projects/<id>/     project.json и файлы внутреннего проекта

state_dir (~/.local/state/com.tyco.app, %LOCALAPPDATA%\com.tyco.app)
  logs/, webview/
  config.base.json     база трёхстороннего слияния
  history/editor/local.jsonl   история «только на этом устройстве»
  index/               индексы чатов (в том числе по хэшу пути vault),
                       orphan-images.json
  recovery/            битые копии, копии перед восстановлением,
                       проигравшие версии слияния
  transactions/
```

На Windows `device_dir` — подпапка `device\` в Local: Roaming уезжает на
другие машины вместе с `deviceId`, а `state_dir` и `cache_dir` Tauri кладёт в
одну папку.

## 4. Сделано

**Хранилище и подключение папки (1a)**

- `device_dir` и `user_dir` разделены; webview на Linux перенесён в
  `state_dir`; служебные файлы — в `state_dir/recovery`, `transactions`,
  `index`. Временные файлы атомарной записи — `.tyco-tmp-*` рядом с целью;
  rename повторяется до ~2 с при блокировке файла синхронизатором (Windows).
- Маркер `tyco-user.json`. Стандартная папка создаётся автоматически;
  выбранная без маркера — «не подключена»: ничего не создаётся, запись
  возвращает ошибку, экран «Папка данных не найдена» («Повторить»,
  «Подключить другую», «Использовать стандартную»). Пропажа папки во время
  работы тоже переводит её в «не подключена». Маркер новее сборки — только
  чтение.
- Смена `machineId` (клон ВМ, бэкап) даёт новый `deviceId`.
- `relocate_user_data` с режимами `move`, `connect`, `resetToDefault`,
  `useDefault`; `inspect_user_data_target` для выбора в UI; общий сервис
  переноса `data_root_relocation.rs`, им же пользуется перенос vault.
  Перезапуск после смены папки, горячего переключения нет.
- Конфиг разделён по `x-scope: device` (горячие клавиши, `windowInsertion`,
  `externalAccess`, масштаб, `aiVault.path`, адрес sherpa-onnx,
  `isInDevelopment`, `editor.history.isLocalOnly`, `variableValues`).
  Неизвестные поля возвращаются в свой файл; восстановление пишет файл только
  при смысловом изменении; `configIsNewer` по любому из двух файлов.
- `config.json` сохраняется через трёхстороннее слияние с
  `config.base.json`; при конфликте одного поля побеждает локальная правка,
  версия с диска уходит в `recovery/`, UI уведомляет.
- История редактора — журнал на устройство, `delete` / `result` / `clear`
  записями в своём журнале; режим «только на этом устройстве».
- Чаты: источник правды — `chats/<id>.json`, индекс в `state_dir`
  пересобирается. Картинки без ссылок удаляются через 7 дней после первого
  обнаружения (не по mtime).
- Читатели принимают только имена своего формата; конфликтные копии всех
  распространённых синхронизаторов и временные файлы пропускаются
  (`storage/user_files.rs`).
- Ключи: id создаётся один раз, значение и origin — свойства устройства;
  сборка неиспользуемых ключей не запускается при неподключённой папке,
  конфиге только на чтение, восстановленном конфиге и конфликтной копии
  `config.json`. Ключ, не заданный на устройстве, — отдельное состояние.
- Пути FastNote хранятся на устройстве (`pluginPaths`, `pluginCommandPaths`).

**Переносимость команд и профилей (1b)**

- Переменные `{{var:NAME}}`: объявление общее, значение на устройстве;
  подстановка в скрипты (через окружение `TYCO_VAR_*`), вебхуки, AI-команды и
  `baseUrl` провайдеров; общие fixtures TS/Rust; вкладка «Переменные».
- Поле `platforms` у команд: команда другой ОС видна, но не выполняется.
- Vault по умолчанию внутри папки данных; внешний путь — поле устройства
  («Папка данных → Дополнительно»). Маркер `tyco-vault.json`; внешний vault
  без маркера не подключён и не создаётся. Внешний путь внутри `user_dir`
  отклоняется.
- Внешние проекты: описание в vault, путь — `device.json →
aiProjectPaths.<vaultId>.<projectId>`. Без пути модель получает «проект не
  подключён на этом устройстве»; модель всегда видит проект как
  `projects/<id>/`.
- Запись памяти профиля поверх изменённого извне файла отклоняется
  (`MemoryReadVersions`).
- Ссылки `config.json` на профили (сетки действий, `chatPrompts.profileId`)
  при отсутствии профиля скрываются, но не удаляются.

**Синхронизаторы (этап 2, частично)**

- Watcher (`storage/watcher.rs`): `notify` с debounce 250 мс, опрос каждые
  30 с и при фокусе окна, SHA-256 изменяемых файлов, фильтр собственных
  записей по хэшу, внутренняя шина `StorageEvent`. Обходятся только области
  данных TyCo; `workspace/`, `.git`, symlink и файлы внутренних проектов
  (кроме `project.json`) не обходятся. Внешний vault отслеживается отдельно.
- Внешний `config.json` применяется без перезапуска через трёхстороннее
  слияние с несохранёнными изменениями.
- События обновляют чаты, историю, плагины и профили; картинка, приехавшая
  позже чата, перечитывается.
- Руководство пользователя `docs/data-folder.md`.

**Исправлено в ред. 6**

- Пути внешних проектов больше не удаляются при чтении списка, где проекта
  нет (файл не доехал или не читается); путь забывается только при удалении
  проекта на этом устройстве.
- Маркер vault по умолчанию детерминирован: `vaultId = data-<dataId>`, где

  нет. Для маркера папки данных без `dataId` (созданного до ред. 6) id —
  `default`. Уже существующие маркеры vault со случайным id не меняются.
- Watcher не хэширует файлы внутренних проектов каждые 30 с.

## 5. Осталось сделать

### 5.1. Конфликтные копии: показать и разобрать безопасное

**Сейчас.** `user_files.rs` распознаёт копии Syncthing
(`*.sync-conflict-*`), Dropbox и Nextcloud (`* (… conflicted copy …)*`,
`*_conflict-*`), OneDrive (`<имя>-<ИМЯ-ПК>.<ext>`, только рядом с основным
файлом). Читатели и watcher их пропускают, сборка ключей при копии
`config.json` не запускается. Больше с копиями ничего не происходит: они
копятся, а правки, оставшиеся только в копии, пользователь не видит.

**Что сделать.**

1. **Обнаружение.** Watcher при сканировании собирает список копий в областях
   данных (`user_dir` и vault, кроме `workspace/` и файлов проектов) и
   публикует его в `UserDataState` как `conflictCopies: [{ path, original }]`
   (относительные пути). Отдельной команды не нужно; после изменения —
   `pnpm generate:desktop`.
2. **Показ.** В блоке «Папка данных» и значком в настройках: «Найдено N
   конфликтных копий синхронизатора» со списком (основной файл и копия) и
   действиями «Открыть папку» и «Удалить копию» (с подтверждением; копия
   уходит в `state_dir/recovery`, а не удаляется безвозвратно).
3. **Автоматический разбор** — только там, где он не теряет данных:
   - `config.json` — трёхстороннее слияние копии с базой и текущим файлом тем
     же механизмом, что и для внешней правки (4); при конфликте поля
     побеждает основной файл, копия уходит в `recovery/`, UI уведомляет;
   - `chats/<id>.json` и чаты профилей. У сообщений нет id, поэтому слияние
     по сообщениям невозможно. Правило: если сообщения одной версии — начало
     другой (обычный случай: чат продолжили на одной машине), остаётся более
     длинная версия; иначе копия сохраняется как новый чат с новым id и
     заголовком «<заголовок> (копия с другого устройства)». Ничего не
     теряется, копия удаляется;
   - `history/editor/*.jsonl` — строки объединяются без дублей по `id` в
     основной файл, если это журнал этого устройства; копия чужого журнала
     просто удаляется после объединения его владельцем (каждый журнал пишет
     одно устройство, такие копии почти не возникают).
4. **Не разбирается автоматически** (только показ, п. 2): `plugins/*.json`,
   `profile.json`, `project.json`, `SOUL.md`, память и другие Markdown-файлы
   vault, маркеры. Решает пользователь, открыв папку.
5. Разбор не выполняется, если папка не подключена или открыта только на
   чтение.

**Тесты:** fixtures имён всех синхронизаторов (уже есть) плюс содержимое:
слияние копии `config.json`, чат-префикс, расходящийся чат → новый чат,
OneDrive без основного файла — не копия, Markdown не трогается.

### 5.2. Проверка версии при сохранении профиля, `SOUL.md` и проекта

**Проблема.** `save_profile`, `write_profile_soul` и `save_project`
(`ai_vault/operations.rs`) перезаписывают файл целиком тем, что прислала
форма. Если форма открыта на машине A, а на B тем временем изменили тот же
профиль и синхронизатор доставил правку, сохранение на A молча затирает
правку B. Конфликтной копии при этом нет: файл просто перезаписан поверх
новой версии.

**Решение** (тот же приём, что у памяти, `MemoryReadVersions`):

- `get_profile`, `read_profile_soul`, `list_projects` возвращают вместе с
  данными `revision` — SHA-256 содержимого файла на диске (для `SOUL.md`
  пустая строка означает «файла нет»).
- Команды сохранения принимают `expectedRevision`. Backend под блокировкой
  vault читает файл, сравнивает хэш и при расхождении возвращает новую
  ошибку `staleRevision`, ничего не записав. Без `expectedRevision`
  (внутренние вызовы, например `delete_project`, который сам только что
  перечитал профили) проверки нет.
- UI на `staleRevision`: «Профиль изменён на другом устройстве или вне TyCo»
  с действиями «Перечитать» (несохранённые правки теряются) и «Сохранить
  мои» (повтор с актуальной `revision`). Форма, открытая без правок,
  перечитывается молча по событию watcher.
- Профили сохраняются целиком, без слияния полей: файл маленький, явный
  выбор понятнее.

**Тесты:** Rust — сохранение после внешнего изменения отклоняется, без
изменения проходит, отсутствующий `SOUL.md`; модель формы профиля — оба
действия.

### 5.3. Предупреждение: внешний проект внутри синхронизируемой папки

Внешний проект означает «файлы ведёт пользователь, TyCo их не
синхронизирует». Если путь проекта лежит внутри `user_dir` или внутри vault
(в том числе внешнего), файлы на самом деле синхронизируются вместе с
папкой данных, а git-репозиторий в ней может повредиться при правках с двух
машин.

- При указании пути (`create_project`, `save_project`) backend не
  отказывает, а `list_projects` возвращает у проекта признак
  `isInsideSyncedFolder`.
- Форма проекта и список проектов показывают предупреждение: «Папка лежит
  внутри папки данных TyCo и синхронизируется вместе с ней. Для
  git-репозитория или файлов, которые не должны синхронизироваться, выберите
  папку снаружи». Сравнение — по нормализованным путям, как в
  `check_external_path`.

### 5.4. Журналы истории старых устройств

`history/editor/<deviceId>.jsonl` устройства, которое больше не
используется (переустановка, клон, проданный ноутбук), никто не
переписывает: ограничения хранения применяются только при чтении, файл
остаётся навсегда. Не срочно.

- В блоке «Папка данных → Дополнительно» список журналов: «это устройство» /
  короткий `deviceId`, число записей, время последней записи.
- Кнопка «Удалить историю устройства» (с подтверждением) удаляет чужой
  журнал. Для своего — существующая очистка истории.
- Чтобы список был понятнее, устройство при записи журнала добавляет в
  него служебную запись `{"type":"device","name":"<hostname>"}` при смене
  имени; читатель берёт последнюю.

### 5.5. Несколько vault: личные и рабочие профили

**Сценарий.** Личные профили и проекты синхронизируются вместе с папкой
данных, а рабочие лежат в отдельной папке со своей синхронизацией (рабочий
Nextcloud, общий диск команды) или под git. Обе группы нужны в одном
клиенте одновременно.

**Сейчас.** На устройстве один vault (`aiVault.path`); сменить его можно
только переносом или подключением, и тогда другой vault не виден. Основа
для нескольких vault уже есть: свой маркер с `vaultId`, пути внешних
проектов по `vaultId`, индексы чатов по хэшу пути vault, watcher с
несколькими корнями.

**Второй экземпляр приложения не нужен.** Второй экземпляр понадобился бы
только для второй папки данных целиком (свои настройки, команды, провайдеры,
ключи). Приложение однооконное (`tauri-plugin-single-instance`), флаг
`--user-data-dir` отклонён (раздел 7): горячие клавиши, трей и внешний
доступ двух экземпляров конфликтуют. Сценарий «личное и рабочее»
покрывается несколькими vault.

**Модель.**

1. **Основной vault** — как сейчас (внутри папки данных или `aiVault.path`).
   **Дополнительные vault** — список устройства
   `aiVaults.attached: [{ path }]` (`x-scope: device`): какие папки
   подключены, решает каждая машина. Имя для UI («Работа») хранится в
   маркере vault (`name`), чтобы на всех машинах было одинаковым.
2. **Подключение** — «Подключить папку профилей…» в разделе профилей: папка
   с маркером подключается, пустая получает маркер (создание нового vault),
   папка с посторонними файлами — предложение подпапки. Отключение только
   убирает путь из списка; файлы не трогаются. Дополнительный vault не может
   лежать внутри `user_dir`, внутри другого vault или содержать их.
3. **Каждый vault самодостаточен**: свои профили, проекты, чаты профилей,
   память. Права профиля (`projectPermissions`) действуют только на проекты
   своего vault. Так рабочий vault можно отдать коллегам или унести на
   другой компьютер без личных данных.
4. **Ссылки из `config.json` указывают vault.** Id профилей — slug из имени,
   «assistant» легко окажется в обоих vault. В ссылки на профиль (элементы
   сеток `profileChat` / `profile`, `chatPrompts.items[].profileId`) и в
   состояние сессии (`lastProfileChatIds`)
   добавляется необязательный `vaultId`; пустой — основной vault. На машине,
   где vault не подключён, ссылка скрывается, но не удаляется (как сейчас).
5. **Что берётся из папки данных:** провайдеры моделей, ключи, команды,
   настройки хранения чатов профилей. `modelId` профиля, которого нет в
   этом конфиге, заменяется первой доступной моделью (уже так); команды из
   `tools.groups.*.commandIds`, которых нет, не предлагаются модели и в
   профиле не удаляются.
6. **Состояния.** Не найденный дополнительный vault — «не подключён на этом
   устройстве» в списке профилей с действиями «Указать папку» и «Убрать из
   списка»; ничего не создаётся. Маркер новее сборки — только чтение.
7. **Доверие.** Если дополнительный vault доступен на запись другим (Linux)
   или явно общий, показывается предупреждение как для папки данных:
   профили из него могут вызывать команды этой машины. Возможен режим
   «только чтение» для vault, подключённого как общая библиотека.
8. **Backend.** `resolve_vault` / `with_vault_of` принимают `vaultId`;
   команды vault получают `vaultId` (пустой — основной). Watcher следит за
   всеми подключёнными vault, события несут `ai-vault/<vaultId>/…` для
   дополнительных. Индексы чатов — уже по хэшу пути vault.
9. **UI.** Профили и проекты сгруппированы по vault; при создании профиля
   выбирается vault; в выборе профиля в сетках и подсказках — имя vault при
   совпадении имён профилей.

**Порядок.** Сначала формат ссылок с `vaultId` в схеме и нормализации обоих
runtime'ов (до релиза — без миграции), затем backend с несколькими vault,
затем UI.

**Тесты:** два vault с одинаковым id профиля, ссылка на профиль
неподключённого vault сохраняется, права на проект другого vault
отклоняются, отключение не трогает файлы, пути проектов разных vault не
смешиваются.

### 5.6. Документы

После каждого пункта — обновить `docs/data-folder.md` (конфликтные копии,

## 6. TyCo Cloud (отдалённое расширение)

Нативная синхронизация по подписке без сторонних утилит и серверная
автоматизация. Серверная БД хранит журнал ревизий (`entity_path`,
`revision`, `content_hash`, `is_deleted`, устройство), контент — в
объектном хранилище. Клиент `CloudSyncClient` в Rust подключается к
существующей шине `StorageEvent` (п. 4), отправляет запись с ожидаемой
ревизией (CAS) и получает новые ревизии по WebSocket, записывая файлы в
`user_dir` атомарно; дальше работает существующий watcher. Удаления
передаются как tombstone в серверной БД, на диске tombstone-файлов нет.
Серверные задачи создают новые сущности с новым UUID, а правки
существующих файлов сверяют ревизию. Подробное проектирование — отдельным
документом, когда до него дойдёт очередь.

## 7. Решено и не входит

- Синхронизация ключей — они в системном хранилище каждой машины.
- Одобрение плагинов, скриптов и команд на каждом устройстве — папка
  доверенная.
- Механизм «поле устройства у плагина» в SDK и переменные в полях плагинов —
  единственный случай, путь FastNote, решён в хосте.
- Список запрещённых имён переменных — окружение получает префикс
  `TYCO_VAR_`.
- Кнопки создания `.stignore` и `.gitignore` — описано в документации.
- `--user-data-dir`, переменная окружения папки данных, второй экземпляр
  приложения, portable-режим на Windows.
- Копирование глобальных горячих клавиш с другого устройства, слияние
  Markdown-файлов vault.
- Tombstone-файлы на диске: удалённый на одной машине и одновременно
  изменённый на другой чат воскресает — это допустимо.

Открытый вопрос: нужны ли переменные в промптах трансформаций и стилей,
правилах LLM-задач, `translation.providers.deepl.endpoint`. Механизм тот же;
решать по запросу пользователей.
