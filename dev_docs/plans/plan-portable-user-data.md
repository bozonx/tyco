# План: переносимая папка пользовательских данных

Дата: 2026-11-09 (ред. 7 — план переписан от текущего состояния: что есть,
что исправить сразу, куда двигаться дальше).
Связанные документы: `dev_docs/config-storage.md`, `dev_docs/cross-platform.md`,
`dev_docs/desktop-api.md`, `dev_docs/plugin-packages.md`,
`dev_docs/chat-files.md`, `docs/data-folder.md` (руководство пользователя).

## 1. Цель и рамки

Всё, что пользователь создал и настроил, лежит в обычных файлах, которые
можно синхронизировать внешними средствами (Syncthing, Nextcloud, Dropbox,
OneDrive, общий диск, git). TyCo на другом компьютере, подключённый к тем же
папкам, работает с теми же настройками, командами, профилями, чатами и
историей. То, что относится к машине (ключи, горячие клавиши, пути, логи,
кэш, webview), остаётся в папках ОС.

Ориентир — Obsidian: vault — это просто папка с файлами, без базы данных;
служебное состояние устройства — отдельно; синхронизатор может быть любым,
конфликты синхронизатора приложение не прячет, но и не пытается решить всё.
Максимально надёжная синхронизация (ревизии, CAS, tombstone) — задача
будущего TyCo Cloud (раздел 7), а не формата файлов.

Поэтому «без фанатизма»:

- формат не создаёт конфликтов там, где это дёшево (файл на сущность,
  журнал на устройство, детерминированные маркеры);
- там, где конфликт возможен, данные не теряются и конфликт виден;
- автоматический разбор конфликтов — только для `config.json` (уже есть
  трёхстороннее слияние); остальное показывается пользователю.

Не цель: журнал изменений или БД на клиенте, синхронизация ключей, слияние
двух независимых наборов данных при первом подключении, второй экземпляр
приложения.

## 2. Принципы

- **Папка данных и подключённые vault доверенные, как домашний каталог.**
  Кто пишет в них, тот меняет команды, плагины и профили на всех машинах.
  Подтверждений на пришедшее через синхронизацию нет; UI предупреждает, если
  папка доступна на запись другим (Linux).
- **У каждого поля и файла одно место.** Поле принадлежит либо пользователю
  (`config.json`), либо устройству (`device.json`); переопределений нет.
  Значение устройства для общей сущности хранится у устройства по id
  сущности (пути FastNote, значения переменных, пути внешних проектов,
  список подключённых vault).
- **Ссылки идут только от устройства к общим данным**, не наоборот.
- **Отсутствие — не удаление.** Ссылка на общую сущность забывается, только
  когда сущность удалена на этом устройстве. Не доехавший или нечитаемый
  файл ничего не удаляет; ссылка на отсутствующее скрывается.
- **Общие идентификаторы не зависят от устройства и не совпадают
  случайно.** Если две машины могут создать один файл независимо, его
  содержимое детерминировано (маркер vault по умолчанию) или его имя
  уникально (новые профили и проекты, см. 5.1).
- **В синхронизируемых папках только данные.** Резервные и битые копии,
  транзакции, индексы, блокировки — в `state_dir`.
- **Ничего не создаётся молча на месте пропавшего.** Не найденная выбранная
  папка (данных, vault, внешнего проекта) — «не подключено».
- **Синхронизируемые корни не вложены друг в друга.** Папка данных,
  внешний vault, дополнительные vault и внешние проекты не лежат один внутри
  другого (кроме vault по умолчанию внутри папки данных).
- **Без настройки всё работает.** Пользователь, ничего не настраивавший,
  получает одну папку данных с vault внутри; синхронизирует её целиком.

## 3. Модель: три вида папок

| Что | Где | Синхронизация |
| --- | --- | --- |
| Папка устройства (`device_dir`) | папки ОС | никогда |
| Состояние (`state_dir`) | папки ОС | никогда |
| Папка данных (`user_dir`) | по умолчанию папки ОС, можно выбрать | пользователем |
| Основной vault | внутри папки данных или внешняя папка устройства | вместе с папкой данных или отдельно |
| Дополнительные vault (5.3) | любые папки, список на устройстве | отдельно, своими средствами |
| Внешний проект | любая папка, путь на устройстве | не TyCo: git, свой синхронизатор |

Vault — переносимый корень «профили + проекты + чаты профилей + память».
Папка данных — настройки, команды, провайдеры, плагины, общие чаты,
история. Профиль берёт из папки данных провайдеры, ключи и команды; если
нужного нет на этой машине, профиль работает с тем, что есть (модель
по умолчанию, недоступные команды не предлагаются).

Типовые сценарии:

1. **Ничего не настроено.** Одна папка данных, vault внутри. Синхронизировать
   её целиком или не синхронизировать вовсе.
2. **Всё в облаке.** Папка данных выбрана внутри Dropbox/Syncthing на каждой
   машине; на разных машинах путь может отличаться (путь — поле устройства).
3. **Личное и рабочее.** Личные профили — в основном vault; рабочие — в
   дополнительном vault в рабочем Nextcloud или git, подключённом только на
   нужных машинах.
4. **Проект с кодом.** Внешний проект: описание в vault, папка на каждой
   машине своя (или не указана — проект «не подключён на этом устройстве»).

## 4. Что есть сейчас

### 4.1. Раскладка

```
device_dir (Linux: ~/.config/com.tyco.app;
            Windows: %LOCALAPPDATA%\com.tyco.app\device)
  device.json          поля x-scope: device, deviceId, machineId,
                       userDataPath, pluginPaths, pluginCommandPaths,
                       aiProjectPaths.<vaultId>.<projectId>
  secrets.json         id и origin ключей этого устройства

user_dir (по умолчанию ~/.local/share/com.tyco.app, %APPDATA%\com.tyco.app)
  tyco-user.json       маркер: formatVersion, dataId
  config.json          настройки пользователя
  history/editor/<deviceId>.jsonl
  chats/<id>.json, chats/images/
  plugins/<key>.json, plugins/<key>.previous
  ai-vault/            vault по умолчанию (если aiVault.path пуст)
    tyco-vault.json    маркер: formatVersion, vaultId (= data-<dataId>)
    profiles/<id>/     profile.json, SOUL.md, chats/, memory/, workspace/
    projects/<id>/     project.json и файлы внутреннего проекта

state_dir (~/.local/state/com.tyco.app, %LOCALAPPDATA%\com.tyco.app)
  logs/, webview/, config.base.json, history/editor/local.jsonl,
  index/ (индексы чатов по хэшу пути vault, orphan-images.json),
  recovery/, transactions/
```

На Windows `device_dir` — подпапка `device\` в Local: Roaming уезжает на
другие машины вместе с `deviceId`.

### 4.2. Реализовано

- **Подключение папки данных.** Маркер `tyco-user.json`; выбранная папка без
  маркера или пропавшая во время работы — «не подключена», экран с
  действиями «Повторить» / «Подключить другую» / «Использовать стандартную»;
  маркер новее сборки — только чтение. `relocate_user_data` (`move`,
  `connect`, `resetToDefault`, `useDefault`), общий сервис
  `data_root_relocation.rs`. Смена папки — через перезапуск.
- **Конфиг.** Разделение по `x-scope: device`; `config.json` сохраняется
  трёхсторонним слиянием с `config.base.json`, проигравшая версия — в
  `recovery/`. Внешняя правка применяется без перезапуска.
- **Устройство.** Смена `machineId` (клон ВМ) даёт новый `deviceId`. Ключи:
  id общий, значение и origin — на устройстве. Пути FastNote на устройстве.
- **Форматы для нескольких писателей.** История — журнал на устройство;
  чаты — файл на чат, индекс в `state_dir`; картинки без ссылок удаляются
  через 7 дней после обнаружения. Читатели пропускают конфликтные копии
  всех распространённых синхронизаторов и временные файлы
  (`storage/user_files.rs`). Атомарная запись с повтором rename (Windows).
- **Переносимость команд.** Переменные `{{var:NAME}}` (объявление общее,
  значение на устройстве), поле `platforms` у команд.
- **Vault.** По умолчанию внутри папки данных; внешний путь — поле
  устройства. Маркер `tyco-vault.json`, внешний vault без маркера не
  подключён. Маркер vault по умолчанию детерминирован. Внешние проекты:
  описание в vault, путь в `device.json`; без пути — «не подключён на этом
  устройстве». Запись памяти поверх внешней правки отклоняется
  (`MemoryReadVersions`). Ссылки на отсутствующие профили скрываются.
- **Watcher** (`storage/watcher.rs`): `notify` + опрос, SHA-256, фильтр
  своих записей, шина `StorageEvent`; обходит только области данных TyCo
  (без `workspace/`, `.git`, symlink, файлов внутренних проектов). Внешний
  vault отслеживается отдельно. События обновляют чаты, историю, плагины,
  профили.
- Руководство пользователя `docs/data-folder.md`.

## 5. Дальше: по порядку

Порядок выбран по риску потери данных, затем по ценности для сценария
«личное и рабочее».

### 5.1. Сразу: уникальные id новых профилей и проектов

**Проблема (найдена при ревизии).** Id профиля и проекта — slug из имени
(`createVaultId` в `lib/ai-profiles/vault-id.ts`); счётчик добавляется
только при совпадении с уже видимым локально id, случайный суффикс — только
для имён без латинского написания. Две машины до синхронизации создают
профиль «Assistant» → обе пишут `profiles/assistant/profile.json`, `SOUL.md`
и т. д. Синхронизатор получает два разных файла с одним именем: конфликтные
копии в лучшем случае, смешанный профиль (`profile.json` от одной машины,
`SOUL.md` от другой) — в худшем. `create_profile` проверяет существование
только локально. То же для проектов и, в будущем, для одинаковых id в двух
vault (5.3).

**Решение.** Новый id — slug + короткий случайный суффикс
(`assistant-7k3f`); id в UI не показывается.
Существующие id не меняются. Отображаемое имя — поле `name`.

**Тесты:** два создания с одинаковым именем дают разные id; старые id
читаются.

### 5.2. Сразу: проверка версии при сохранении профиля, `SOUL.md` и проекта

**Проблема.** `save_profile`, `write_profile_soul`, `save_project`
(`ai_vault/operations.rs`) перезаписывают файл тем, что прислала форма. Если
форма открыта на A, а правка с B доехала через синхронизатор, A молча
затирает её — без конфликтной копии.

**Решение** (приём памяти, `MemoryReadVersions`):

- `get_profile`, `read_profile_soul`, `list_projects` возвращают `revision`
  — SHA-256 файла (для `SOUL.md` пустая строка — «файла нет»).
- Сохранение принимает `expectedRevision`; под блокировкой vault хэш
  сверяется, при расхождении — ошибка `staleRevision`, ничего не записано.
  Без `expectedRevision` (внутренние вызовы) проверки нет.
- UI: «Профиль изменён на другом устройстве или вне TyCo» — «Перечитать»
  / «Сохранить мои». Форма без правок перечитывается молча по событию
  watcher.
- Без слияния полей: файл маленький, явный выбор понятнее.

**Тесты:** Rust — отклонение после внешней правки, проход без неё,
отсутствующий `SOUL.md`; модель формы — оба действия.

### 5.3. Несколько vault: личные и рабочие профили

**Сценарий.** Рабочие профили и проекты — в отдельной папке со своей
синхронизацией (рабочий Nextcloud, общий диск, git); в одном клиенте нужны
обе группы. Второй экземпляр приложения не нужен (раздел 8).

**Основа уже есть:** маркер с `vaultId`, пути проектов по `vaultId`, индексы
чатов по хэшу пути vault, watcher с несколькими корнями.

**Модель.**

1. **Основной vault** — как сейчас. **Дополнительные** — список устройства
   `aiVaults.attached: [{ path }]` (`x-scope: device`). Имя для UI («Работа»)
   — поле `name` маркера vault, одинаковое на всех машинах.
2. **Подключение** — «Подключить папку профилей…»: папка с маркером
   подключается; пустая получает маркер (новый vault со случайным id); папка
   с посторонними файлами — предложение подпапки. Отключение убирает путь
   из списка, файлы не трогаются. Проверка вложенности — общая функция
   (5.4).
3. **Два vault с одним `vaultId`** (папку скопировали, а не подключили ту же)
   — второй не подключается, UI объясняет.
4. **Каждый vault самодостаточен**: профили, проекты, чаты профилей,
   память. `projectPermissions` действуют только на проекты своего vault.
5. **Ссылки из `config.json` указывают vault.** В ссылки на профиль
   (элементы сеток `profileChat` / `profile`, `chatPrompts.items[].profileId`)
   и `lastProfileChatIds` добавляется необязательный `vaultId`; пустой —
   основной. Ссылка на неподключённый vault скрывается, не удаляется.
6. **Состояния.** Не найденный vault — «не подключён на этом устройстве» с
   «Указать папку» и «Убрать из списка». Маркер новее сборки — только
   чтение.
7. **Доверие.** Vault, доступный на запись другим (Linux), — предупреждение:
   профили из него вызывают команды этой машины.
8. **Backend.** `resolve_vault` / `with_vault_of` по `vaultId`; команды
   vault принимают `vaultId` (пустой — основной). Watcher следит за всеми
   vault; события дополнительных — `ai-vault/<vaultId>/…`.
9. **UI.** Профили и проекты сгруппированы по vault; при создании — выбор
   vault; при совпадении имён профилей в выборе показывается имя vault.

**Порядок.** Формат ссылок с `vaultId` в схеме и нормализации обоих
runtime'ов (до релиза — без миграции) → backend → UI.

**Тесты:** ссылка на профиль неподключённого vault сохраняется; права на
проект другого vault отклоняются; отключение не трогает файлы; пути
проектов разных vault не смешиваются; копия vault с тем же id не
подключается.

### 5.4. Проверка вложенности синхронизируемых корней

**Проблема (найдена при ревизии).** `check_external_path`
(`ai_vault/marker.rs`) отклоняет только внешний vault внутри папки данных.
Не проверяется обратное: внешний vault, содержащий папку данных (выбрали
`~/Dropbox`, а папка данных — `~/Dropbox/TyCo`), и смена папки данных на
папку внутри внешнего vault. Тогда watcher и синхронизатор видят одни файлы
дважды, а перенос одного корня тащит другой.

**Решение.** Одна функция `check_sync_roots` (нормализованные пути, как
сейчас): папка данных, основной внешний vault и дополнительные vault не
лежат друг в друге (кроме vault по умолчанию). Вызывается при выборе
папки данных, vault и при подключении дополнительного vault. Внешние
проекты внутри любого корня не запрещаются, а получают предупреждение
(5.5).

### 5.5. Предупреждение: внешний проект внутри синхронизируемой папки

Внешний проект — «файлы ведёт пользователь». Если путь лежит внутри папки
данных или любого vault, файлы синхронизируются вместе с ней, а
git-репозиторий может повредиться при правках с двух машин.

- `create_project` / `save_project` не отказывают; `list_projects`
  возвращает `isInsideSyncedFolder`.
- Форма и список проектов: «Папка лежит внутри папки данных TyCo и
  синхронизируется вместе с ней. Для git-репозитория выберите папку
  снаружи».

### 5.6. Конфликтные копии: показать

Сейчас копии распознаются и пропускаются, но копятся, и правки, оставшиеся
только в копии, не видны.

1. **Обнаружение.** Watcher собирает копии в областях данных (папка данных и
   все vault, кроме `workspace/` и файлов проектов) и публикует в
   `UserDataState` `conflictCopies: [{ path, original }]`; затем
   `pnpm generate:desktop`.
2. **Показ.** Блок «Папка данных» и значок в настройках: «Найдено N
   конфликтных копий» со списком, «Открыть папку» и «Убрать копию» (с
   подтверждением; копия уходит в `state_dir/recovery`).
3. **Автоматически** разбирается только `config.json`: трёхстороннее слияние
   копии тем же механизмом, что для внешней правки; при конфликте поля
   побеждает основной файл, копия — в `recovery/`, UI уведомляет.
4. Разбор не выполняется при неподключённой папке или режиме только чтения.

**Тесты:** слияние копии `config.json`; OneDrive без основного файла — не
копия; Markdown не трогается.

### 5.7. Журналы истории старых устройств (не срочно)

Журнал устройства, которое больше не используется, остаётся навсегда.

- «Папка данных → Дополнительно»: список журналов («это устройство» /
  имя устройства), число записей, время последней записи; «Удалить историю
  устройства» для чужого журнала.
- Имя: служебная запись `{"type":"device","name":"<hostname>"}` при смене
  имени; читатель берёт последнюю.

### 5.8. Документы

После каждого пункта — `docs/data-folder.md` (сценарии из раздела 3,
несколько vault, конфликтные копии, проекты внутри синхронизируемой папки)
и `dev_docs/config-storage.md`. Когда план выполнен — перенести итог в
`config-storage.md` и удалить план.

## 7. TyCo Cloud (отдалённое расширение)

Нативная синхронизация по подписке. Серверная БД хранит журнал ревизий
(`entity_path`, `revision`, `content_hash`, `is_deleted`, устройство),
контент — в объектном хранилище. `CloudSyncClient` в Rust подключается к
шине `StorageEvent`, пишет с ожидаемой ревизией (CAS), получает новые
ревизии по WebSocket и записывает файлы атомарно; дальше работает watcher.
Удаления — tombstone на сервере, не на диске. Единица синхронизации — корень
(папка данных или vault), поэтому рабочий vault можно синхронизировать
облаком отдельно от личного. Проектирование — отдельным документом.

## 8. Решено и не входит

- Синхронизация ключей — системное хранилище каждой машины.
- Одобрение плагинов, скриптов и команд на каждом устройстве.
- Поле устройства у плагина в SDK — единственный случай (FastNote) решён в
  хосте.
- Запрещённые имена переменных — окружение получает префикс `TYCO_VAR_`.
- Кнопки создания `.stignore` / `.gitignore` — описано в документации.
- `--user-data-dir`, переменная окружения папки данных, второй экземпляр
  приложения, portable-режим на Windows: горячие клавиши, трей и внешний
  доступ двух экземпляров конфликтуют; «личное и рабочее» покрывают vault.
- Копирование горячих клавиш с другого устройства, слияние Markdown vault.
- Tombstone-файлы на диске: удалённый на одной машине и одновременно
  изменённый на другой чат воскресает — допустимо.
