# Режим «Слушание»: расшифровка звука компьютера

Статус: реализация этапов 1–4 выполнена; VM-тесты отложены по запросу пользователя.
Обновлено: 2026-11-10. Нативная приёмка Windows и ручная матрица ещё не выполнены.

## 1. Задача

Пользователь слушает голосовое сообщение в Telegram, видео в браузере или
любой другой звук и хочет получить текст. Для этого вводим отдельный режим
оверлея — **«Слушание»**, рядом с оверлеем голосового ввода (окно `quick`,
`VoiceView` в режиме `bar`, активация `voice`). Между двумя режимами
можно переключаться кнопкой.

Голосовой ввод в чат, в быстрый запрос к ИИ и в голосовые команды
не меняется.

Не входит в задачу:

- расшифровка аудиофайлов (отдельная задача);
- фоновая запись или кольцевой буфер «последние N секунд». Запись идёт только
  после явного действия пользователя.

## 2. Почему отдельный режим

У голосового ввода и слушания разное всё, кроме внешнего вида:

|                           | Голосовой ввод         | Слушание                           |
| ------------------------- | ---------------------- | ---------------------------------- |
| Источник                  | микрофон               | весь звук или приложение           |
| Чья речь                  | пользователя           | чужая                              |
| Голосовые команды         | да                     | нет                                |
| Контекстная коррекция     | да                     | нет                                |
| Короткий endpoint (1,5 с) | да                     | нет (паузы между сообщениями)      |
| Автостоп: 3 мин тишины    | да                     | да                                 |
| Общий лимит: 1 час        | да                     | да                                 |
| Скрытие при потере фокуса | да                     | нет (пользователь кликает в плеер) |
| Конечное действие         | вставка в целевое окно | меню действий с расшифровкой       |

Если сделать это одним режимом с выбором источника, каждое из этих отличий
станет условием «если источник не микрофон». Отдельный режим проще и
понятнее пользователю. Общее — компоненты панели (волна, живой текст,
кнопки), сессия распознавания, таймеры автостопа (`voice-session.ts`)
и транспорт звука.

## 3. Сценарии

1. **Хоткей «Слушать звук компьютера».** Сразу открывает оверлей в режиме
   «Слушание» и начинает запись всего звука компьютера (или приложения,
   выбранного в настройках для этого хоткея). Пользователь сдвигает оверлей,
   если он закрывает сообщение, включает воспроизведение, затем
   останавливает запись (кнопкой или повторным нажатием хоткея) и попадает
   в меню действий с расшифровкой.
2. **Переключение режима.** В панели обоих режимов есть кнопка
   «🎤 ⇄ 🔊»: из голосового ввода — на слушание и обратно.
3. **Выбор источника в слушании.** «Весь звук» или конкретное приложение из
   тех, что сейчас воспроизводят звук. Источник можно сменить во время
   записи без потери текста.
4. **Перемещение оверлея мышью.** Касается всех оверлеев окна `quick`, там,
   где платформа это позволяет штатно (см. 7). Позиция не сохраняется.

## 4. UX

### 4.1 Панель слушания

```
[🎤⇄🔊]  [🔊 Весь звук ▾]   ~~~~ волна ~~~~   00:12   [ⓘ]  [Стоп]
            ├ 🔊 Весь звук
            ├ ── Сейчас играет ──
            ├ Telegram           ▮▮▯
            └ Firefox            ▮▯▯
```

- Панель визуально отличается от голосового ввода (иконка 🔊 и подпись
  «Слушаю»), чтобы не перепутать, что записывается.
- В списке приложений только те, у которых сейчас есть поток воспроизведения.
  Список обновляется на лету: Telegram появляется, когда начинает играть.
  Рядом — уровень звука, чтобы было видно, кто сейчас звучит.
- Выбор в оверлее действует до конца сессии и не запоминается. Хоткей
  слушания всегда начинает со своего источника из настроек.
- Если источник пропал (приложение закрыли), запись ждёт его возвращения,
  сохраняя текст. Область записи автоматически не расширяется. Оверлей
  сообщает об ожидании и предлагает выбрать «Весь звук» вручную.
- Иконка ⓘ — подсказка о том, куда уходит звук (см. 8). Отдельного
  предупреждения нет.

### 4.2 Переключение режима

- Кнопка переключает режим в том же окне `quick`, без закрытия и без сброса
  позиции.
- Переключение во время записи останавливает текущий захват и начинает
  новый в другом режиме. Уже распознанный текст не теряется: если он есть,
  сначала показывается результат текущего режима (для слушания — меню
  действий, для голосового ввода — его меню результата), а переключатель
  остаётся в нём доступен.
- Хоткей переключения — в подсказках оверлея (`ShortcutList`), например Tab.

### 4.3 Поведение режима «Слушание»

- **Окно `quick` не прячется при потере фокуса** — ни во время записи, ни
  в меню действий после неё. Пользователь кликает в Telegram, чтобы включить
  или переслушать сообщение. Скрывается только по «Стоп»/«Отмена», выбору
  действия, Esc (когда оверлей в фокусе) или повторному хоткею.
- **Повторное нажатие хоткея слушания — «Стоп».** Оверлей почти всегда не в
  фокусе, поэтому без этого остановить запись можно только мышью. Нажатие
  хоткея в меню действий закрывает оверлей (как Esc).
- **После остановки сразу открывается меню действий**, где расшифровка уже
  стала контекстом. Результат не вставляется автоматически. В меню:
  - быстрые действия: копировать, вставить, открыть в редакторе,
    отправить в чат;
  - ИИ-действия над текстом (пересказать, ответить, перевести и т.п.) —
    те же, что в существующем меню действий над контекстом;
  - «Ответить голосом» — открывает голосовой ввод, расшифровка передаётся
    как контекст для коррекции и для ИИ-ответа. Это главный сценарий:
    прослушал сообщение — надиктовал ответ.
- **Пустая расшифровка** (тишина или ничего не распознано): меню действий
  не открывается, вместо него — «Ничего не распознано» с кнопками
  «Повторить» и «Закрыть».
- **Нет голосовых команд, контекстной коррекции и короткого endpoint.**
  Автостоп общий для всех голосовых режимов (`voice-session.ts`):
  `SILENCE_TIMEOUT_MS` — 3 минуты без распознанной речи,
  `MAX_RECORDING_MS` — 1 час, с предупреждением за
  `AUTO_STOP_WARNING_MS`. Тишиной считается и звук без речи (музыка),
  и ожидание потока приложения (4.4).
- **Звуки самого TyCo** не попадают в запись: на Windows процесс TyCo
  исключается системой (см. 5.2), на Linux звуки интерфейса не
  проигрываются, пока открыт поток захвата. Звук старта играет до
  открытия потока, звук остановки — после его закрытия.

### 4.4 Настройки

В настройках хоткеев у новой активации есть поле «Источник»:
«Весь звук» (по умолчанию) или приложение.

- Приложение выбирается из списка звучащих сейчас или вводится по имени.
  Хранится устойчивый идентификатор (см. 5.3), а не PID.
- Если при нажатии хоткея приложение не воспроизводит звук, запись ждёт его
  потока. В оверлее при этом написано «Ждём звук из Telegram…», и там же
  можно переключиться на «Весь звук». Ожидание идёт в счёт таймера тишины,
  так что забытая сессия закроется сама.

### 4.5 История

Расшифровки слушания пишутся в историю с отдельной пометкой
(`kind: 'listen'`, диктовки — `kind: 'dictation'`). В UI истории — значок
и фильтр по виду.

## 5. Захват звука

Новый вариант источника в `services/voice` поверх трейта `AudioSource`.
Выход тот же: PCM16 моно 16 кГц чанками по 100 мс через тот же канал.
Провайдер распознавания не знает, откуда звук.

```rust
pub enum CaptureSource {
    Microphone,
    SystemMix,
    Application(AudioAppId),
}
```

Платформенная часть — в `services/platform/audio/` (сейчас это
`platform/audio.rs`, разнести по файлам): микрофон через CPAL, звук
компьютера — нативно.

### 5.1 Linux (PipeWire)

CPAL здесь не подходит: он не умеет ни monitor-источники, ни отдельные
потоки приложений.

- Используем `pipewire-rs`. Список звучащих приложений — узлы с
  `media.class = Stream/Output/Audio`: имя из `application.name`,
  бинарник из `application.process.binary`, иконка из `application.icon-name`.
- **Весь звук:** поток захвата с `stream.capture.sink = true`, цель —
  sink по умолчанию. Следуем за сменой устройства по умолчанию
  (наушники ↔ колонки).
- **Приложение:** поток захвата с `target.object`, равным serial узла
  приложения. У одного приложения может быть несколько потоков (у браузера —
  по вкладке, у Telegram — новый поток на каждое сообщение). Поэтому
  подключаемся ко всем потокам с данным `AudioAppId` и подключаем новые,
  когда они появляются. Микширование в моно — у нас.
- Свои потоки (процесс TyCo) из «Всего звука» исключить нельзя: monitor
  отдаёт уже готовый микс. Решение — не проигрывать свои звуки во время
  захвата (4.3).
- **Чистый PulseAudio без PipeWire не поддерживаем.** PipeWire — звуковой
  сервер по умолчанию во всех актуальных дистрибутивах, второй бэкенд
  (`libpulse`) ради уходящего случая не окупается. Без PipeWire режим
  «Слушание» недоступен: активация в настройках и переключатель в оверлее
  показывают причину. Определяет Rust, фронтенд получает `canListen`.
- Flatpak-версия Telegram и браузеры в sandbox видны в PipeWire как обычные
  потоки. Проверить имена в VM-тестах.

### 5.2 Windows (WASAPI)

- **Весь звук:** process loopback в режиме
  `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE` с PID самого TyCo:
  весь звук без наших собственных звуков. Запасной вариант на старых
  сборках — обычный loopback устройства по умолчанию (тогда свои звуки
  глушим, как на Linux).
- **Приложение:** `ActivateAudioInterfaceAsync` с
  `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`,
  `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`. Доступность проверяется
  реальной активацией и инициализацией потока, а не номером сборки Windows.
  При недоступности показываем только «Весь звук» через device loopback.
- Браузеры воспроизводят звук из дочернего процесса (audio service у Chromium).
  Поэтому берём PID **корневого** процесса приложения, тогда режим
  `…_PROCESS_TREE` захватит и детей. Список звучащих приложений —
  `IAudioSessionManager2` с активными сессиями, сгруппированными по
  корневому процессу.
- Process loopback не сообщает формат через `GetMixFormat`: задаём его
  сами (float32, 48 кГц, стерео), затем downsampler.
- Зависимость: фичи `windows-sys` или крейт `windows` для COM. Код —
  в `platform/windows/`.

### 5.3 Идентификатор приложения

`AudioAppId` должен быть устойчив между запусками, чтобы его можно было
хранить в настройках хоткея:

- Linux: `application.process.binary`, если нет — `application.name`
  (для Flatpak — app id).
- Windows: имя исполняемого файла корневого процесса (`Telegram.exe`).

Пользователю показываем понятное имя, сохраняем идентификатор.

### 5.4 Смена источника во время записи

Внутри слушания (весь звук ↔ приложение) сессия `VoiceCaptureSession`
остаётся той же: закрываем старый поток, открываем новый и продолжаем слать
чанки в тот же канал. Для провайдера распознавания это непрерывный поток.
Разрыв, в том числе ожидание потока приложения, заполняем тишиной, чтобы
не сбить временные метки и не дать провайдеру закрыть соединение
по простою.

Смена режима (голосовой ввод ↔ слушание) — это новая сессия: у режимов
разные настройки распознавания (команды, коррекция, endpoint).

### 5.5 Длинные сессии и провайдеры

Общий лимит в 1 час длиннее, чем живёт сессия у части облачных стриминговых
провайдеров (например, у Gemini Live аудиосессия ограничена по времени).
Перед реализацией сверить фактические лимиты каждого провайдера. Где
сессия короче часа — прозрачно переподключаться, сохраняя уже распознанный
текст. Это касается и голосового ввода.

## 6. Контракты и фронтенд

Rust:

- Команда `list_audio_apps` → `AudioApp[] { id, label, iconName?, level }`
  и событие `audio-apps-changed` для живого обновления списка. Отслеживать
  потоки только пока открыт выпадающий список или идёт ожидание приложения.
- `start_capture` получает `source: CaptureSource`.
- Команда `switch_capture_source(sessionId, source)`.
- Новая активация `ActivationMode::Listen` с параметром источника в конфиге
  хоткеев. По умолчанию без хоткея, как другие голосовые активации кроме
  `voice` и `voiceCommands`. Повторное срабатывание при активной сессии
  слушания — событие «стоп» для оверлея, а не новая сессия.
- Флаг «не скрывать при потере фокуса» для окна `quick` на всё время
  показа в режиме слушания, включая меню действий; вместо
  `hide_quick_window_on_blur`.
- `canListen` и `canMoveOverlay` в состоянии окна / сессии.
- Поле `kind` у записи истории.
- После изменений — `pnpm generate:desktop`.

Фронтенд:

- Новый вид `ListenView` (маршрут в `lib/navigation/routes.ts`) рядом с
  `VoiceView`. Общие компоненты панели (`VoiceRecordingBar`,
  `AudioWaveform`, `LiveTranscript`) переиспользуются, режимные отличия
  передаются параметрами, а не условиями внутри компонентов.
- Модель `lib/listen/listen-model.ts` с тестами: выбор источника, ожидание
  приложения после его исчезновения, автостоп, стоп по повторному
  хоткею, пустая расшифровка, переход в меню действий и в голосовой ввод
  с контекстом.
- `lib/stt/voice-capture.ts` и `voice-session.ts` принимают источник
  и набор возможностей сессии (команды, коррекция, endpoint). Таймеры
  тишины и лимита общие.
- Голосовой ввод принимает необязательный контекст (расшифровку) для
  коррекции и ИИ-ответа.
- Переключатель режима — общий компонент для обоих видов.
- Все новые строки — во все локали (`pnpm check:i18n`).

## 7. Перемещение окна `quick`

Только штатными средствами платформы, без обходных путей. Где штатного
способа нет — оверлей не перемещается.

| Окружение                                    | Как                                     | Делаем                        |
| -------------------------------------------- | --------------------------------------- | ----------------------------- |
| Windows                                      | `startDragging()` из Tauri              | да                            |
| X11                                          | `startDragging()` из Tauri              | да                            |
| Wayland без layer-shell (GNOME)              | `startDragging()` → `xdg_toplevel.move` | да, если композитор выполняет |
| Wayland с layer-shell (KWin, Hyprland, Sway) | —                                       | см. ниже                      |

Layer-shell-поверхность не перемещается как окно по протоколу: положение
задаётся якорем и отступами (`margin`). Менять отступы во время перетаскивания —
допустимое использование протокола, но это своё перетаскивание, а не
системное (нужно самим отслеживать указатель, сдвигать область ввода
`set_panel_input_region`, ограничивать монитором). **Решение: в первой
версии на layer-shell не перемещаем.** Вернуться к этому, если на KWin
оверлей заметно мешает в реальном использовании.

Прочее:

- Тянуть можно за ручку ⋮⋮ на панели (`startDragging()` по `mousedown`), но
  не за кнопки и текст.
- Кнопка или ручка показывается только там, где перемещение работает.
  Решает Rust (`platform::session::current()` и наличие layer-shell),
  фронтенд получает `canMoveOverlay` в состоянии окна.
- Позиция не сохраняется: при каждом новом показе окна `quick` применяется
  позиция по умолчанию. Переход между видами внутри одного показа
  (слушание → меню действий → голосовой ввод) положение сохраняет.

## 8. Приватность

- Запись только по явному действию. Пока она идёт, это видно в оверлее,
  и там же видно, какой источник слушается.
- Отдельного предупреждения нет. Иконка ⓘ в панели слушания объясняет:
  при облачном распознавании (Deepgram, Gemini) звук, включая чужую речь,
  уходит выбранному провайдеру; Sherpa отправляет звук настроенному серверу.
  Звук остаётся на компьютере только при локальном сервере. Тот же текст —
  в пользовательской документации.
- Ничего не сохраняем на диск, кроме итогового текста по обычным правилам
  истории.

## 9. Тесты

- Rust: группировка потоков по приложению, ожидание при пропаже, смена
  источника внутри сессии, заполнение разрыва тишиной — на фейковом
  бэкенде, без PipeWire и WASAPI; выбор `canMoveOverlay` и `canListen`;
  повторная активация `Listen` как «стоп».
- Фронтенд: `listen-model`, `ListenView` (нет вставки, нет команд, не
  скрывается по blur, пустая расшифровка), меню действий с расшифровкой,
  «Ответить голосом» с контекстом, переключатель режимов, сброс позиции
  при новом показе.
- VM-тесты (`dev_docs/vm-testing.md`): воспроизвести WAV через `pw-play`
  и на Windows, проверить, что захват получает звук; «Всё, кроме TyCo»
  на Windows; Flatpak-плеер на Linux.
- Ручная проверка: Telegram Desktop и Chromium/Firefox на обеих платформах,
  перетаскивание на Windows, X11, GNOME; сессия дольше лимита провайдера.

## 11. Как сделано (этапы 1–3) и отличия от дизайна

- ✅ Захват: `CaptureSource` в `services/voice/source.rs`, PipeWire —
  `platform/audio/pipewire.rs`, WASAPI — `platform/audio/wasapi.rs`,
  микширование потоков приложения — `voice/mixer.rs`, заполнение разрывов
  тишиной и смена источника внутри сессии — в цикле `voice.rs`.
  Linux проверен вживую (`integration_records_the_system_sound_and_one_application`).
  Windows-код компилируется под `x86_64-pc-windows-msvc`, но на Windows
  не запускался — нужна ручная проверка из раздела 9.
- Идентичность приложения на Linux берётся у **клиента** PipeWire
  (`client.id` узла): у узла потока нет бинарника, а его имя может
  отличаться (`pw-play` играет как клиент `pw-cat`).
- Список приложений — не глобальное событие `audio-apps-changed`, а канал:
  `watch_audio_apps` / `unwatch_audio_apps`. Уровень на Linux — через
  потоки пиков (`resample.peaks`), на Windows — `IAudioMeterInformation`.
- Источник хоткея хранится в `stt.listenAppId` / `stt.listenAppLabel`
  (значения хоткеев — строки), поле показано под хоткеем «Слушать» в
  настройках.
- История: вместо нового поля `kind` — существующее `origin` со значением
  `listen` и фильтр «Слушание».
- Переключение режима — `switch_quick_mode` (новая активация без
  перепоказа окна), клавиша **Alt+L**: Tab в голосовом вводе уже занят
  («дальше»).
- «Ответить голосом»: расшифровка показывается над панелью диктовки и
  передаётся в коррекцию (`voiceCorrectionRules`). В ИИ-запросе из меню
  результата она становится контекстом, а надиктованный текст — запросом;
  это работает и для буферизованного хоткея действия.
- Звуки самого TyCo: интерфейс звуков не проигрывает, глушить нечего.
- Не скрывается по blur: режим `listen` не входит в `DISMISSIBLE_MODES`,
  плюс удержание `useQuickDismissStore`.

## 12. Исправления после проверки

- «Стоп» отменяет ещё не завершившуюся проверку ключей: захват не может
  стартовать после показа пустого результата. Поздние ошибки запуска
  не заменяют уже готовый результат.
- Смена источников сериализована, ожидающие операции не меняют новую
  сессию. Статус ожидания приходит и для сразу доступного приложения.
- Наблюдение списка освобождается и при позднем ответе после размонтирования.
- Windows захватывает все независимые корни приложения и перечисляет
  сессии на всех активных render endpoints, включая новые устройства.
- Ошибки нативного захвата сообщаются явно. Перекрытие двух потоков
  при смене источника удаляется на границе передачи.
- PipeWire перепроверяется после запуска приложения и восстановления сервера.
- При исчезновении приложения слушание ждёт тот же источник; переход
  на весь звук требует явного выбора. Это изменение исходного дизайна.
- Для Gemini в слушании нет короткого отсечения по тишине; тихий звук
  передаётся. Длинные соединения меняются с сохранением очереди захвата,
  текста и смещения временных меток, без повторной отправки аудио.
- Подсказка ⓘ уточняет: Sherpa может быть удалённым сервером, поэтому
  локальность зависит от настроенного адреса. Обновлены все локали.
