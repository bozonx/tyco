# Режим «Слушание»: расшифровка звука компьютера

Статус: дизайн, к реализации не приступали.
Дата: 2026-11-08

## 1. Задача

Пользователь слушает голосовое сообщение в Telegram, видео в браузере или
любой другой звук и хочет получить текст. Для этого вводим отдельный режим
оверлея — **«Слушание»**, рядом с оверлеем голосового ввода (окно `quick`,
`VoiceView` в режиме `bar`, активация `voice`). Между двумя режимами
можно переключаться кнопкой.

Голосовой ввод в чат, в быстрый запрос к ИИ и в голосовые команды
не меняется.

Не входит в задачу:

- расшифровка аудиофайлов (отдельная задача);
- фоновая запись или кольцевой буфер «последние N секунд». Запись идёт только
  после явного действия пользователя.

## 2. Почему отдельный режим

У голосового ввода и слушания разное всё, кроме внешнего вида:

| | Голосовой ввод | Слушание |
|---|---|---|
| Источник | микрофон | весь звук или приложение |
| Чья речь | пользователя | чужая |
| Голосовые команды | да | нет |
| Контекстная коррекция | да | нет |
| Автостоп по тишине | да | нет (паузы между сообщениями) |
| Скрытие при потере фокуса | да | нет (пользователь кликает в плеер) |
| Конечное действие | вставка в целевое окно | меню результата |

Если сделать это одним режимом с выбором источника, каждое из этих отличий
станет условием «если источник не микрофон». Отдельный режим проще и
понятнее пользователю. Общее — компоненты панели (волна, живой текст,
кнопки), сессия распознавания и транспорт звука.

## 3. Сценарии

1. **Хоткей «Слушать звук компьютера».** Сразу открывает оверлей в режиме
   «Слушание» и начинает запись всего звука компьютера (или приложения,
   выбранного в настройках для этого хоткея). Пользователь сдвигает оверлей,
   если он закрывает сообщение, включает воспроизведение, затем
   останавливает запись и получает текст.
2. **Переключение режима.** В панели обоих режимов есть кнопка
   «🎤 ⇄ 🔊»: из голосового ввода — на слушание и обратно.
3. **Выбор источника в слушании.** «Весь звук» или конкретное приложение из
   тех, что сейчас воспроизводят звук. Источник можно сменить во время
   записи без потери текста.
4. **Перемещение оверлея мышью.** Касается всех оверлеев окна `quick`, там,
   где платформа это позволяет штатно (см. 7). Позиция не сохраняется.

## 4. UX

### 4.1 Панель слушания

```
[🎤⇄🔊]  [🔊 Весь звук ▾]   ~~~~ волна ~~~~   00:12   [Стоп]
            ├ 🔊 Весь звук
            ├ ── Сейчас играет ──
            ├ Telegram           ▮▮▯
            └ Firefox            ▮▯▯
```

- Панель визуально отличается от голосового ввода (иконка 🔊 и подпись
  «Слушаю»), чтобы не перепутать, что записывается.
- В списке приложений только те, у которых сейчас есть поток воспроизведения.
  Список обновляется на лету: Telegram появляется, когда начинает играть.
  Рядом — уровень звука, чтобы было видно, кто сейчас звучит.
- Выбор в оверлее действует до конца сессии и не запоминается. Хоткей
  слушания всегда начинает со своего источника из настроек.
- Если источник пропал (приложение закрыли), запись не обрывается. Она
  переключается на «Весь звук», а в оверлее показывается сообщение об этом.

### 4.2 Переключение режима

- Кнопка переключает режим в том же окне `quick`, без закрытия и без сброса
  позиции.
- Переключение во время записи останавливает текущий захват и начинает
  новый в другом режиме. Уже распознанный текст не теряется: если он есть,
  сначала показывается меню результата текущего режима, а переключатель
  остаётся в нём доступен.
- Тот же переключатель — в меню результата слушания: «Ответить голосом»
  открывает голосовой ввод. Это главный сценарий: прослушал сообщение —
  надиктовал ответ. Передавать ли расшифровку как контекст для ответа —
  открытый вопрос (см. 11).
- Хоткей переключения — в подсказках оверлея (`ShortcutList`), например Tab.

### 4.3 Поведение режима «Слушание»

- **Оверлей не прячется при потере фокуса.** Пользователь кликает в Telegram,
  чтобы включить сообщение. Скрывается только по «Стоп», «Отмена» или Esc
  (Esc работает, когда оверлей в фокусе).
- **Результат не вставляется автоматически.** Показывается `InsertMenu`:
  копировать, вставить, открыть в редакторе, отправить в чат,
  «Ответить голосом».
- **Нет голосовых команд, контекстной коррекции и автостопа по тишине.**
  Вместо автостопа — лимит длительности с предупреждением (значение —
  открытый вопрос).
- **Звуки самого TyCo** не попадают в запись: на Windows процесс TyCo
  исключается системой (см. 5.2), на Linux звуки интерфейса не
  проигрываются, пока идёт слушание.

### 4.4 Настройки

В настройках хоткеев у новой активации есть поле «Источник»:
«Весь звук» (по умолчанию) или приложение.

- Приложение выбирается из списка звучащих сейчас или вводится по имени.
  Хранится устойчивый идентификатор (см. 5.3), а не PID.
- Если при нажатии хоткея приложение не воспроизводит звук, запись ждёт его
  потока. В оверлее при этом написано «Ждём звук из Telegram…», и там же
  можно переключиться на «Весь звук».

## 5. Захват звука

Новый вариант источника в `services/voice` поверх трейта `AudioSource`.
Выход тот же: PCM16 моно 16 кГц чанками по 100 мс через тот же канал.
Провайдер распознавания не знает, откуда звук.

```rust
pub enum CaptureSource {
    Microphone,
    SystemMix,
    Application(AudioAppId),
}
```

Платформенная часть — в `services/platform/audio/` (сейчас это
`platform/audio.rs`, разнести по файлам): микрофон через CPAL, звук
компьютера — нативно.

### 5.1 Linux (PipeWire)

CPAL здесь не подходит: он не умеет ни monitor-источники, ни отдельные
потоки приложений.

- Используем `pipewire-rs`. Список звучащих приложений — узлы с
  `media.class = Stream/Output/Audio`: имя из `application.name`,
  бинарник из `application.process.binary`, иконка из `application.icon-name`.
- **Весь звук:** поток захвата с `stream.capture.sink = true`, цель —
  sink по умолчанию. Следуем за сменой устройства по умолчанию
  (наушники ↔ колонки).
- **Приложение:** поток захвата с `target.object`, равным serial узла
  приложения. У одного приложения может быть несколько потоков (у браузера —
  по вкладке, у Telegram — новый поток на каждое сообщение). Поэтому
  подключаемся ко всем потокам с данным `AudioAppId` и подключаем новые,
  когда они появляются. Микширование в моно — у нас.
- Свои потоки (процесс TyCo) из «Всего звука» исключить нельзя: monitor
  отдаёт уже готовый микс. Решение — не проигрывать свои звуки во время записи.
- Чистый PulseAudio без PipeWire: только «Весь звук» через monitor-источник
  (`libpulse`). Выбор приложения не показывается. Перед реализацией стоит
  решить, поддерживать ли такой случай вообще.
- Flatpak-версия Telegram и браузеры в sandbox видны в PipeWire как обычные
  потоки. Проверить имена в VM-тестах.

### 5.2 Windows (WASAPI)

- **Весь звук:** process loopback в режиме
  `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE` с PID самого TyCo:
  весь звук без наших собственных звуков. Запасной вариант на старых
  сборках — обычный loopback устройства по умолчанию.
- **Приложение:** `ActivateAudioInterfaceAsync` с
  `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`,
  `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`. Нужна Windows 10 2004
  (сборка 19041) или новее. На более старых показываем только «Весь звук».
- Браузеры воспроизводят звук из дочернего процесса (audio service у Chromium).
  Поэтому берём PID **корневого** процесса приложения, тогда режим
  `…_PROCESS_TREE` захватит и детей. Список звучащих приложений —
  `IAudioSessionManager2` с активными сессиями, сгруппированными по
  корневому процессу.
- Process loopback не сообщает формат через `GetMixFormat`: задаём его
  сами (float32, 48 кГц, стерео), затем downsampler.
- Зависимость: фичи `windows-sys` или крейт `windows` для COM. Код —
  в `platform/windows/`.

### 5.3 Идентификатор приложения

`AudioAppId` должен быть устойчив между запусками, чтобы его можно было
хранить в настройках хоткея:

- Linux: `application.process.binary`, если нет — `application.name`
  (для Flatpak — app id).
- Windows: имя исполняемого файла корневого процесса (`Telegram.exe`).

Пользователю показываем понятное имя, сохраняем идентификатор.

### 5.4 Смена источника во время записи

Внутри слушания (весь звук ↔ приложение) сессия `VoiceCaptureSession` остаётся той же: закрываем старый поток,
открываем новый и продолжаем слать чанки в тот же канал. Для провайдера
распознавания это непрерывный поток. Короткий разрыв заполняем тишиной,
чтобы не сбить временные метки.

Смена режима (голосовой ввод ↔ слушание) — это новая сессия: у режимов
разные настройки распознавания (команды, коррекция, автостоп).

## 6. Контракты и фронтенд

Rust:

- Команда `list_audio_apps` → `AudioApp[] { id, label, iconName?, level }`
  и событие `audio-apps-changed` для живого обновления списка. Отслеживать
  потоки только пока открыт выпадающий список или идёт ожидание приложения.
- `start_capture` получает `source: CaptureSource`.
- Команда `switch_capture_source(sessionId, source)`.
- Новая активация `ActivationMode::Listen` с параметром источника в конфиге
  хоткеев. По умолчанию без хоткея, как другие голосовые активации кроме
  `voice` и `voiceCommands`.
- Флаг «не скрывать при потере фокуса» для окна `quick` на время слушания.
- После изменений — `pnpm generate:desktop`.

Фронтенд:

- Новый вид `ListenView` (маршрут в `lib/navigation/routes.ts`) рядом с
  `VoiceView`. Общие компоненты панели (`VoiceRecordingBar`,
  `AudioWaveform`, `LiveTranscript`) переиспользуются, режимные отличия
  передаются параметрами, а не условиями внутри компонентов.
- Модель `lib/listen/listen-model.ts` с тестами: выбор источника, откат
  к «Всему звуку», ожидание приложения, лимит длительности, переход
  в голосовой ввод.
- `lib/stt/voice-capture.ts` и `voice-session.ts` принимают источник
  и набор возможностей сессии (команды, коррекция, автостоп).
- Переключатель режима — общий компонент для обоих видов.
- Все новые строки — во все локали (`pnpm check:i18n`).

## 7. Перемещение окна `quick`

Только штатными средствами платформы, без обходных путей. Где штатного
способа нет — оверлей не перемещается.

| Окружение | Как | Делаем |
|---|---|---|
| Windows | `startDragging()` из Tauri | да |
| X11 | `startDragging()` из Tauri | да |
| Wayland без layer-shell (GNOME) | `startDragging()` → `xdg_toplevel.move` | да, если композитор выполняет |
| Wayland с layer-shell (KWin, Hyprland, Sway) | — | см. ниже |

Layer-shell-поверхность не перемещается как окно по протоколу: положение
задаётся якорем и отступами (`margin`). Менять отступы во время перетаскивания —
допустимое использование протокола, но это своё перетаскивание, а не
системное (нужно самим отслеживать указатель, сдвигать область ввода
`set_panel_input_region`, ограничивать монитором). **Решение: в первой
версии на layer-shell не перемещаем.** Вернуться к этому, если на KWin
оверлей заметно мешает в реальном использовании.

Прочее:

- Тянуть можно за ручку ⋮⋮ на панели (`startDragging()` по `mousedown`), но
  не за кнопки и текст.
- Кнопка или ручка показывается только там, где перемещение работает.
  Решает Rust (`platform::session::current()` и наличие layer-shell),
  фронтенд получает `canMoveOverlay` в состоянии окна.
- Позиция не сохраняется: при каждом новом показе окна `quick` применяется
  позиция по умолчанию. Переход между видами внутри одного показа
  (слушание → меню результата → голосовой ввод) положение сохраняет.

## 8. Приватность

- Запись только по явному действию. Пока она идёт, это видно в оверлее,
  и там же видно, какой источник слушается.
- При облачном распознавании (Deepgram, Gemini) к провайдеру уходит **чужая
  речь** — голос собеседника. При первом использовании слушания
  с облачным провайдером показать одно короткое предупреждение.
  Локальный вариант (sherpa) это снимает.
- Ничего не сохраняем на диск, кроме итогового текста по обычным правилам
  истории.

## 9. Тесты

- Rust: группировка потоков по приложению, откат при пропаже, смена
  источника внутри сессии — на фейковом бэкенде, без PipeWire и WASAPI;
  выбор `canMoveOverlay` по типу сессии.
- Фронтенд: `listen-model`, `ListenView` (нет вставки, нет команд),
  переключатель режимов, сброс позиции при новом показе.
- VM-тесты (`dev_docs/vm-testing.md`): воспроизвести WAV через `pw-play`
  и на Windows, проверить, что захват получает звук; «Всё, кроме TyCo»
  на Windows; Flatpak-плеер на Linux.
- Ручная проверка: Telegram Desktop и Chromium/Firefox на обеих платформах,
  перетаскивание на Windows, X11, GNOME.

## 10. Этапы

1. Перемещение окна `quick` там, где это работает штатно.
2. Режим «Слушание» с захватом «Всего звука» на Linux и Windows, хоткей,
   переключатель режимов, поведение из 4.3.
3. Список звучащих приложений, захват отдельного приложения, источник
   в настройках хоткея.
4. Предупреждение о приватности для облачных провайдеров, VM-тесты.
