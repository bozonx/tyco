# Расшифровка звука компьютера в оверлее голосового ввода

Статус: дизайн, к реализации не приступали.
Дата: 2026-11-08

## 1. Задача

Пользователь слушает голосовое сообщение в Telegram, видео в браузере или
любой другой звук и хочет получить текст. Делаем это на базе оверлея голосового
ввода: окно `quick`, `VoiceView` в режиме `bar`, активация `voice`.
Голосовой ввод в чат, в быстрый запрос к ИИ и в голосовые команды
не меняется.

Не входит в задачу:

- расшифровка аудиофайлов (отдельная задача);
- фоновая запись или кольцевой буфер «последние N секунд». Запись идёт только
  после явного действия пользователя.

## 2. Сценарии

1. **Хоткей «Расшифровать звук компьютера».** Сразу открывает оверлей и
   начинает запись всего звука компьютера (или приложения, выбранного
   в настройках для этого хоткея). Пользователь сдвигает оверлей, если он
   закрывает сообщение, включает воспроизведение, затем останавливает запись
   и получает текст.
2. **Переключение источника в оверлее.** В обычном оверлее голосового ввода
   есть выбор источника: «Микрофон», «Весь звук», конкретное приложение из
   тех, что сейчас воспроизводят звук. Источник можно сменить во время записи:
   звук продолжает идти в ту же сессию распознавания.
3. **Перемещение оверлея мышью.** Касается всех оверлеев окна `quick`. Позиция
   не сохраняется: каждый показ начинается с позиции по умолчанию.

## 3. UX

### 3.1 Выбор источника

Компактный выпадающий список в панели оверлея, рядом с индикатором записи:

```
[🔊 Весь звук ▾]   ~~~~ волна ~~~~   00:12   [Стоп]
   ├ 🎤 Микрофон
   ├ 🔊 Весь звук
   ├ ── Сейчас играет ──
   ├ Telegram           ▮▮▯
   └ Firefox            ▮▯▯
```

- В списке приложений только те, у которых сейчас есть поток воспроизведения.
  Список обновляется на лету: Telegram появляется, когда начинает играть.
  Рядом с приложением — уровень звука, чтобы было видно, кто сейчас звучит.
- Название источника всегда видно на кнопке. По нему сразу понятно, что
  слушается, и функцию не надо искать в настройках.
- Выбор в оверлее действует до конца сессии и не запоминается. Обычный
  хоткей голосового ввода всегда начинает с микрофона, хоткей звука
  компьютера — со своего источника из настроек. Предсказуемость важнее
  экономии одного клика.
- Если источник пропал (приложение закрыли), запись не обрывается. Она
  переключается на «Весь звук», а в оверлее показывается сообщение об этом.

### 3.2 Настройки

В настройках хоткеев у новой активации есть поле «Источник»:
«Весь звук» (по умолчанию) или приложение.

- Приложение выбирается из списка запущенных и звучащих сейчас или вводится
  по имени. Хранится устойчивый идентификатор (см. 4.3), а не PID.
- Если при нажатии хоткея приложение не воспроизводит звук, запись ждёт его
  потока. В оверлее при этом написано «Ждём звук из Telegram…», и там же
  можно сразу переключиться на «Весь звук».

### 3.3 Что меняется, пока слушается звук компьютера

- **Оверлей не прячется при потере фокуса.** Пользователь кликает в Telegram,
  чтобы включить сообщение. Если оверлей скроется при потере фокуса, функция
  не работает. Пока идёт запись звука компьютера, оверлей скрывается только
  по «Стоп», «Отмена» или Esc.
- **Результат по умолчанию не вставляется автоматически.** При диктовке
  текст вставляется в целевое окно (`insertIntoTarget`). Для расшифровки
  целевым окном станет Telegram или браузер, куда текст никто не просил.
  Здесь результат показывается в `InsertMenu`: копировать, вставить,
  открыть в редакторе, отправить в чат.
- **Голосовые команды и контекстная коррекция выключены.** Они рассчитаны
  на речь самого пользователя, а не на чужое сообщение.
- **Автостоп по тишине мягче или выключен.** Между сообщениями бывают паузы,
  и пользователь может переключаться между ними. Предлагаю выключить
  автостоп для источников звука компьютера, а запись ограничить разумным
  лимитом времени с предупреждением.
- **Звуки самого TyCo** (звуки начала и конца записи) не должны попадать
  в запись. Для «Всего звука» исключаем процесс TyCo (см. 4), а звуки
  интерфейса не проигрываем, пока идёт запись.

### 3.4 Перемещение оверлеев

- Ручка перетаскивания — край панели или иконка ⋮⋮. Тянуть можно за пустую
  область панели, но не за кнопки и поле ввода.
- Двигаем в пределах текущего монитора, не даём уехать за край.
- Позиция не сохраняется: при каждом новом показе окна `quick` она
  сбрасывается к позиции по умолчанию. Переход между видами внутри одного
  показа (например, оверлей → `InsertMenu`) положение сохраняет, иначе
  результат «прыгнет» обратно.

## 4. Захват звука

Новый вариант источника в `services/voice` поверх трейта `AudioSource`.
Выход тот же: PCM16 моно 16 кГц чанками по 100 мс через тот же канал.
Распознавание и фронтенд не знают, откуда звук.

```rust
pub enum CaptureSource {
    Microphone,
    SystemMix,
    Application(AudioAppId),
}
```

Платформенная часть — в `services/platform/audio/` (сейчас это
`platform/audio.rs`, разнести по файлам): микрофон через CPAL, звук
компьютера — нативно.

### 4.1 Linux (PipeWire)

CPAL здесь не подходит: он не умеет ни monitor-источники, ни отдельные
потоки приложений.

- Используем `pipewire-rs`. Список звучащих приложений — узлы с
  `media.class = Stream/Output/Audio`: имя из `application.name`,
  бинарник из `application.process.binary`, иконка из `application.icon-name`.
- **Весь звук:** поток захвата с `stream.capture.sink = true`, цель —
  sink по умолчанию. Следуем за сменой устройства по умолчанию
  (наушники ↔ колонки).
- **Приложение:** поток захвата с `target.object`, равным serial узла
  приложения. У одного приложения может быть несколько потоков (у браузера —
  по вкладке, у Telegram — новый поток на каждое сообщение). Поэтому
  подключаемся ко всем потокам с данным `AudioAppId` и подключаем новые,
  когда они появляются. Микширование в моно — у нас.
- Свои потоки (процесс TyCo) из «Всего звука» исключить нельзя: monitor
  отдаёт уже готовый микс. Решение — не проигрывать свои звуки во время записи.
- Чистый PulseAudio без PipeWire: только «Весь звук» через monitor-источник
  (`libpulse`). Выбор приложения не показывается. Перед реализацией стоит
  решить, поддерживать ли такой случай вообще.
- Flatpak-версия Telegram и браузеры в sandbox видны в PipeWire как обычные
  потоки. Проверить имена в VM-тестах.

### 4.2 Windows (WASAPI)

- **Весь звук:** process loopback в режиме
  `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE` с PID самого TyCo:
  весь звук без наших собственных звуков. Запасной вариант на старых
  сборках — обычный loopback устройства по умолчанию.
- **Приложение:** `ActivateAudioInterfaceAsync` с
  `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`,
  `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`. Нужна Windows 10 2004
  (сборка 19041) или новее. На более старых показываем только «Весь звук».
- Браузеры воспроизводят звук из дочернего процесса (audio service у Chromium).
  Поэтому берём PID **корневого** процесса приложения, тогда режим
  `…_PROCESS_TREE` захватит и детей. Список звучащих приложений —
  `IAudioSessionManager2` с активными сессиями, сгруппированными по
  корневому процессу.
- Process loopback не сообщает формат через `GetMixFormat`: задаём его
  сами (float32, 48 кГц, стерео), затем downsampler.
- Зависимость: фичи `windows-sys` или крейт `windows` для COM. Код —
  в `platform/windows/`.

### 4.3 Идентификатор приложения

`AudioAppId` должен быть устойчив между запусками, чтобы его можно было
хранить в настройках хоткея:

- Linux: `application.process.binary`, если нет — `application.name`
  (для Flatpak — app id).
- Windows: имя исполняемого файла корневого процесса (`Telegram.exe`).

Пользователю показываем понятное имя, сохраняем идентификатор.

### 4.4 Смена источника во время записи

Сессия `VoiceCaptureSession` остаётся той же: закрываем старый поток,
открываем новый и продолжаем слать чанки в тот же канал. Для провайдера
распознавания это непрерывный поток. Короткий разрыв заполняем тишиной,
чтобы не сбить временные метки.

## 5. Контракты

- Команда `list_audio_apps` → `AudioApp[] { id, label, iconName?, level }`
  и событие `audio-apps-changed` для живого обновления списка.
  Опрашивать только пока открыт выпадающий список.
- `start_capture` получает `source: CaptureSource`.
- Команда `switch_capture_source(sessionId, source)`.
- Новая активация `ActivationMode::VoiceSystemAudio` с параметром источника
  в конфиге хоткеев. По умолчанию без хоткея, как другие голосовые активации
  кроме `voice` и `voiceCommands`.
- После изменений — `pnpm generate:desktop`.

## 6. Фронтенд

- `lib/stt/voice-capture.ts` и `voice-session.ts` принимают источник.
  Логика выбора, отката к «Всему звуку» и ожидания приложения — в модели
  `lib/voice/capture-source-model.ts` с тестами.
- `VoiceRecordingBar.vue` — выпадающий список источника.
- `VoiceView` для источника звука компьютера ставит
  `finish-behavior="showResult"` (или аналог), без голосовых команд
  и коррекции.
- Перемещение: общий composable `use-overlay-drag` для окна `quick`.
  Компонент сообщает смещение, позицию двигает Rust (см. 7).
- Все новые строки — во все локали (`pnpm check:i18n`).

## 7. Перемещение окна `quick`

На разных платформах окно `quick` устроено по-разному, поэтому одного
`startDragging()` недостаточно:

- **Windows и X11:** обычное окно. Можно `startDragging()` у Tauri или
  своё перетаскивание через `set_position`. Свое удобнее: ограничение
  монитором и сброс позиции в одном месте.
- **Wayland с layer-shell:** окно — layer-surface, перетаскивание
  средствами окна не работает. Двигаем отступами (`margin`) якоря
  в `layer_shell`: фронтенд шлёт смещение во время перетаскивания,
  Rust пересчитывает отступы. Нужно учесть `set_panel_input_region`:
  область ввода сдвигается вместе с панелью.
- **Wayland без layer-shell:** позицию окна задать нельзя, остаётся
  `startDragging()` (xdg_toplevel move), если композитор разрешит.
- Сброс: в `position_quick_window` и в аналогах для layer-shell при каждом
  показе применяется позиция по умолчанию и обнуляется смещение.

Команда: `move_quick_window_by(dx, dy)` или `begin/update/end_overlay_drag`.
Конкретный вариант выбрать после прототипа на KWin и GNOME (Mutter
без layer-shell).

## 8. Приватность

- Запись только по явному действию. Пока она идёт, это видно в оверлее,
  и там же видно, какой источник слушается.
- При облачном распознавании (Deepgram, Gemini) к провайдеру уходит **чужая
  речь** — голос собеседника. При первом использовании звука компьютера
  с облачным провайдером показать одно короткое предупреждение.
  Локальный вариант (sherpa) это снимает.
- Ничего не сохраняем на диск, кроме итогового текста по обычным правилам
  истории.

## 9. Тесты

- Rust: модель источников (группировка потоков по приложению, откат при
  пропаже, смена источника внутри сессии) — на фейковом бэкенде, без PipeWire
  и WASAPI.
- Фронтенд: `capture-source-model`, выпадающий список в `VoiceRecordingBar`,
  `finish-behavior` для звука компьютера, сброс позиции оверлея.
- VM-тесты (`dev_docs/vm-testing.md`): воспроизвести WAV через `pw-play` или
  `paplay` и на Windows, проверить, что захват получает звук; «Всё, кроме
  TyCo» на Windows; Flatpak-плеер на Linux.
- Ручная проверка: Telegram Desktop и Chromium/Firefox на обеих платформах,
  перетаскивание на KWin, GNOME, Windows.

## 10. Этапы

1. Перемещение окна `quick` мышью со сбросом позиции (полезно отдельно).
2. Захват «Всего звука» на Linux и Windows, источник в оверлее,
   новая активация с хоткеем, поведение оверлея из 3.3.
3. Список звучащих приложений и захват отдельного приложения, источник
   в настройках хоткея.
4. Предупреждение о приватности для облачных провайдеров, VM-тесты.
